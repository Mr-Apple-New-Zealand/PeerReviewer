# Analysis of BANK-471: Payment receipt emails not delivered

## 1. What the log actually shows

The attached log covers only the period from the 18:02 pod restart to 18:40 (the 60 lines pulled by `kubectl logs --tail=60`). The previous container's log (covering ~14:00–18:02, when the outage actually started) **was not captured**.

The operative errors are unambiguous and repeat throughout:

```
System.Net.Mail.SmtpException: The SMTP server requires a secure connection or
the client was not authenticated. The server response was:
5.7.139 Authentication unsuccessful, basic authentication is disabled.
SMTP status code: 535
```

This is an **SMTP authentication rejection by the mail server** (`smtp.example.com:587`). The server has disabled basic authentication and is rejecting the credentials the notifications service is presenting. It affects multiple notification types (`payment-receipt`, `statement-ready`) and multiple customers (41082, 55617, 63340), confirming a systemic credential/config problem rather than a data-specific one.

Additional log facts:

- **1412 messages were already in the outbox at 18:02:48**, before the new pod had processed a single one. The queue grew to **2089 by 18:39:48** (~18/min).
- Outbox item 991204 (customer 41082) hit its 5-attempt cap at 18:03:08 and **stays at the head of the queue** with a fixed 5 s retry. There is **no backoff and no dead-letter path**, so one stuck item can block the entire dispatcher.
- At 18:05:00 the service logs its SMTP config: `host smtp.example.com:587, user svc-notify@example.com, StartTls=True`. Despite `StartTls=True`, the server still rejects the auth with 535.
- The health check at 18:21:09 reports **`smtp skipped`** – SMTP connectivity is not covered by the liveness/readiness probe.
- A brief NATS disconnect at 18:07:12 reconnected after 1 attempt. Almost certainly unrelated.
- Two data-protection warnings appear at startup (non-persisted key directory; no XML encryptor). These are real warnings but, as shown below, are not the cause of the email failures.

## 2. Does the log support Marcus's explanation?

**No.** Marcus's comment (18:44) attributes the failure to ASP.NET Data Protection keys being stored in a non-persisted directory with no XML encryptor, calling them "effectively junk" and asking Platform to fix key storage.

The log does not support this as the cause of the email outage:

- **Data Protection keys** encrypt/decrypt application-level data (anti-forgery tokens, cookie payloads, `IDataProtectionProvider`-protected values). They are **not** the mechanism used to authenticate to an SMTP server. SMTP credentials (`svc-notify@example.com` / password) are supplied via configuration (env vars, config file, secrets manager) and passed to `SmtpClient`. The log shows exactly that: a host, user, and `StartTls` flag.
- **A restart would not make things worse if this were a key-persistence problem** in the way Marcus frames it – the new container generates fresh keys. Yet the SMTP 535 errors were already present at 18:02:48, the very first outbox dispatch attempt of the new container, and 1,412 messages were already queued from before the restart.
- **The error text is explicit and specific**: `basic authentication is disabled`. This is a server-side policy change (or a credential that no longer matches what the server expects). It is not a symptom of missing or junk data-protection keys.

The data-protection warnings are a legitimate operational concern (any data encrypted by the service – e.g. anti-forgery tokens, protected cookies – will be lost on every pod restart) and should be fixed. But they are a **separate issue** from the email delivery failure and do not explain the SMTP 535.

> **Inference (labelled):** The most likely root cause is that the mail server at `smtp.example.com` had basic authentication disabled (security hardening, credential rotation, or an auth-policy change), and the notifications service was not updated to use the new mechanism (e.g. OAuth 2.0 / XOAUTH2) or the service account `svc-notify@example.com` was deactivated or its password rotated. This is inferred from the exact 5.7.139 response text and the fact that `StartTls=True` is set but the server still rejects the credential.

## 5. Risks and gaps

- **Wrong diagnosis driving work to the wrong team.** If Platform spends time migrating data-protection key storage (e.g. to a shared blob or K8s secret), the email outage will continue because the SMTP credential is still being rejected.
- **Growing backlog with no relief valve.** The outbox is growing ~18 msg/min. With no dead-letter queue and a 5 s fixed retry, one permanently-failing item (e.g. customer 41082) sits at the head of the queue and can starve all subsequent messages even after the auth issue is fixed. 1,412 messages were already stuck before the restart; the count reached 2,089 by 18:39.
- **No monitoring gap on SMTP.** The health check explicitly skips SMTP. A sustained SMTP auth failure went from ~14:00 to at least 18:40 (~4 h 40 min) without an automated alert, relying on customer call volume to surface it.
- **Missing historical logs.** The 18:02 pod restart destroyed the previous container's log. If this recurs, the evidence trail will be lost again. Pod restarts in production should capture logs first (or use a log shipper / persistent sidecar).
- **Data-protection key warnings are real but separate.** Any feature relying on `IDataProtectionProvider` (anti-forgery, cookie protection) will silently break after every pod restart. This should be tracked as its own ticket.
- **No linked tickets, sprint, or fix version** – the ticket is not yet part of any delivery plan, which is unusual for a Highest-priority production outage.
