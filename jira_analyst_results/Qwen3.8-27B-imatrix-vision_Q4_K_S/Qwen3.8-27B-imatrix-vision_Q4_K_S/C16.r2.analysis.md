# Log Comparison – BANK-482

## 1. Summary

The `GetStatementLineQuery` endpoint went from a stable ~300 ms to 34–73 s between the pre-release baseline (4.6.3) and the post-release window (4.7.0). No other endpoint regressed. The logs also show a thread-pool starvation event that appears to be a secondary effect of the long queries tying up worker threads.

---

## 2. Quantified Regression

| Metric | Before (4.6.3, 09-13) | After (4.7.0, 09-15) | Change |
|---|---|---|---|
| **GetStatementLineQuery** – n | 10 requests | 14 requests | – |
| Range | 281 – 319 ms | 33 757 – 72 974 ms | **~106× – ~260×** slower |
| Mean | 299.8 ms | 51 759 ms | **~173×** |
| Warnings | 0 | 14 × `[WRN] Long-running request` (threshold 10 000 ms) | New |
| **GetAccountSummaryQuery** – n | 4 requests | 4 requests | – |
| Range | 2 987 – 3 341 ms | 3 011 – 3 402 ms | Unchanged (within noise) |
| **ExportStatementCommand** | 1 840 ms | 1 902 ms | Unchanged |
| Health check `/healthz` (db) | 6 ms, Healthy | 9 ms, Healthy | Unchanged |

**Escalation pattern in the "after" log.** The 14 long queries are not uniformly slow. They cluster in two phases:

- **00:20:43 – 00:23:56** (8 queries): 33.8 s – 36.5 s
- **00:24:02 – 00:24:34** (6 queries): 41.5 s – 73.0 s, with three consecutive queries at ≈ 72 s

Between the two phases the log records:

> `2026-09-15 00:24:11 [WRN] ThreadPool starvation detected: 31 work items queued, 0 threads available for 4200ms.`

Because the long queries began at 00:20:43 and the starvation warning fired at 00:24:11, the starvation reads as a **consequence** of threads being held by slow queries, not the initial cause. The jump from ~35 s to ~72 s is consistent with a queue building up once available threads are exhausted.

## 3. What Changed Between the Two Windows

- **App version:** 4.6.3 → 4.7.0 (visible in the startup line).
- **Migration applied at deploy time:**
  > `2026-09-14 21:05:36 [INF] Applied 1 pending migration: 20260914_2100_ReindexStatementLines.`
  No equivalent line exists in the baseline log.
- **GetStatementLineQuery latency:** ~300 ms → 34–73 s (see table above).
- **Thread-pool starvation event:** present only in the after log.

## 4. What Did NOT Change

- **GetAccountSummaryQuery:** still ~3 s in both windows. (This directly contradicts Ravi Kumar's comment, see §6.)
- **ExportStatementCommand:** ~1.8–1.9 s in both windows.
- **Database health check:** 6 ms → 9 ms; still "Healthy". No evidence of DB outage or connectivity problem.
- **Request mix and cadence:** the same three endpoint types appear at similar spacing in both windows; no new endpoint or unexpected call pattern.

---

## 5. What These Logs Cannot Establish

- **Root cause of the query slowdown.** The logs record latency but contain no SQL text, query plan, index statistics, row counts, or connection-pool metrics. We cannot tell from these logs *why* `GetStatementLineQuery` is slow.
- **Whether the migration is the cause.** The migration is named `ReindexStatementLines`, which is topically relevant, but the log only records that it "applied" successfully. It does not show whether the index was created on the correct column, whether it was a CONCURRENTLY build that left a stale index behind, whether it failed silently on a partial segment, or whether the query's planner is simply not using the new index. The correlation is suggestive, not conclusive.
- **When the degradation started.** The migration ran at 21:05:36 on 09-14; the after-log window starts at 00:19:08 on 09-15, roughly 3 h 14 min later. We do not know whether the slowdown was present from the first request after the migration or developed gradually.
- **User-facing impact.** The description mentions browser timeouts, but neither log shows an HTTP 504, a cancelled request, or an error response. The logs show server-side processing time only.
- **Concurrency / load differences.** Both windows are 5-minute samples. If the 09-15 window happened to hit a different request volume, the comparison is confounded. (The request counts differ slightly – 10 vs 14 line queries – which is a small but real difference.)
- **Whether the problem is persistent or transient.** One 5-minute window cannot confirm whether the queries remain at 70 s or whether they eventually recover (e.g., after the reindex completes or the index is rebuilt).
- **Any other environmental change** (infra scaling, other deployments, database compaction, network) that coincided with the release.

## 6. Conflicts Between the Logs and the Comments

- **Tom Becker (09:20):** *"Nothing in 4.7.0 touched statements. The release was notifications and the admin screens."*
  The after-log shows a migration explicitly named **`ReindexStatementLines`** applied during the 4.7.0 deployment. Even if the *application code* changes were limited to notifications and admin screens, the 4.7.0 release **did** include a database migration that modifies the statement-lines table/index. The comment and the log contradict each other.

- **Ravi Kumar (09:40):** *"It'll be the account summary query. That one has always been slow, everyone knows it. I'd start there."*
  The logs show `GetAccountSummaryQuery` is essentially identical in both windows (≈ 3 s). The regression is entirely in `GetStatementLineQuery`. Ravi's suggested starting point is contradicted by the evidence attached to the ticket.

Neither comment should be treated as an authoritative diagnosis; the log data takes precedence.

## 7. Risks and Gaps

- **Production is actively degraded.** The description says branch staff are telling customers to call back. The after-log confirms 35–73 s per statement-line request with thread-pool starvation, which will cascade to other endpoints sharing the pool.
- **No fix version or sprint is set.** The ticket is still unassigned to a sprint and has no due date, despite a High priority and active customer impact.
- **Only two 5-minute samples.** A single before/after pair is the minimum evidence; there is no trend data over the hours since the migration.
- **No linked tickets or components beyond "Statements".** If the migration was authored under a different Jira key (e.g., a DBA or infrastructure ticket), it is not linked here, making the traceability chain incomplete.
- **Missing diagnostic data.** No `EXPLAIN` output, no `pg_stat_statements` / equivalent, no APM trace, no database slow-query log for the same window.
