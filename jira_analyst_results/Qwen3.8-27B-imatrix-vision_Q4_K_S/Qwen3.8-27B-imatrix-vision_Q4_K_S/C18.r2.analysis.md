# Sentry Triage – bank-ui, week 2026-09-05 → 09-12

## 1. Summary

Five of the seven open issues share a single root cause: **API calls returning HTTP 401**, which the UI does not handle gracefully, causing unhandled `TypeError` crashes on four different routes and a flood of handled console errors on a fifth. A sixth issue is a **chunk-404 that appeared six minutes after the 4.7.0 deploy** and is hitting the largest user count of any single issue. The seventh is **noise from a browser extension** on one user's machine and is not a bank-ui defect.

## 2. Grouping by cause

### Group A – 401 / auth cascade (5 issues)

| Sentry ID | Title (abbreviated) | Events | Users | Handled? |
|-----------|---------------------|--------|-------|----------|
| **BANKUI-3C8** | `HttpErrorResponse: 401 OK` on `GetAllRunBookingsForCustomerOrder` | 5 140 | 44 | Yes (console.error) |
| **BANKUI-4A1** | `…reading 'sort'` on `/settlements/run/8214` | 312 | 41 | **No** |
| **BANKUI-4A2** | `…reading 'rows'` on `/payments/batch/actions/allocation-reports` | 289 | 39 | **No** |
| **BANKUI-4A9** | `…reading 'returnProperties'` on `…/allocation-entry` | 104 | 33 | **No** |
| **BANKUI-4B3** | `…reading 'length'` on `/payments/batch/actions` | 97 | 31 | **No** |

**Inference (based on the breadcrumb data in each issue):** BANKUI-3C8 is the upstream event. Each of the four TypeErrors records 401 XHR responses in the 40 seconds immediately before the crash. The pattern is:

1. A backend call returns **401** (session/token expired or invalid).
2. The Angular `HttpClient` interceptor (or lack thereof) does **not** redirect to login or short-circuit the promise.
3. The calling component receives a response whose body is not the expected JSON shape.
4. The code does `data.sort()`, `data.rows`, `data.returnProperties`, or `data.length` on `undefined` → unhandled `TypeError`.

This is **two defects in one**:
- **Defect A1 – missing global 401 handling.** The app has no (or incomplete) `HttpInterceptor` that catches 401s, invalidates the session, and routes the user to a re-auth screen. Fixing this would prevent all four TypeErrors *and* reduce the 5 140 console-error events.
- **Defect A2 – defensive coding.** Even with an interceptor, individual data-access points should guard against a non-2xx payload rather than blindly dereferencing. This is a smaller, follow-up hardening task.

The **auth/infrastructure question** (why are 44 users in production getting 401s this frequently?) may or may not be a bank-ui code issue. It could be a token-refresh bug, a gateway timeout mismatch, or an identity-provider problem. That investigation is a dependency on the fix.

### Group B – Post-deploy chunk 404 (1 issue)

| Sentry ID | Details | Events | Users |
|-----------|---------|--------|-------|
| **BANKUI-5D6** | `ChunkLoadError: Loading chunk 6728 failed` – the bundle URL returns **404** | 63 | **58** |

- First seen **2026-09-10 21:11 UTC**, six minutes after the **4.7.0** deploy (21:05 UTC).
- Breadcrumb: a navigation immediately before; the requested bundle is a 404.
- **Inference:** Users who loaded the app shell *before* 4.7.0 still hold references to the old chunk map. When they navigate to a lazy route, the browser requests a chunk hash that no longer exists on the CDN. Alternatively, the 4.7.0 build did not publish all chunks (a pipeline/CDN-sync gap). The fact that 58 distinct users are affected (more than any other issue) makes this the **widest-reaching single problem** in this export.

## 3. What to work on first, and why

Given two slots:

### Slot 1 – Fix the 401 handling (Group A)

**Why first:**
- **5 Sentry issues collapse into one fix.** A proper `HttpInterceptor` for 401 (redirect to login / show "session expired" banner) eliminates the four unhandled TypeErrors *and* suppresses the 5 140 handled console errors.
- **Largest combined user impact:** 44 users hit the root 401; the four downstream TypeErrors each hit 31–41 users. Even with overlap, this is the broadest set of affected users.
- **Unhandled errors** mean users see a broken/blank screen, not just a log entry. In a banking UI this is a trust and usability problem.
- The ticket's own context: *"Last time we worked top down by event count and spent the sprint on something that turned out to affect one person."* BANKUI-2F0 is exactly that trap (4 812 events, 1 user). Group A is the opposite: moderate per-issue event counts but **real, multi-user, user-facing breakage**.

**Scope for the sprint task:**
1. Add / repair the global 401 `HttpInterceptor`: on 401, clear the auth token, show a re-auth prompt, and reject the pending observable with a typed error so components don't dereference the response body.
2. Audit the four affected routes (`/settlements/run/*`, `/payments/batch/actions/*`, `…/allocation-reports`, `…/allocation-entry`) and add null-guards on the response shape as a second line of defence.
3. Open a separate investigation ticket (or sub-task) for *why* 44 production users are getting 401s this week – token lifetime, refresh-token rotation, gateway config – and assign to the backend/auth team. The UI fix is necessary regardless, but the auth root cause is a parallel thread.

### Slot 2 – Investigate and fix the chunk-404 (BANKUI-5D6)

**Why second:**
- **58 users** – the highest user count of any single issue in this export, even more than the 44 on the root 401.
- It started **immediately after the 4.7.0 deploy** and was still firing at the end of the reporting window (last seen 2026-09-12 19:44 UTC). If it is a stale-asset / CDN-sync problem, it will keep hitting users who have a pre-deploy session open.
- The fix is likely operational (CDN purge, correct deploy ordering, or a "reload on chunk-load-failure" fallback in the Angular `ChunkLoadError` handler) rather than a deep code change, so it is tractable in a sprint.

**Scope:**
1. Confirm with the release/DevOps owner whether all 4.7.0 chunks were published to the CDN and whether a stale-asset purge was performed.
2. Add a `ChunkLoadError` handler in the Angular app: catch the failure, force a full page reload (which picks up the new chunk map), and report the event. This is a standard Angular 14+ pattern.
3. Verify the fix by loading the app on a 4.6.0-cached session and navigating to `/payments/batch/actions`.

## 4. Risks, gaps, and flags

- **Source maps are still not uploaded** (Ravi's comment, 2026-09-15). Every `lastFrame` in this export is a minified name (`ie.project`, `q.render`, `L.buildAction`, `N.setRows`, `a.loadChunk`). This makes root-cause analysis slower and makes the Sentry breadcrumbs the only real signal. This should be pulled into the next sprint as a prerequisite if it isn't already, because every future triage cycle will suffer the same problem.

- **Domain discrepancy to verify.** The Sentry query filters on `environment:Production`, yet the chunk-404 URL and the cross-origin SecurityError both reference **`https://bank-uat.example.com`**. Either (a) `bank-uat.example.com` is actually the production hostname (naming is misleading), or (b) these events are UAT traffic mis-tagged as Production. Worth a quick check with the platform team so the "Production" label can be trusted.

- **The 401 root cause may not be a bank-ui bug.** The UI fix (Slot 1) is necessary, but if the 401s are caused by, say, a gateway that expires tokens at 15 minutes while the app assumes 30, the *real* fix lives in the auth/gateway config. The UI interceptor is a band-aid without that. Flag this dependency explicitly when writing the sprint ticket.

- **BANKUI-1A7 `lastSeen` (Sep 11) post-dates the 4.6.0 fix (Aug 27).** Low risk, but if any users are still on a cached 4.5.x bundle they could be hitting the old stack-overflow bug. A CDN purge or a service-worker update prompt would close this out.

- **No acceptance criteria or reproduction steps** are present in the export for any issue. The JSON gives breadcrumbs but not the exact user action sequence. If the sprint tickets are to be testable, the QA team will need to reproduce the 401 scenario (e.g., let a token expire mid-session, then navigate to `/settlements/run`) and the chunk scenario (load pre-4.7.0, then navigate to a lazy route).

- **No linked tickets or sprints** are assigned to any of the seven Sentry issues. They are currently orphaned observations. Each should be linked to a Jira task once the two sprint slots are filled.
