# Analysis: BANK-412 – Transfer retry after timeout debits source account twice

## 1. Summary

A mobile-web transfer of $250 (cheque → savings) timed out with `ERR_TXN_504`; the customer tapped **Retry**, and the system processed the transfer a second time. The result is a **double debit** on the source account and a **single credit** on the destination. Priya Nair has identified two compounding root causes: the Retry button issues a fresh `POST /api/transaction/transfer` with **no idempotency key**, and the debit and credit are **not wrapped in a single database transaction**, so a credit-side timeout leaves the first debit permanently committed.

## 3. Key details

**Reproduction (staging, confirmed by Priya and independently by Tom Becker):**
1. Log in on **mobile web**; start a transfer between two own accounts.
2. Inject >30 s latency between API and DB (toxiproxy).
3. When `ERR_TXN_504` appears, tap **Retry**.

- **Expected:** one debit, one credit.
- **Actual:** two debits, one credit.

**Affected scope:**
- Version: **3.1.4** (fix targeted at 3.2.0).
- Platform: **Mobile web only.** Tom Becker confirmed it does **not** reproduce on desktop web, which disables the submit button and has no Retry affordance after a timeout.
- Labels: `customer-impact`, `mobile-web`.

**Log excerpt (from the 09-08 incident):**
```
09:41:02  debit committed  txn=8841  account=***1180  amount=250.00
09:41:32  credit FAILED    txn=8841  timeout after 30000ms
09:41:40  debit committed  txn=8842  account=***1180  amount=250.00
09:41:41  credit committed txn=8842  account=***2271  amount=250.00
```
This confirms the two-transaction sequence: txn 8841's debit survives the credit timeout; Retry creates a wholly separate txn 8842.

**Fix in flight (PR #218):**
- Wraps debit + credit in a **single DB transaction**.
- Adds an **Idempotency-Key header** to the transfer endpoint so a retry is recognised as the same logical operation.

**Missing from the ticket:**
- No explicit **acceptance criteria** beyond the one-line "one debit, one credit" in the repro. No guidance on what the UI should show if the idempotency key is rejected or if the single DB transaction itself times out.
- No **linked ticket** for the Finance reversal work or for any post-incident monitoring.
- No **screenshots** or support-call transcripts attached despite three customer reports.
- No **due date** set on the ticket itself (release target is only in a comment).
