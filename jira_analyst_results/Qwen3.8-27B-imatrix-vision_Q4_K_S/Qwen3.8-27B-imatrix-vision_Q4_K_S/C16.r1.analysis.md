# BANK-482 – Log Comparison: Before vs. After 4.7.0

## Summary

`GetStatementLineQuery` went from a steady ~300 ms to 35–73 s (a ~170× average slowdown) between the two windows. Every other operation in the service is unchanged. The only new artefact in the post-release log is a migration named `20260914_2100_ReindexStatementLines`, applied at deployment start. The regression is confined to the statement-lines query and escalates over the five-minute window, eventually triggering thread-pool starvation.

---

## Quantified regression

| Metric | Before (4.6.3, Sep 13) | After (4.7.0, Sep 15) | Change |
|---|---|---|---|
| **GetStatementLineQuery** – min | 281 ms | 33 757 ms | ~120× |
| **GetStatementLineQuery** – max | 319 ms | 72 974 ms | ~230× |
| **GetStatementLineQuery** – mean (10 vs 14 calls) | **300 ms** | **51 759 ms** | **~172×** |
| GetAccountSummaryQuery – range | 2 987–3 341 ms (n=4) | 3 011–3 402 ms (n=4) | ≈ 0 % |
| ExportStatementCommand | 1 840 ms | 1 902 ms | +3 % (noise) |
| Health check DB latency | 6 ms | 9 ms | Negligible |

### Escalation pattern in the "after" window

The statement-line queries do not degrade uniformly; they accelerate:

- 00:20:43 – 00:23:56: roughly **34–37 s** (6 calls)
- 00:24:02 – 00:24:05: **41–44 s** (2 calls)
- 00:24:21 – 00:24:34: **68–73 s** (6 calls, all within 13 seconds)

At 00:24:11 the log records:

> `ThreadPool starvation detected: 31 work items queued, 0 threads available for 4200ms.`

This is consistent with the long queries occupying every worker thread, so subsequent requests queue behind them.

## What changed

1. **App version:** 4.6.3 → 4.7.0 (new pod `statements-api-7d4a2f9c61-xr6vh` replaced `statements-api-6b9f4d7c85-w4lnp`).
2. **Migration applied at startup (21:05:36):**
   > `Applied 1 pending migration: 20260914_2100_ReindexStatementLines.`
   This is the only new line that is not a request or health check. It directly targets the statement-lines table.
3. **GetStatementLineQuery latency** – the sole operation that regressed.

## What did NOT change

- **GetAccountSummaryQuery:** identical ~3 s latency before and after. It was already slow in 4.6.3 and remains slow.
- **ExportStatementCommand:** ~1.9 s in both windows.
- **Database connectivity / health:** `db 6 ms` → `db 9 ms`; the database is reachable and responsive.
- **Request mix and cadence:** the same three query types appear at similar intervals in both windows.
- **Export path:** unaffected.

---

## Inference: likely root cause

**Inference (based on the migration name, the isolated query regression, and the escalation pattern):** The `ReindexStatementLines` migration either (a) dropped the existing index on the statement-lines table and the new index has not been built, or (b) built an index that the query planner is not using, forcing a full sequential scan. The progressive worsening (35 s → 73 s) and the thread-pool starvation are consistent with an increasingly contended full-table scan under concurrent requests. The fact that `GetAccountSummaryQuery` (different table/path) is untouched supports a statement-lines-specific index problem.

This is an inference; the logs do not contain query plans or index state.

---

## What these logs cannot establish

- **Whether the migration completed.** The log says "Applied," which in many migration frameworks means "started." There is no "Migration complete" or "Reindex finished" line. The reindex may still have been running during the Sep 15 00:18 window.
- **Query execution plans.** No `EXPLAIN` output is present, so we cannot confirm a missing index, a bad index, or a table lock.
- **Index state.** No `pg_stat_user_indexes`, `pg_stat_activity`, or equivalent output is attached.
- **Whether the issue is customer-specific or universal.** Both windows are low-volume (4–14 requests in 5 min); we cannot tell if one account's data volume drives the worst cases.
- **Whether the degradation is ongoing or was a transient reindex artefact.** The "after" window is a single five-minute slice.
- **The exact traffic differential.** The reporter describes them as "the same five-minute window," but the actual request counts differ (10 vs 14 statement-line calls), and no request-arrival log is provided.
- **The mechanism of thread-pool starvation.** It is almost certainly a consequence of the long queries, but the logs do not show thread-pool configuration or whether a different sizing in 4.7.0 contributed.
- **Whether any other service or database object was affected.** Only the statements-api pod logs are attached.
