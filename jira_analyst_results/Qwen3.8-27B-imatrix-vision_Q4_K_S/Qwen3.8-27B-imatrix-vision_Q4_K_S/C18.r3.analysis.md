## Group 1: 401 responses cascading into unhandled TypeErrors

| Issue | Property read | Events | Users | Route |
|-------|-------------|--------|-------|-------|
| BANKUI-3C8 | (root 401, handled) | 5,140 | 44 | `/api/settlements/Run/GetAllRunBookingsForCustomerOrder` |
| BANKUI-4A1 | `.sort` | 312 | 41 | `/settlements/run/8214` |
| BANKUI-4A2 | `.rows` | 289 | 39 | `/payments/batch/actions/allocation-reports` |
| BANKUI-4A9 | `.returnProperties` | 104 | 33 | `…/allocation-entry` |
| BANKUI-4B3 | `.length` | 97 | 31 | `/payments/batch/actions` |

**Shared cause (inference, based on breadcrumb evidence):** All four TypeError issues have breadcrumb summaries showing 401 responses from their respective API endpoints immediately before the crash. The app receives an error response instead of the expected data object, then calls `.sort()`, `.rows`, `.returnProperties`, or `.length` on `undefined`. The 401 is the trigger; the missing null/undefined guard is the defect.

Supporting evidence that they are one incident, not four:

- BANKUI-3C8, 4A1, and 4A2 all have `firstSeen` within one second of each other (02:14:08–09 on 09-05).
- The user populations overlap heavily (31–44 users per issue).
- BANKUI-4A1's breadcrumb explicitly notes "22 XHR breadcrumbs returning 401 in the 40 seconds before the error," indicating the session had already expired and the user kept interacting without a redirect.
- BANKUI-3C8 is `handled: true` (logged via `console.error`); the four TypeErrors are `handled: false` and crash through `auto.function.angular.error_handler`.

**Why first:** 44 distinct users are hitting 401s; the majority of those are then hitting an unhandled crash that breaks the UI. It spans at least three routes in the payments/settlements area. The total event volume is high, but more importantly the *user* count is the broadest among the actionable items (tied with the chunk error). The fix is twofold and the ticket should clarify which part is in scope for the sprint:

1. **Understand the 401 trigger.** Is it session timeout, a token-refresh race, or a server-side auth regression introduced in 4.6.0 or 4.7.0? The JSON does not say. Priya or the backend team need to pull auth-service logs for the 09-05 02:14 window.
2. **Guard the client code.** Wherever the app passes an `HttpErrorResponse` into a template or model without checking, add a guard or intercept the 401 and redirect to login before the component renders. This prevents the crash regardless of the auth root cause.

## Group 2: Stale-bundle ChunkLoadError after 4.7.0 deploy

| Issue | Events | Users | First seen |
|-------|--------|-------|------------|
| BANKUI-5D6 | 63 | 58 | 2026-09-10 21:11:36 UTC |

**Cause (inference, based on timing and breadcrumb):** 4.7.0 was deployed at 21:05:00 UTC. The first error appears six minutes later. The breadcrumb says "a navigation immediately before; the requested bundle returns 404." This is the classic pattern where a user's browser cached the old `index.html`, which references chunk `6728.b4f17ce620a8d539.js`; the new deploy removed or renamed that file, so the fetch 404s.

**Why second:** 58 distinct users is the widest user reach of any issue in the list. The event count (63) is low because most users hit it once and reload (getting the new index.html). The fix is operational rather than a code change:

- Verify `index.html` is served with `Cache-Control: no-cache` (or a very short TTL) so browsers revalidate after a deploy.
- Add a retry or full-reload handler for `ChunkLoadError` in the Angular `ErrorHandler` so a stale user is redirected to the new entry point instead of seeing a white screen.
- Confirm with the infra/CDN team whether old chunk files are purged on deploy (the 404 confirms they are, which is what makes this painful).

## Gaps and risks

- **Source maps are not uploaded** (confirmed by Ravi's comment and the JSON notes). Every `lastFrame` is a minified symbol (`ie.project`, `q.render`, `L.buildAction`, `N.setRows`, `a.loadChunk`). Fixing the 401 cascade requires reading the actual code paths, and that will be slower or impossible without de-minification. Lifting source maps off the backlog is a prerequisite for efficient work on Slot 1.
- **Root cause of the 401s is unknown.** The JSON tells us *what* 401s are returned and *where* the app crashes, but not *why* the session is invalid. Is it a token-expiry policy change, a server-side auth regression, a clock-skew issue, or a specific user-group problem? This needs backend/auth-team input before the sprint starts.
- **No fix-version or sprint is set** on BANK-498 itself, and no acceptance criteria are written. The ticket is an analysis request, not a dev task, so that is expected, but the two resulting dev tasks should carry their own ACs.
- **4.7.0 deploy scope is not in the export.** We cannot confirm whether the 4.7.0 release changed auth logic, chunk-splitting config, or cache headers. If the deploy team can confirm what changed, it would narrow the chunk-error and 401 investigations.
- **User counts cannot be summed across issues** (the JSON notes this explicitly), so the "total users affected" for Group 1 is at most 44 (the max in the group), not 5942.
