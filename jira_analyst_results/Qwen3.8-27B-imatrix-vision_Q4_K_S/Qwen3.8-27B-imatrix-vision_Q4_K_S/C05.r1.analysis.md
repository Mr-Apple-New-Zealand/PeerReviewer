## Verdict

**BANK-425 is a duplicate of BANK-440.** MOB-88 and BANK-419 are not.

---

## Why BANK-425 is a duplicate of BANK-440

| | BANK-440 | BANK-425 |
|---|---|---|
| Symptom | Balance on web dashboard stays stale after a transfer | Balance on web home screen stays stale after moving money |
| Platform / version | Web, 3.1.4 | Web, 3.1.4 |
| API state | Correct (GET /api/user/balance returns new value) | Not stated, but consistent |
| Recovery | Only after logout / login | Refresh does not help (consistent with a client-side cache that survives a reload) |

Both describe the same user-visible failure on the same platform and version. BANK-425 adds the confirmed root cause (Hana Sato's comment): the `BalanceCache` in local storage is never invalidated after a transfer. BANK-440 reaches the same conclusion implicitly—logout clears local storage, a page refresh does not.

**Inference (basis: identical symptom, platform, version, and a root cause that explains both reports):** These are the same defect reported independently by two users nine days apart.

---

## Why MOB-88 is **not** a duplicate

- **Different platform:** iOS / Android push notification vs. web dashboard.
- **Different root cause:** The notification service subscribes to `TransferRequested` (fired before the debit) instead of `TransferCompleted`. There is no client-side caching involved.
- **Different component & version:** Mobile App / Notifications, mobile 5.4.0 vs. Web, 3.1.4.
- **Different symptom:** A wrong dollar amount in a one-shot notification vs. a persistently stale UI value.

These will need separate fixes in separate codebases.

---

## Why BANK-419 is **not** a duplicate

BANK-419 is the **originating task** that introduced the 15-minute local-storage cache in 3.1.4. It is a Task (not a Bug), already **Done**, and its purpose (reducing API load) was legitimate. It is the *cause* of BANK-440/BANK-425, not a duplicate of them.
