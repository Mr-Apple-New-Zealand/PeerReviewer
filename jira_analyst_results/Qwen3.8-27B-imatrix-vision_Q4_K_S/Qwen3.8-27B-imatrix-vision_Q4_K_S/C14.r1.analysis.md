# Triage of payments-api-prod.log (OPS-92)

## 1. What is actually broken

### Critical – 403 Forbidden from masterfile-api (causes the user-reported failure)

Four distinct failures in the 48-hour window all share the same root cause: payments-api calls masterfile-api over Dapr and receives **HTTP 403 (Forbidden)**.

| Time (no date) | Command | Dapr target | RuleSet / Branch |
|---|---|---|---|
| 19:13:31 | `AddPaymentRoutingRuleSecondaryCommand` | `branchlocation/get?ID=71&includeDetails=False` | 41001 / branch 71 |
| 19:09:00 | `AddPaymentRoutingRuleSecondaryCommand` | `branchlocation/get?ID=71&includeDetails=False` | 41002 / branch 71 |
| 04:01:20 | `BulkUpdateSecondaryBranchesCommand` | `branchlocation/GetAll` | 41002, 41005–41013 |
| 19:09:10 | `BulkUpdateSecondaryBranchesCommand` | `branchlocation/GetAll` | (same set, trimmed) |

The stack trace shows the exception propagates as:

```
Dapr.Client.InvocationException
 └─ HttpRequestException: 403 (Forbidden)
     at MasterfileServiceClient.cs:64 / :121
```

This is the exact mechanism behind the user complaint: the handler calls masterfile-api to validate the branch, the call is rejected, the transaction rolls back, and the UI receives a generic failure with no error code. **This is not a database problem.** It is a service-to-service authorisation failure.

Likely causes (inference, not confirmed by this log):
- Expired or missing Dapr service-account / JWT between payments-api and masterfile-api
- An RBAC or authz policy change on the masterfile-api side
- A Dapr sidecar configuration drift on either pod

**Ownership:** Platform team (Dapr / service-mesh auth) in coordination with the masterfile-api team. Priya's framing of "us or the database team" misses the actual boundary – the database is not involved in these failures.

### Medium – SQL conversion error 245 on SearchPaymentRoutingRuleQuery

Five occurrences (03:37:32, 03:38:24, 03:38:50, 03:40:12, 20:26:31):

```
Conversion failed when converting the ****** value '******' to data type ******.
Error Number: 245, State: 1, Class: 16
at SearchPaymentRoutingRuleQueryHandler.cs:59
```

The offending values are **masked** in the log (asterisks), so the actual bad data or parameter cannot be identified from this file. This hits the *search* path for routing rules, not the save path, so it is a separate bug from the 403 issue. It will cause intermittent search failures for users browsing routing rules.

**Ownership:** Payments team – needs to reproduce the query and inspect the actual data or parameter that triggers the cast failure.

### Medium – Execution timeout on GetMonitorJobsQuery

Between 22:26:37 and 22:29:08, **seven** consecutive `GetMonitorJobsQuery` calls time out (Error Number −2, Class 11). The same query then succeeds at 22:36:47 in 279 ms.

This is in the PendingPayments area, not routing rules, so it does not explain the user-reported save failures. The burst-then-recover pattern (inference) suggests transient lock contention or a one-off slow query holding a lock, rather than a structural problem.

**Ownership:** Database team to confirm whether there was a lock or maintenance window; Payments team to check whether the query needs an index or timeout tuning.

### Low – Validation failure on UpdatePaymentRoutingRuleCommand

Two occurrences (22:35:24, 22:35:32) for RuleSetId 41003:

```
ApplicationValidationException: Application validation errors have occured.
```

The request body shows `BranchId: null, BranchRowId: null`. The error message gives no detail on *which* validation rule fired. This may be a legitimate user input error, but the uninformative message means support cannot help the user without code inspection.

**Ownership:** Payments team – add specific validation error messages.

## 3. What the log does NOT let us determine

- **Exact dates.** The log timestamps are time-of-day only (no date). With a 48-hour window and a container restart, it is impossible to assign a calendar date to each line or to tell how recent the 403 errors are.
- **Which users hit the 403.** The command payload contains RuleSetId and BranchID but no user identity (unlike the ReversalItemsCommand entries which carry a `UserCode`). The two users who reported the issue cannot be matched to specific log lines.
- **Whether the 403 is new or chronic.** Without a date, we cannot tell if masterfile-api started rejecting requests hours ago or has been doing so for days.
- **The actual values in the conversion error 245.** They are masked with `******`.
- **Which validation rule failed** on the UpdatePaymentRoutingRuleCommand.
- **The state of masterfile-api itself.** We only have payments-api logs; we do not know whether masterfile-api is healthy, whether it logged the rejected requests, or whether a policy change was deployed.
- **Whether the 403 affects all masterfile-api endpoints** or only `branchlocation/get` and `branchlocation/GetAll`. Other masterfile calls (if any exist in the 48 h window) are not visible in this log.
- **The root cause of the GetMonitorJobs timeouts.** No SQL Server-side log is provided.
- **Affects / fix versions, sprint, or component-level scope** are all blank on the ticket, so we cannot confirm whether a recent release or config change is implicated.

## 4. Risks and gaps in the ticket itself

- **No assignee.** The ticket is High priority, Open, and unassigned. Nobody is driving the triage.
- **Priya's framing is off.** Her comment asks whether it is "us or the database team." The dominant error (403 from masterfile-api) is a **Platform / service-auth** issue, not a database issue. The SQL conversion error is a Payments-team data issue. These are two separate problems that need two different owners.
- **Multiple distinct defects in one ticket.** The 403, the conversion error, the timeout burst, and the vague validation message are unrelated. If left in one ticket, the 403 will get buried under the others.
- **No reproduction steps, no user IDs, no error codes** were captured from the two users. The log is the only evidence.
- **Log completeness.** Support trimmed repeated stack traces (noted in the header). If the trimming removed the *first* occurrence of an error type that is different from the repeated ones, it would be lost. The header says "after the first occurrence … replaced with [stack trace trimmed – identical to first]," which implies the first is kept, but this should be verified.
- **Connection string in the log** is a credential-leak risk now that the file is in Jira.
