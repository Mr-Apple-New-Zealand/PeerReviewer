# BANK-495 Analysis

## 1. Summary

The batch actions screen crashes with `TypeError: Cannot read properties of undefined (reading 'sort')` when a user who has left the tab idle for an extended period (~4 hours in this event) interacts with the page again. All subsequent API calls return **401 Unauthorized** with empty response bodies, and the application code attempts to call `.sort()` (and, in sibling errors, `.rows`, `.returnProperties`, `.length`) on data that never arrived because the requests failed. The unhandled Angular error then blanks the screen.

## 2. What actually happened in the user's session (breadcrumb reconstruction)

The breadcrumbs span roughly **4 hours and 17 minutes** (timestamps 1789182659 → 1789197830).

**Phase 1 – Normal work (~0 min to ~2.5 min into the captured window)**
- User is on `bank-uat.example.com/payments/batch/actions`, working on settlement run 8214 (the `transaction`/`culprit`).
- Multiple `SettlementAllocation/Query`, `GetAllocationLineMarketPlanDetail`, and `InvokeAction` calls all return **200**.
- UI interactions: typing into AG Grid number inputs (`ag-355059-input`, `ag-358001-input`, `ag-358159-input`, `ag-358161-input`), clicking secondary and primary buttons.
- A **token refresh** succeeds at timestamp 1789182766.696: `POST /api/security/token/refresh` → 200, 1 238 bytes.
- A large `InvokeAction` response (~780 KB) at 1789182798.375.
- All working normally.

**Phase 2 – Idle gap (~4 h 15 min)**
- No breadcrumbs between 1789182813 and 1789197792. The tab was open but unused.

**Phase 3 – 401 cascade and crash (immediately after the user interacts again)**
- User clicks a dropdown (`button.btn.btn-sm.btn-secondary.dropdown-toggle`), then selects an item (`a.dropdown-item.cursor-pointer`).
- A burst of **8+ API calls** fires nearly simultaneously. **Every one returns 401** with `response_body_size: 0`:
  - `GET /api/settlements/Run/GetAllRunBookingsForCustomerOrder` (×4)
  - `POST /api/masterfile/Branch/Query`
  - `GET /api/masterfile/ClearanceType/GetAll`
  - `GET /api/hq/SettlementBatch/GetAllDistinctCustomerGroup`
  - `POST /api/masterfile/Period/Query`
  - `POST /api/settlements/CustomerOrder/Search` (×2)
- Angular's `HttpErrorResponse` objects are logged to the console, each with `status: 401`, `statusText: "OK"`, `response_body_size: 0`.
- **Three additional Sentry events fire within ~200 ms**, all the same class of bug on different properties:
  - `TypeError: Cannot read properties of undefined (reading 'rows')` (×2)
  - `TypeError: Cannot read properties of undefined (reading 'returnProperties')`
- User clicks the modal close button (`button.btn-close`), navigates through `allocation-reports/allocation-entry` → `allocation-reports` → back to `batch/actions`.
- More 401s on `InvokeAction`, `PaymentBatch/Get?pageNo=1&pageSize=10000&selectedFlag=true`, `PaymentBatch/Actions`.
- **A fourth Sentry event fires:** `TypeError: Cannot read properties of undefined (reading 'length')`.
- The **main event for this ticket** – `Cannot read properties of undefined (reading 'sort')` – fires in the same window.

**Inference (labelled):** The pattern strongly indicates the user's auth token expired during the ~4-hour idle period. When the user's next interaction triggered API calls, the stale token produced 401s across the board. The application's RxJS error-handling pipeline does not guard against the error path: it assumes the HTTP response contains a data object (with `.rows`, `.length`, `.sort`, etc.) and crashes when the 401 response body is empty/undefined.

## 3. The underlying defect

There are **two distinct problems** visible in this event:

### 3a. Missing error-path guard on HTTP responses (the crash)
The code in lazy chunk **6728** (function `ie.project`, an RxJS `map`/`switchMap` projection) calls `.sort()` on a value that is `undefined` when the HTTP call fails. The same unguarded pattern produces the `rows`, `returnProperties`, and `length` variants. Inference: the service or component does something like:

```
http.get(url).pipe(
  map(res => res.rows.sort(...))   // res is undefined on 401
)
```

…without an `catchError` or a null-check before accessing the payload. Because the error is **unhandled** (`mechanism.handled: false`) and goes through Angular's `ErrorHandler`, the component tree tears down and the screen goes blank.

### 3b. No effective token-recovery on 401 (the root trigger)
A token refresh succeeded ~4 hours earlier. After the idle gap, **no refresh is attempted** before the user's interaction; the first batch of requests goes out with an expired token, all 401, and the app does not transparently re-authenticate and retry. Either the refresh interceptor is missing, the refresh token has also expired, or the 401 is not being intercepted to trigger a re-login.

### 3c. Minified, unsymbolicated stack trace
All three bundles (`6728.b4f17ce620a8d539.js`, `main.7a2d95ef0c418bb3.js`, `polyfills.3e8c04b7a91d6f22.js`) report `js_no_source` / `missing_source`. The `scraping_attempts` show DNS failures resolving `bank-uat.example.com.google.internal` (A record not found), so Sentry could not download the bundles to attach source maps. `release` and `dist` are both **null**. The stack trace is therefore stuck at minified function names (`ie.project`, `XMLHttpRequest.Y`, `ie.error`, etc.) and the exact source line is **not recoverable from this event**.

## 5. Risks, gaps, and conflicts

- **Environment conflict.** The Sentry event tag says `environment: Production`, but every URL in the event is `https://bank-uat.example.com/…`. Tom Becker's comment explicitly flags this: *"worth someone confirming which environment this is actually coming from before we treat it as a production incident."* Until someone resolves whether the Sentry project is misconfigured (UAT traffic tagged as Production) or the UAT URL is actually serving production, the severity and blast radius are uncertain.

- **No source maps / no release tag.** Without source maps or a release identifier, the exact file and line calling `.sort()` cannot be identified from this event. The DNS failure in `scraping_attempts` (querying `bank-uat.example.com.google.internal`) suggests the Sentry server's network path to the UAT asset host is broken, which may be a recurring ingestion problem.

- **One event, one user, one browser.** This is a single Sentry event from one Edge user in NZ. It is not established that all "Cannot read properties of undefined" events on this screen share the 401-after-idle trigger. The `fingerprint` is `{{ default }}`, so the `rows`, `length`, `returnProperties`, and `sort` variants are **separate Sentry groups**; the full frequency and correlation are unknown.

- **Trimmed stack trace.** Support removed the raw stack trace and trimmed 28 frames described as "the same rxjs error-propagation chain." Inference: those frames are almost certainly rxjs internal `Subscriber` / `Operator` plumbing, but this is an assumption – the original frames are no longer available.

- **`statusText: "OK"` on 401 responses.** Every `HttpErrorResponse` in the console breadcrumbs shows `status: 401` but `statusText: "OK"`. This is unusual (expected: `"Unauthorized"`) and could indicate a reverse-proxy or gateway that overrides the reason phrase. It does not change the 401 semantics, but it is a data point for the backend team.

- **`allocationLineId=null` in URLs.** Several `GetAllocationLineMarketPlanDetail` calls have the literal string `null` in the query parameter (`allocationLineId=null`), while one has `allocationLineId=0`. This is a minor data-quality issue in the URL builder and is unlikely to be the crash cause, but it is worth a side note.

- **No linked tickets, no sprint, no fix version.** The ticket is unassigned with no planned delivery. The `sentry` label is the only tag.

## 6. What this event does **not** let you determine

1. **The exact source line or component** responsible for the `.sort()` call. Minified stack + missing source maps + null release = not recoverable from this event alone.
2. **Whether the 401 is a client-side or server-side token problem.** All we see is that the server returned 401. We cannot tell whether the `Authorization` header was absent, contained an expired access token, or contained an expired refresh token that the client failed to use.
3. **The token TTL and refresh strategy.** The successful refresh was ~4 h before the failure; we don't know the configured access-token lifetime, whether a silent-refresh interval exists, or whether the refresh token itself had a shorter expiry.
4. **Whether this is the only trigger for the blank screen.** This event correlates the crash with 401s after idle, but without a reproduction or additional events it is an inference, not a confirmed universal cause.
5. **Whether the UAT environment is a test deployment or a production-facing one.** The URL says "uat" but the Sentry tag says "Production." This is unresolved.
6. **The full untrimmed stack trace.** 28 frames were removed. While they are described as rxjs internals, the original data is gone.
7. **Impact scope.** Single event, single user, single browser. No other events are included. We cannot say how many users are affected, how often, or on which screens beyond the batch actions page.
