# Triage: OPS-92 Payments API Log

## Summary

The reported "save secondary branch spins then fails" is caused by a **403 Forbidden** returned by `masterfile-api` when `payments-api` calls it via Dapr to look up branch locations. Two commands that save secondary branches (`AddPaymentRoutingRuleSecondaryCommand`, `BulkUpdateSecondaryBranchesCommand`) both hit this 403 and abort. This is a service-to-service authorisation failure, not a database problem. A second, independent issue (SQL type-conversion error) breaks the *search* of routing rules but does not affect saving.

---

## 1. What is actually broken

### A. Dapr 403 from masterfile-api (the reported user issue) — **CRITICAL for the affected users**

| Time (container) | Command | Dapr call | Result |
|---|---|---|---|
| 19:13:31 | `AddPaymentRoutingRuleSecondaryCommand` (RuleSetId 41001, BranchID 71) | `GET branchlocation/get?ID=71&includeDetails=False` on `masterfile-api` | **403 Forbidden** |
| 04:01:20 | `BulkUpdateSecondaryBranchesCommand` (10 rule sets, BranchID 72) | `GET branchlocation/GetAll` on `masterfile-api` | **403 Forbidden** |
| 19:09:00 | `AddPaymentRoutingRuleSecondaryCommand` (RuleSetId 41002, BranchID 71) | same as first | 403 (trimmed) |
| 19:09:10 | `BulkUpdateSecondaryBranchesCommand` | same as second | 403 (trimmed) |

- The handler (`AddPaymentRoutingRuleSecondaryCommandHandler.cs:line 43`, `BulkUpdateSecondaryBranchesCommandHandler.cs:line 50`) calls `MasterfileServiceClient.InvokeServiceGetAsync` / `InvokeServiceGetAllAsync`, which wraps `DaprClient.InvokeMethodAsync`. The Dapr sidecar is returning HTTP 403.
- This means the payments-api Dapr identity (or the token it presents) is **not authorised** by masterfile-api's auth layer. It is not a network reachability problem (a connection error would look different); the request reaches masterfile-api and is explicitly rejected.
- **Impact:** Any user attempting to add or bulk-update a secondary branch on a routing rule will see the spin-then-fail behaviour. There is no error code surfaced to the user (per the ticket description), consistent with the 403 being swallowed into a generic failure response by the controller.
- **How bad:** Complete functional blockage of secondary-branch saves in production. Affects at least the two reporting users; potentially all users who touch this feature since the auth change (see gaps below).

### B. SQL Error 245 – conversion failure in `SearchPaymentRoutingRuleQuery` — **MEDIUM**

- First seen 03:37:32, repeated at 03:38:24, 03:38:50, 03:40:12, 20:26:31 (5 occurrences in the 48 h window).
- Message: `Conversion failed when converting the ****** value '******' to data type ******.` (actual value, source column and target type are **redacted** in the log).
- Origin: `SearchPaymentRoutingRuleQueryHandler.cs:line 59` → `ToListAsync` via EF Core → SQL Server.
- **Impact:** The search/filter page for routing rules intermittently returns an error. Does **not** affect the save path.
- **How bad:** Degrades a read path; users can still navigate to a specific rule and save it. But the redaction means we cannot tell which column or value is offending.

### C. Execution timeout on `GetMonitorJobsQuery` — **LOW-MEDIUM (self-recovered)**

- 22:26:37 → 22:29:08: seven consecutive `Execution Timeout Expired` errors (SQL Error −2, Class 11).
- Origin: `GetMonitorJobsQueryHandler.cs:line 24` via Dapper.
- Recovered by 22:36:47 (subsequent calls complete in <3 s).
- **Impact:** The pending-payments monitor page was unresponsive for ~2.5 minutes. Unrelated to routing rules.

### D. `ApplicationValidationException` on `UpdatePaymentRoutingRuleCommand` — **LOW (likely by-design)**

- 22:35:24 (twice, 8 s apart), RuleSetId 41003, ProductCode 5500412.
- The payload has `BranchId: null, BranchRowId: null`. The validation layer rejects this before any DB write.
- This is a normal business-rule guard (a routing rule update without a branch is invalid). No data corruption. If it is not expected, the frontend may be sending an incomplete form.

## 3. What the log does NOT let you determine

- **Root cause of the 403.** The log shows the symptom (Dapr → masterfile-api returns 403) but not *why*. Is it a missing/rotated JWT, a Dapr mTLS certificate expiry, a changed authorization policy on masterfile-api, or a new Dapr version that altered how the caller identity is presented? The 48 h window and the fact that the log is from a single pod do not tell us when the break started or whether a deploy on either side triggered it.
- **Which user hit which error.** The 403 log lines do not carry a user identity (no `X-User` header, no auth token in the log). We cannot confirm the two reporting users are the ones who generated these specific 403s.
- **The actual values in the SQL conversion error.** Redacted as `******`. Without the column name and value, we cannot tell whether it is a single bad row, a bad default, or a schema-type mismatch after a migration.
- **Whether the 403 is intermittent or 100 % reproducible.** All four 403s are in the window, but we don't see successful calls to the same endpoints in the log, so we can't confirm it's a total outage of that path.
- **Database team involvement.** The conversion error (B) and the timeout (C) are database-side, but the 403 (A) is a service-mesh / authz issue. The log does not contain masterfile-api logs, so we cannot confirm masterfile-api is healthy and simply rejecting.
- **Sprint / version context.** No build tag, image digest, or release reference in the log beyond `App=1.0.0 Contracts=0.1.7`. We cannot tie this to a specific deploy.

If there is more than one thing to fix, **fix A first** because it is the one matching the user complaint and completely blocks the feature. B (conversion error) is second. C and D can wait.

## 6. Note on the log file itself

- The container logs **time-of-day only, no date** (stated in the export header). Timestamps wrap (e.g., 22:xx appears before 19:xx and after 01:xx), so the 48 h window is not strictly chronological in the file. This makes it harder to confirm the 403 onset time.
- Support trimmed repeated stack traces, which is fine for diagnosis but means we cannot count exact occurrences beyond the unique ones shown.
- The connection string (including password) is logged at DBG level: `Server=sql-prd.internal,1433;…;Password=Pr0d-Payments-2026!;…`. This is a **security hygiene issue** in its own right and should be flagged separately; the log should not be shared beyond the ticket in its current form.
