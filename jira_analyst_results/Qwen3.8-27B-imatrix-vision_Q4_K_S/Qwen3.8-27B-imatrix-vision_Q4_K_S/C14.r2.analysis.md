# Triage: payments-api-prod.log (OPS-92)

## 1. Summary

The user-reported failure—"saving a secondary branch on a payment routing rule just spins and then says it failed"—is caused by **payments-api receiving a 403 Forbidden from `masterfile-api`** every time it tries to look up a branch during `AddPaymentRoutingRuleSecondaryCommand` or `BulkUpdateSecondaryBranchesCommand`. The Dapr sidecar call to `masterfile-api` (`branchlocation/get?ID=71` or `branchlocation/GetAll`) is being rejected at the HTTP/auth layer, so the save never reaches the database. This is an **inter-service authorisation problem, not a database problem**.

The log also contains a second, independent defect (SQL Server error 245 in routing-rule search) and a third (a validation failure on a different rule set), but neither of those explains the user report.

---

## 2. What is actually broken (ranked by impact on the user report)

### P0 – 403 from masterfile-api on every secondary-branch save

| Time (no date) | Command | masterfile-api endpoint | Result |
|---|---|---|---|
| 19:09:00 | `AddPaymentRoutingRuleSecondaryCommand` (RuleSetId 41002, BranchID 71) | `branchlocation/get?ID=71&includeDetails=False` | **403** |
| 19:09:10 | `BulkUpdateSecondaryBranchesCommand` (10 rule sets, BranchID 72) | `branchlocation/GetAll` | **403** |
| 19:13:31 | `AddPaymentRoutingRuleSecondaryCommand` (RuleSetId 41001, BranchID 71) | `branchlocation/get?ID=71&includeDetails=False` | **403** |
| 04:01:20 | `BulkUpdateSecondaryBranchesCommand` (10 rule sets, BranchID 72) | `branchlocation/GetAll` | **403** |

All four go through `MasterfileServiceClient.cs` (lines 64 / 121) via the Dapr gRPC invoke path. The exception is:

> `Dapr.Client.InvocationException: An exception occurred while invoking method: 'branchlocation/get?ID=71&includeDetails=False' on app-id: 'masterfile-api'`
> `→ System.Net.Http.HttpRequestException: Response status code does not indicate success: 403 (Forbidden).`

**Why the user sees "it spins and then says it failed":** the Dapr call has to reach masterfile-api, hit the 403, and propagate back through the `TransactionBehaviour` (which has already opened a DB transaction) before the API returns an error to the UI. The UI likely shows a generic failure because no user-friendly error code is mapped for this exception type.

**Scope:** Both single-add and bulk-update paths are affected. Both `branchlocation/get` (by ID) and `branchlocation/GetAll` are rejected, so the 403 is not specific to one branch or one endpoint—it is an identity/permission problem on the calling side.

### P1 – SQL Server error 245 in `SearchPaymentRoutingRuleQuery`

Repeated at 03:37:32, 03:38:24, 03:38:50, 03:40:12, and 20:26:31:

> `Conversion failed when converting the ****** value '******' to data type ******.`
> `Microsoft.Data.SqlClient.SqlException (0x80131904)`
> `Error Number:245, State:1, Class:16`
> Raised in `SearchPaymentRoutingRuleQueryHandler.Handle`, line 59.

The actual offending column, value, and target type are **redacted** in the log (literal `******`). This breaks routing-rule *search/listing*, not saves. Between failures, the same query succeeds (e.g. 03:37:30 → 285 ms, 03:38:46 → 465 ms), which points to a **data-dependent** conversion error: certain rows contain a value that cannot be cast to the column's declared type.

### P2 – `ApplicationValidationException` on `UpdatePaymentRoutingRuleCommand` (RuleSetId 41003)

At 22:35:24 and again 22:35:32:

> `Application.BuildingBlocks.Exceptions.ApplicationValidationException: Application validation errors have occured.`
> Raised in `UpdatePaymentRoutingRuleCommandHandler.Handle`, line 40.

The request payload shows `"BranchId": null, "BranchRowId": null`. The log does **not** record which validation rule fired, so the exact cause cannot be confirmed from this log alone. It is a different command (Update, not Add-Secondary) and a different rule set, so it is unlikely to be the same user complaint, but it does represent a broken save path for at least one user.

### P3 – Execution Timeout on `GetMonitorJobsQuery` (transient)

Between 22:26:37 and 22:29:08, **eight** consecutive attempts timed out:

> `Execution Timeout Expired. The timeout period elapsed prior to completion of the operation or the server is not responding.`
> `Error Number:-2, State:0, Class:11`

By 22:36:47 the same query was completing in 279 ms. This was a **transient database-side stall**, not a code defect. It affects the "Monitor Jobs" screen only.

## 5. What the log does NOT let you determine

- **Why masterfile-api returns 403.** The log shows the caller (payments-api) side only. It does not show masterfile-api's own logs, the Dapr identity/token that was presented, or the auth policy (OAuth scope, RBAC role, service-mesh mTLS policy) that rejected it. You need masterfile-api logs from the same window and the Dapr/identity configuration to determine whether this is a token expiry, a missing role after a deploy, a sidecar identity mismatch, or a changed auth policy on the masterfile side.
- **When the 403 started.** Container logs have time-of-day only, no date. The 48-hour window contains two restarts, so timestamps before and after the 02:50 restart are from different container lifetimes but the same calendar day is ambiguous. You cannot correlate the 403 onset with a specific deploy without the date.
- **The exact column, value, and target type in the SQL conversion error (245).** All three are masked as `******`. You need to query the database directly or reproduce with full SQL logging to identify the offending data.
- **Which validation rule failed** for `UpdatePaymentRoutingRuleCommand` (RuleSetId 41003). The exception message is the generic "Application validation errors have occured" with no field-level detail.
- **Whether other pods exhibit the same 403.** This log is from one replica (`payments-api-7c4f9b6d58-k2xqp`). If the 403 is pod-identity-related, other pods may or may not be affected.
- **The user-facing error message / code.** The ticket says "no error code was given to them," but the API's error response shape for a `Dapr.Client.InvocationException` wrapping an `HttpRequestException(403)` is not visible in this log. You need the API's exception-to-HTTP-mapping or the browser network tab to confirm what the user actually saw.

## 6. Answering Priya's question: "Is it us or the database team?" and "Which to fix first?"

- **It is not the database team.** The 403 is an HTTP-level rejection from `masterfile-api`. No SQL error is involved in the failing save. The transaction never reaches `Commit`; it is aborted in the Dapr invoke before any write. **Ownership: Platform / the team that owns the payments-api ↔ masterfile-api auth path** (Dapr identity, service-to-service auth config, or whichever team manages the masterfile-api's access-control policy).

- **Fix order if more than one thing is wrong:**
  1. **403 from masterfile-api** (P0) – blocks the reported user action. Fix first.
  2. **SQL conversion error 245** (P1) – breaks routing-rule search intermittently. Second.
  3. **Validation failure on RuleSetId 41003** (P2) – one user, one rule set, needs the validation detail. Third.
  4. **Timeout on GetMonitorJobs** (P3) – self-recovered; monitor, do not actively fix unless it recurs.
  5. **Credentials in log** – rotate the DB password and fix the log level. Parallel work, do not block on the other fixes.
