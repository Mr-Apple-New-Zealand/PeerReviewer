# Analysis of BANK-495

## 1. Summary

The batch actions screen crashes and goes blank when a user's authentication token expires after a long idle period. When the user returns and triggers an action, a cascade of simultaneous API calls all return HTTP 401. The Angular components then attempt to read properties (`.sort`, `.rows`, `.length`, `.returnProperties`) on `undefined` response data, throwing unhandled `TypeError`s that destroy the component tree. The primary crash is `TypeError: Cannot read properties of undefined (reading 'sort')` in the `ie.project` function of chunk `6728.b4f17ce620a8d539.js`.

## 2. What Actually Happened in the User's Session

The breadcrumbs tell a clear chronological story in three phases:

**Phase 1 – Normal work (~07:24:19 – 07:26:53 UTC, ~135 s)**
The user is working the allocation entry flow on `/payments/batch/actions`. A series of `SettlementAllocation/Query`, `GetAllocationLineMarketPlanDetail`, and `InvokeAction` calls all return **200**. The user is typing into AG Grid number fields (`ag-355059`, `ag-358001`, `ag-358159`, `ag-358161`) and clicking buttons. One notable call returns a very large body (799,741 bytes) at `timestamp 1789182798.375`. At `timestamp 1789182766.696` a **`POST /api/security/token/refresh` returns 200**, confirming the app has a token-refresh mechanism that worked at that point.

**Phase 2 – Long idle (~4 hours 10 minutes)**
There is a gap of roughly **14,979 seconds** between the last normal API call (`timestamp 1789182813.637`) and the next user interaction (`timestamp 1789197792.375`). No breadcrumbs are recorded during this period. This matches the reporter's observation that it "seems to happen to people who have had the tab open a while."

**Phase 3 – Token expiry and cascade failure (~07:23:12 – 07:23:50 UTC, ~38 s)**
The user clicks a dropdown item. Almost immediately, a burst of API calls fires and **every single one returns 401 with `response_body_size: 0`**:

## 3. The Underlying Defect

**Primary defect: no auth-failure interception or graceful degradation on 401.**

The chain of failure is:

1. The access token (and presumably the refresh token) expires during the ~4-hour idle period. The earlier successful token refresh at `1789182766.696` does not extend indefinitely.
2. When the user acts again, the app fires a batch of concurrent API calls. None of them carry a valid token, and **no interceptor steps in to refresh the token and retry** — every call gets a raw 401.
3. The Angular components treat the 401 response as if it were a successful response with an empty or missing data body. The HTTP client resolves (or rejects in a way the component swallows) with `undefined` where a `{ rows: [...], returnProperties: [...] }` object is expected.
4. Component code then calls `.sort()` (the main crash), `.rows`, `.length`, and `.returnProperties` on that `undefined`, throwing `TypeError`.
5. The errors are **unhandled** (`"handled": "no"`, mechanism `auto.function.angular.error_handler`). Angular's error handler destroys the component tree, producing the blank screen.

**Secondary defect: multiple unguarded property accesses across at least three different components or data structures.** The four distinct property names (`sort`, `rows`, `length`, `returnProperties`) indicate the problem is not one isolated `.sort()` call but a systemic absence of null/undefined checks on API response data throughout the batch actions screen.

**Tom Becker's comment** correctly identifies the `.sort` hypothesis for the main crash but also correctly says he'd "rather understand why it's undefined before I paper over it." The Sentry data confirms the "why": it's a 401 auth cascade, not a data-logic bug in the sort itself.

## 6. Risks and Gaps

### Environment conflict (high)
The Sentry event tags **`environment: "Production"`** and **`_dsc.environment: "Production"`**, but the URL in every request and breadcrumb is **`https://bank-uat.example.com/…`** — a UAT domain. Tom Becker flags this: *"worth someone confirming which environment this is actually coming from before we treat it as a production incident."* This must be resolved before scoping the fix or escalating. Possibilities (inference): (a) the UAT environment is mislabelled as Production in the Sentry DSN config; (b) the UAT domain is actually serving production traffic; (c) the `environment` tag is set by a static config that was copy-pasted. None of these can be confirmed from the ticket data.

### Source maps missing (high)
All three JS bundles (`6728.…js`, `main.…js`, `polyfills.…js`) have `symbolicator_type: "missing_source"`. The `scraping_attempts` show DNS failures:
> `"proto error: no records found for Query { name: Name(\"bank-uat.example.com.google.internal.\"), query_type: A, query_class: IN }"`

This means Sentry could not download the bundles to symbolicate. The stack trace contains only minified names (`ie.project`, `ie.next`, `ie._next`, `XMLHttpRequest.An`, `XMLHttpRequest.Y`, etc.). **Without source maps, the exact source line and variable that is `undefined` cannot be identified.** The `symbolicated_in_app` field is `false`.

### Token expiry duration unknown (medium)
The observed idle window is ~4 h 10 min, but the actual token/refresh-token TTL is not stated anywhere in the ticket. The fix (or at least the reproduction) depends on knowing this. It is not in the ticket.

### 401 `statusText: "OK"` anomaly (medium)
Every `HttpErrorResponse` in the breadcrumbs shows `status: 401` but `statusText: "OK"`. This is not normal. It could indicate an API gateway or reverse proxy is rewriting the status text, or an Angular HTTP interceptor is mutating the response object. If a gateway is involved, the fix may need to span both the frontend and the gateway layer.

### Multiple error types, one ticket (low)
The breadcrumbs reveal at least **four different properties** being read from `undefined` (`rows`, `returnProperties`, `length`, `sort`), implicating at least three different components or data-fetching functions. The ticket title and description focus on the `.sort` crash. A single guard on the `.sort` call (as Tom suggests) would fix one symptom but leave the others.

### No linked issues (low)
No linked tickets, no duplicate check documented. If the 401 cascade or the missing auth-interceptor is a known systemic issue, it is not referenced here.

### Suspicious embedded instruction check
No embedded instructions found in the ticket text, comments, or attachment. The attachment note *"raw_stacktrace removed and the frame list trimmed by support before attaching"* and the frame `[28 further frames in the same rxjs error-propagation chain trimmed by support]` are editorial notes about data reduction, not instructions. Flagging them for transparency.

## 7. What This Event Does **Not** Let You Determine

- **Exact source code location of the `.sort` call.** The stack trace is fully minified and unsymbolicated. `ie.project` in chunk 6728 could be any mapped function. The 28 trimmed rxjs frames (removed by support) might have contained the originating service or component name.
- **Which specific API response triggered the main `.sort` crash.** The breadcrumbs show many 401s in rapid succession. The `.sort` TypeError at `1789197830.606` coincides with 401s on `PaymentBatch/Get` and `PaymentBatch/Actions`, but without source maps we cannot confirm which response's missing data fed into the `.sort` call.
- **Whether the token refresh mechanism is supposed to auto-retry on 401.** The one successful refresh at `1789182766.696` happened proactively (or on a timer). There is no evidence in the event of a refresh being attempted *in response to* the 401s — but the absence of evidence is not evidence of absence; the refresh attempt might not have been logged as a breadcrumb.
- **How widespread this is.** One Sentry event is attached. The ticket says "Sentry has been firing" this error, implying multiple events, but no count, rate, or dashboard link is provided. We cannot tell if this is one user or many, one session or dozens.
- **Whether the `release: null` / `dist: null` is a configuration gap or expected.** We cannot confirm the event maps to bank-ui 4.7.0 with certainty.
- **The root cause of the 401 `statusText: "OK"` anomaly.** No gateway, proxy, or API-gateway ticket is linked.
- **Whether the blank screen is recoverable** (e.g., does a browser reload restore the session, or does the user need to re-authenticate?). The ticket says "they have to reload" but doesn't specify if re-login is also needed.
