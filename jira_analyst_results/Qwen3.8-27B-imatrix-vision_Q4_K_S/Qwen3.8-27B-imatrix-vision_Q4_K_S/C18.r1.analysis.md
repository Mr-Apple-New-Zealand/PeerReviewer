## 3. What to work on first and why

**Sprint capacity is ~2 issues. Recommendation:**

### Priority 1 – Fix the 401 response-handling gap (Group A)

- **Why first:** One root-cause fix eliminates four separate Sentry issues (4A1, 4A2, 4A9, 4B3) and stops the 5 140-event 401 log flood (3C8). Combined event volume ≈ 6 000/week. Affects ~44 distinct users across the settlements and payments flows. It is the issue most likely to block a user mid-transaction (unhandled TypeError on `/settlements/run/8214` and `/payments/batch/actions/…`).
- **What to do (concrete):** In the Angular HTTP interceptor or the API service layer, check for non-2xx status before dereferencing the body. On 401, surface an auth-expired message or redirect to re-authenticate. Add a regression test per call-site.
- **Also investigate:** *Why* are 401s happening at this volume? The 401s started 2026-09-05 02:14 Z. No deploy or infra change is recorded in the ticket. Check token TTL, auth-service logs, and whether a specific user cohort is affected. (Information gap – see §5.)
- **Owner:** Priya Nair (assignee) to scope; frontend team to implement.

### Priority 2 – Add chunk-load resilience (BANKUI-5D6)

- **Why second:** Widest user reach of any single issue (58 users). It is a user-facing "white screen / broken page" on navigation. The fix is small and well-trodden: on `ChunkLoadError`, reload the page once (or refetch the chunk) before giving up.
- **What to do (concrete):** Wrap the dynamic-import path with a retry-once handler. Optionally coordinate with DevOps to keep old chunk files for a grace period (e.g. 24 h) after a deploy so in-flight tabs can still resolve them.
- **Owner:** Frontend team; DevOps for the CDN/retention question.

### Do NOT spend sprint capacity on

- **BANKUI-2F0 (chrome extension):** Mark as *ignored* in Sentry. Add a release rule to filter `chrome-extension://` culpts so it stops appearing in future exports. One-line fix, no code.
- **BANKUI-1A7 (resolved, still firing):** Quick check that the 12 users have refreshed. If they have and it persists, reopen with a new repro; otherwise close the Sentry issue.

## 4. Risks and gaps

- **Source maps are not uploaded** (confirmed in Ravi Kumar's comment and in the JSON notes). Every `lastFrame` is a minified identifier (`ie.project`, `q.render`, `L.buildAction`, `N.setRows`). Debugging and verifying the fix for Group A will be guesswork without readable stack traces. **This is the single biggest gap in the export.** Uploading source maps should be pulled into the sprint or the very next one; it will make every future triage cycle faster.
- **No "why" for the 401s.** The export tells us 401s are happening on five different endpoints starting 2026-09-05 02:14 Z, but there is no linked incident, deploy record, or auth-service ticket. The fix for Group A (handle 401 gracefully) is still correct, but if the 401s are caused by a misconfigured token rotation or an expired cert, the user-facing problem will persist even after the code fix.
- **No steps-to-reproduce or acceptance criteria** on BANK-498 itself. The ticket asks "which two and why," which this analysis answers, but the resulting sprint tickets need concrete ACs.
- **User-count overlap is unknown.** The JSON notes warn that the same user appears in multiple issues, so the 44 users in Group A and the 58 in Group B may overlap. True blast radius could be lower than the sum.
- **BANKUI-1A7 status conflict.** Sentry says `resolved` / `resolvedInRelease: 4.6.0`, yet it fired 18 events as late as 2026-09-11. Either the resolution was premature or some users are on an old build. Needs a 10-minute check before the next triage.
