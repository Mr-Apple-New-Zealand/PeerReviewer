## 1. Summary

Customers stopped receiving payment-receipt (and other) emails at approximately 14:00 on 2026-09-15. The attached production log shows every email send failing with SMTP status 535 – the mail server is rejecting the service account's credentials because **basic authentication is disabled** on `smtp.example.com:587`. The outbox queue has been growing from 1,412 to 2,089 messages in the ~37 minutes of the log, with no dead-letter path and a stuck head-of-queue item.

The reporter's diagnosis (data-protection keys) does **not** match what the log shows.

## 3. What the log actually shows

**The real error (repeated dozens of times):**

> `System.Net.Mail.SmtpException: The SMTP server requires a secure connection or the client was not authenticated. The server response was: 5.7.139 Authentication unsuccessful, basic authentication is disabled.`
> SMTP status code: 535

This is an **SMTP-layer authentication failure**. The mail server at `smtp.example.com:587` is telling the client that basic auth is no longer accepted. The service is configured (per the 18:05:00 log line) with `user svc-notify@example.com` and `StartTls=True`, but the server-side policy has evidently changed.

**What the data-protection lines say (and do not say):**

- `WRN: Storing keys in a directory '/app/.aspnet/DataProtection-Keys' that may not be persisted outside of the container.`
- `WRN: No XML encryptor configured. Key {3c8e5a19-…} may be persisted to storage in unencrypted form.`

These are legitimate warnings about ASP.NET Core data-protection key persistence (relevant to cookie encryption, anti-forgery tokens, etc.). They do **not** cause SMTP 535 errors. The exception stack trace goes through `SmtpClient.SendMailCallback → SmtpTransport.EndGetConnection` – there is no data-protection code in the failure path. A pod restart would regenerate keys, yet the error persists identically, which further disproves the key-storage hypothesis.

**Other notable log details:**

- **Queue head blocking:** `Outbox item 991204 has reached 5 delivery attempts and stays at the head of the queue. Retry interval is fixed at 5s; there is no backoff and no dead-letter path.` The dispatcher cannot progress past this item.
- **Backlog growth:** 1,412 → 1,508 → 1,604 → 1,702 → 1,799 → 1,896 → 1,993 → 2,089 messages over 18:02–18:39 (~100 msg / 5 min).
- **Multiple notification types affected:** `payment-receipt` (customers 41082, 63340) and `statement-ready` (customer 55617) both fail. This is not isolated to payment receipts.
- **Health check blind spot:** `Health check /healthz: Healthy (db 8ms, nats 3ms, smtp skipped).` SMTP is explicitly excluded from the health probe, so no monitoring alert would fire.
- **NATS blip (minor):** Connection lost at 18:07:12, reconnected 1 s later. Unrelated to the email failure.
- **Previous container log lost:** The log header notes the prior container's log was not captured. We do not have the first-failure timestamp; the "14:00" figure comes from the contact centre, not the log.

## 4. Does the log support the reporter's explanation?

**No.** Marcus's comment states: *"The service is storing its data protection keys in a directory that is not persisted and there is no XML encryptor configured, so the keys are effectively junk. That is why the notifications are failing."*

The log does not support this. The failure is an SMTP 535 "basic authentication is disabled" error. Data-protection key issues would manifest as deserialisation/decryption exceptions in the ASP.NET pipeline, not as an SMTP transport-level auth rejection. The pod restart at 18:02 (which would generate fresh keys) produced the same error, contradicting the key-storage theory.

> **Inference (not stated in the ticket):** The most likely root cause is a server-side change on `smtp.example.com` – for example, an IT/Platform team disabled plain/basic auth in favour of OAuth2 or CRAM-MD5 – made around 14:00. The notifications service was not updated to match. This is an inference based on the specific server response text ("basic authentication is disabled"), the fact that the pod's own config still looks intact (user, host, StartTls all logged), and the fact that a client restart changed nothing.

## 5. Risks and gaps

- **Misdirected fix.** If Platform "fixes key storage" as Marcus requests, email will remain down. Time is being lost on the wrong component.
- **Growing backlog with no safety valve.** ~2,100 messages and climbing, no dead-letter queue, no backoff. If the SMTP issue persists for hours, the backlog could reach tens of thousands. The fixed 5 s retry on a head-of-queue item means the dispatcher is effectively stuck.
- **No alerting on email failure.** The health endpoint skips SMTP. The outage has been visible only via customer calls, not monitoring.
- **Missing information:**
  - No exact first-failure timestamp (prior container log lost).
  - No record of what changed on the SMTP server and when.
  - No linked ticket or change record for the mail server.
  - No acceptance criteria or target recovery time in the ticket.
- **Secondary (real but separate) issues in the log:**
  - Data-protection keys are not persisted and not encrypted. This is a latent reliability/security risk that should be tracked separately.
  - No retry backoff or dead-letter path in the outbox dispatcher.
  - Health check excludes SMTP.

## 6. Conflicts between comments

- Marcus attributes the fault to key storage and asks Platform to fix that; the log shows an SMTP auth rejection. These point to different teams and different fixes.
- Priya suggests restarting the pod again. The log already contains post-restart behaviour showing the same error; another restart will not help and will lose the current log as well.
- Marcus calls the diagnosis "fairly clear cut" and says he "would rather not spend more time on this," yet the diagnosis does not match the evidence.
