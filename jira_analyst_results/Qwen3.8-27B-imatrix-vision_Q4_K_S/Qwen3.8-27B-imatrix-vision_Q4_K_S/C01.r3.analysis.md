# Analysis: BANK-412

## 1. Summary

On mobile web (v3.1.4), a transfer that times out with `ERR_TXN_504` can be retried by the user, and the retry issues a fresh `POST /api/transaction/transfer` with no idempotency key, so the server creates a second transfer. Compounding this, the debit and credit are not wrapped in a single database transaction, so when the credit leg times out on the *first* attempt, the debit persists. The net result for the customer is two debits against the source account and one credit to the destination. Three customers have been affected (support calls 5, 6, and 8 September 2026).

## 3. Key details

**Root causes (identified by Priya, confirmed by Tom Becker in staging):**
- **No idempotency on retry.** The mobile-web Retry button re-issues the same `POST` with no deduplication key; the server treats it as a brand-new transfer (new `txn` id, e.g. 8841 → 8842 in the log).
- **Debit and credit are separate DB transactions.** When the credit leg hits the 30 s timeout, the debit from step 1 has already committed and is orphaned.

**Reproduction (staging, confirmed by both Priya and Tom Becker):**
1. Mobile web, transfer between own accounts.
2. Inject > 30 s latency API → DB (toxiproxy).
3. Wait for `ERR_TXN_504`, tap **Retry**.

**Affected surface:**
- **Mobile web only.** Tom Becker (10 Sep) confirmed it does **not** reproduce on desktop web, where the submit button is disabled and no Retry control exists after a timeout. The `mobile-web` label is consistent with this.
- Affects version **3.1.4**. No other versions are mentioned.

**Log excerpt (verbatim from the ticket):**
```
2026-09-08 09:41:02 INFO  TransactionService.Transfer: debit committed txn=8841 account=***1180 amount=250.00
2026-09-08 09:41:32 ERROR TransactionService.Transfer: credit failed txn=8841: timeout after 30000ms
2026-09-08 09:41:40 INFO  TransactionService.Transfer: debit committed txn=8842 account=***1180 amount=250.00
2026-09-08 09:41:41 INFO  TransactionService.Transfer: credit committed txn=8842 account=***2271 amount=250.00
```
This confirms: txn 8841 debits but never credits; txn 8842 (the retry) debits *and* credits. Account `***1180` is debited twice; `***2271` is credited once.

- **Scope of the idempotency fix.** The fix adds an `Idempotency-Key` header. (Inference) The ticket does not specify:
  - How long the idempotency key is cached on the server side.
  - What happens if the *first* request actually committed both legs but the client still received the 504 (i.e., the server succeeded, the network lost the response). The retry would then be rejected as a duplicate, which is correct — but this scenario should be covered in the PR's test cases.
  - Whether any other retry paths exist (e.g., the user closes the app and re-enters the transfer, or a mobile network drop triggers an OS-level retry). The fix as described covers the explicit Retry button only.
