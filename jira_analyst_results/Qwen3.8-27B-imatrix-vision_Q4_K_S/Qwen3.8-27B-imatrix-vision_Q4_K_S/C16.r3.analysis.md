# Log Comparison: BANK-482 (Statements page regression since 4.7.0)

## 1. The regression, quantified

| Metric | Before (4.6.3, 13 Sep 00:19–00:25) | After (4.7.0, 15 Sep 00:19–00:25) | Change |
|---|---|---|---|
| **GetStatementLineQuery** (10 samples) | 281–319 ms, avg **≈ 300 ms** | 33 757–72 974 ms, avg **≈ 51 760 ms** | **~170× slower** |
| **GetAccountSummaryQuery** (4 vs 4 samples) | 2 987–3 341 ms, avg ≈ 3 171 ms | 3 011–3 402 ms, avg ≈ 3 225 ms | Unchanged |
| **ExportStatementCommand** (1 each) | 1 840 ms | 1 902 ms | Unchanged |
| **Health-check DB latency** | 6 ms | 9 ms | Negligible |
| **Warnings / errors** | None | 14× `WRN Long-running request` + 1× `WRN ThreadPool starvation` | New |

The GetStatementLineQuery degradation is not flat. It **escalates within the window**:

- First call (00:20:43): 35 171 ms
- Mid-window (00:23:56): 36 545 ms
- Final cluster (00:24:21–00:24:34): 69 342 → 72 974 ms

The escalation coincides with the thread-pool event at 00:24:11:

> `ThreadPool starvation detected: 31 work items queued, 0 threads available for 4200ms.`

This suggests a feedback loop: slow queries occupy pool threads → new requests queue → queuing adds further latency → queries get even slower. The logs do not let us say which direction the causality starts.

## 2. What changed between the two runs

- **App version:** 4.6.3 → 4.7.0 (new pod `statements-api-7d4a2f9c61-xr6vh` vs `…6b9f4d7c85-w4lnp`).
- **A migration ran at pod start (21:05:36 UTC, 14 Sep):**
  > `Applied 1 pending migration: 20260914_2100_ReindexStatementLines.`
- **GetStatementLineQuery** went from sub-350 ms to 34–73 s, all above the 10 000 ms warning threshold.
- **ThreadPool starvation** appeared for the first time.

## 3. What did NOT change

- **GetAccountSummaryQuery** is essentially identical in both windows (~3 s, same variance). Ravi Kumar's comment ("It'll be the account summary query") is **contradicted by the data**; the regression is in a different query.
- **ExportStatementCommand** is unchanged (~1.9 s).
- **Database connectivity / health** is unchanged (db 6 ms → 9 ms).
- The five-minute clock window is matched, so time-of-day effects are controlled.

## 4. Conflict with Tom Becker's comment

Tom writes: *"Nothing in 4.7.0 touched statements."* The after-log shows the 4.7.0 pod applied the migration **`20260914_2100_ReindexStatementLines`** at startup. The migration name targets the same table that `GetStatementLineQuery` reads. This is a direct contradiction: the 4.7.0 release *did* include a statement-lines change, even if the application code in the statements module was untouched. (Inference: the migration was likely bundled into the 4.7.0 deploy as part of the notifications/admin release, which is why Tom may not have registered it as a "statements" change.)

## 5. What these logs **cannot** establish

| Gap | Why it matters |
|---|---|
| **Whether the reindex is the root cause** | The logs show the migration was *applied* and the regression appeared later, but they do not show what the migration did (dropped an index? created a new one? is it still running in the background? did it complete or fail?). |
| **Query execution plans / SQL** | No `EXPLAIN` output, no slow-query-log SQL, no index-scan vs seq-scan evidence. |
| **Database-side state** | Lock contention, table bloat, autovacuum activity, connection-pool exhaustion on the DB side—none of this is visible in application logs. |
| **Migration duration and completion** | The log says "Applied 1 pending migration" at 21:05:36 but does not show when it finished. If the reindex ran for hours, it could have degraded performance well before the 00:19 window. |
| **Thread-pool causality direction** | The starvation warning at 00:24:11 could be a *cause* (pool exhausted → queries wait) or an *effect* (slow queries exhaust the pool). The logs alone can't distinguish. |
| **Whether the regression was already in progress before 00:19** | The pod started at 21:05 UTC; the first sampled query is at 00:19. There is a ~3-hour gap with no log lines. The degradation may have been climbing since the reindex started. |
| **Customer-facing timeout threshold** | The ticket says requests "time out in the browser," but the logs show no HTTP 504/timeout entries, only `[WRN]` long-running markers. We don't know the browser/gateway timeout value. |
