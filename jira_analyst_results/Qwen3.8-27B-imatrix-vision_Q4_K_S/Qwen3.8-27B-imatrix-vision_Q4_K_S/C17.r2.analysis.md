# BANK-495 Analysis

## 1. What actually happened in the user's session

The Sentry breadcrumbs tell a clear two-act story:

**Act 1 – Normal operation (~4 hours).** The user was working on the allocation-reports sub-screen of the batch actions page. Over the span from breadcrumb timestamp 1789182659 to 1789182813, roughly 25 API calls to `SettlementAllocation/Query`, `GetAllocationLineMarketPlanDetail`, and `InvokeAction` all returned **200 OK**. At 1789182766 a call to `/api/security/token/refresh` also returned 200. The user was interacting with AG Grid number inputs and buttons. Everything was fine.

**Act 2 – The ~4-hour gap and the crash.** The next breadcrumb is at 1789197792, about **4 hours 17 minutes later** (Δ ≈ 14,979 s). This matches the reporter's observation that it "seems to happen to people who have had the tab open a while." The user clicked a dropdown-toggle, then selected a dropdown item. That single click triggered a burst of **simultaneous** API calls:

| Endpoint | Status |
|---|---|
| `GET /api/settlements/Run/GetAllRunBookingsForCustomerOrder` | **401** |
| `GET /api/settlements/Run/GetAllRunBookingsForCustomerOrder` (×3 more) | **401** |
| `POST /api/masterfile/Branch/Query` | **401** |
| `GET /api/masterfile/ClearanceType/GetAll` | **401** |
| `GET /api/hq/SettlementBatch/GetAllDistinctCustomerGroup` | **401** |
| `POST /api/masterfile/Period/Query` | **401** |
| `POST /api/settlements/CustomerOrder/Search` | **401** |
| `POST /api/hq/SettlementAllocation/InvokeAction` | **401** |
| `GET /api/hq/PaymentBatch/Get?pageNo=1&pageSize=10000&selectedFlag=true` | **401** |
| `GET /api/payments/PaymentBatch/Actions` | **401** |

Every response body was **0 bytes**. The token that was successfully refreshed ~4 hours earlier had expired, and the app did **not** intercept the 401s, refresh the token, and retry. Instead the HTTP error objects propagated into RxJS `map`/`project` operators where the code expected a successful response with a data payload.

**The crashes.** Four distinct `TypeError` events fired in rapid succession (all within ~28 seconds):

| Breadcrumb time (Δ from 401 burst) | Message | Sentry event id |
|---|---|---|
| 1789197802.243 | `Cannot read properties of undefined (reading 'rows')` | `b71c40d8…` |
| 1789197802.257 | `Cannot read properties of undefined (reading 'rows')` | `5a0e9fb3…` |
| 1789197826.144 | `Cannot read properties of undefined (reading 'returnProperties')` | `9d3a17e5…` |
| 1789197830.595 | `Cannot read properties of undefined (reading 'length')` | `c4820f6a…` |

The **reported exception** (the one the ticket is named after) is:

> `TypeError: Cannot read properties of undefined (reading 'sort')`
> in `ie.project`, file `/6728.b4f17ce620a8d539.js`, col 60295

The stack shows the error arriving through Angular's `ErrorHandler` → `notifyError` → an RxJS error-propagation chain (28 frames trimmed by support) → `ie.project` in the chunk-6728 bundle. The `mechanism` is `auto.function.angular.error_handler`, `handled: false`, meaning it crashed the Angular error boundary and blanked the screen.

After the crash the user navigated back and forth between `allocation-reports/allocation-entry` and `batch/actions`, each navigation re-firing the same 401s and generating further TypeErrors. The user then closed a modal and the session effectively ended.

## 2. The underlying defect (inference, based on the breadcrumb sequence)

The primary defect is **not** a missing array in some data model. It is a **missing or broken 401-interception / token-refresh-and-retry path** for the batch-actions screen:

1. The app has a token-refresh mechanism (proven by the successful `/api/security/token/refresh` call earlier in the session).
2. After the token expires, the next batch of API calls returns 401 with an empty body.
3. The 401 `HttpErrorResponse` objects are **not** intercepted at the HTTP-client level to trigger a refresh-and-retry. They instead flow into the RxJS streams as error emissions.
4. Downstream `map`/`project` operators in the component/service code assume the stream emitted a successful response with a data object. When the error (or a resolved-but-undefined payload) arrives, properties like `.rows`, `.length`, `.returnProperties`, and `.sort` are read on `undefined`.
5. Because the error is `handled: false`, Angular's error handler catches it and the screen goes blank.

This explains why **four different property names** crash: it isn't one missing array; it is every component on that screen that consumes a list-shaped API response, all hitting the same "response is undefined because the request 401'd" condition simultaneously.

Tom Becker's comment ("something is calling .sort on an array that isn't there") is directionally correct for the symptom but skips the root cause. A null-guard on the `.sort` call would suppress one of the four crash sites while leaving the other three, and would not fix the blank-screen behaviour or the underlying auth failure.

### Environment conflict

- The Sentry `environment` tag and `_dsc.environment` both say **"Production"**.
- The `url` tag and every breadcrumb URL is **`https://bank-uat.example.com/…`** – a UAT hostname.
- The `Referer` header is `https://ntp.msn.com/` (a default browser new-tab page), which is uninformative.
- Tom Becker's comment explicitly asks: *"worth someone confirming which environment this is actually coming from before we treat it as a production incident."*

This is either a Sentry project misconfiguration (UAT deployment tagged as Production) or the UAT URL is being served under a "Production" environment label. **This must be resolved before the ticket can be triaged with the correct severity.**

### Anomalous statusText

Every 401 console-error object in the breadcrumbs has `"statusText": "OK"` instead of `"Unauthorized"`. This is non-standard for a raw HTTP 401 and suggests either a reverse-proxy/gateway rewriting the response line, or a quirk in how the Angular `HttpErrorResponse` is constructed in this codebase. It is a secondary observation but worth noting for the auth team.

### Other observations from the event JSON

- `transaction` is `/settlements/run/8214`, and `culprit` is the same. The user was working within a specific settlement run.
- The SDK is `@sentry/angular` 10.49.0, Angular 19, browser Edge 153 on Windows, locale `en-NZ`, user geo: New Zealand.
- `sample_rand: 0.497`, `sample_rate: 1.0` – this event was not sampled out; it was captured at 100%.
- The `fingerprint` is `["{{ default }}"]`, so Sentry is grouping by default (likely by exception message + top frame). The four different property names (`sort`, `rows`, `length`, `returnProperties`) may end up in **four separate Sentry issues** rather than one, which could fragment the incident.
- The `_note` in the exception says: *"raw_stacktrace removed and the frame list trimmed by support before attaching; it duplicated stacktrace.frames."* The 28 rxjs frames in the middle of the stack were removed. This means the full call chain from the HTTP client to the specific component is not fully visible.

## 4. Risks and gaps

- **Cannot pinpoint the exact code location.** Without source maps, `ie.project` in chunk 6728 is all we have. Someone needs to either (a) restore source-map publishing for the UAT build and re-symbolicate, or (b) search the codebase for `.sort` calls in the batch-actions feature that operate on a list returned by one of the failing endpoints.
- **The 401-interception gap is likely app-wide, not screen-specific.** The failing endpoints span `settlements`, `masterfile`, `hq`, and `payments` services. If the token-refresh interceptor is missing or broken, any screen that makes API calls after token expiry will crash the same way. The ticket is scoped to the batch-actions screen, but the fix may need to be at the `HttpClient` interceptor level.
- **Environment ambiguity blocks correct triage.** If this is genuinely UAT, the operational impact is lower but the user experience bug is real. If the "Production" tag is correct and the UAT URL is a red herring (e.g., DNS aliasing), this is a production incident. Tom Becker's comment is correct to flag this before assigning severity.
- **No assignee, no sprint, no story points, no due date.** The ticket is High priority but unowned and unscoped.
- **The token-expiry window is uncharacterised.** The successful refresh was at ~4 h before the crash. Was the token's TTL 4 hours? Was there supposed to be a proactive refresh at, say, 80 % of TTL? The ticket does not say.
- **Potential duplicate / related tickets.** The four different TypeError messages (`rows`, `length`, `returnProperties`, `sort`) may each be separate Sentry issues. If so, this ticket (named after the `sort` one) may not be the canonical one to fix. The ticket should link or reference the other Sentry event ids.
