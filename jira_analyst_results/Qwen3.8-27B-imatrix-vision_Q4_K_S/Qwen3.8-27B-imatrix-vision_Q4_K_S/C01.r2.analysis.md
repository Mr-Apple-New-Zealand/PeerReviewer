## BANK-412 Analysis

### 1. Summary

On mobile web, a transfer that times out (ERR_TXN_504) can be retried by tapping a Retry button, which issues a brand-new POST to the transfer endpoint with no idempotency key. Because the debit and credit are not wrapped in a single database transaction, the first attempt's debit survives after the credit times out, and the retry creates a second debit. Net result: the source account is debited twice, the destination credited once. Three customers have been affected as of 8 September.

### 3. Key details

**Reproduction (staging, confirmed by Priya and Tom Becker):**
1. Mobile web; transfer between two own accounts.
2. Inject >30 s latency via toxiproxy between API and DB.
3. ERR_TXN_504 appears; tap Retry.

**Root causes identified (Priya, 2026-09-09):**
- **No idempotency key on the retry.** The Retry button fires `POST /api/transaction/transfer` with no key, so the server allocates a new transaction ID (log: `txn=8841` → `txn=8842`).
- **Debit and credit are separate DB transactions.** When the credit times out at 30 000 ms, the already-committed debit has no compensating rollback.

**Log evidence (2026-09-08, account ***1180 → ***2271, $250):**
- `09:41:02` debit committed `txn=8841`
- `09:41:32` credit failed `txn=8841`: timeout after 30000 ms
- `09:41:40` debit committed `txn=8842` (retry)
- `09:41:41` credit committed `txn=8842`

**Scope:**
- **Mobile web only.** Tom Becker (2026-09-10) confirmed it does **not** reproduce on desktop web: desktop disables the submit button and has no Retry button after a timeout.
- Affects version **3.1.4**.
- Three customer support calls: 5, 6, and 8 September.

### 4. Risks and gaps

- **In-flight exposure at deploy time.** Wrapping debit + credit in one transaction fixes *future* transfers, but does not address any transfer that is mid-flight (debit committed, credit pending) at the moment the 3.2.0 build is deployed. The three known cases need the manual reversal; there may be additional cases not yet reported.
- **Finance Ops action is unconfirmed.** Aroha asked Marcus to raise the reversal request, but the ticket shows no follow-up, no linked ticket, and no owner on that sub-task. If it is not done, the three customers remain in a wrong-balance state.
- **Idempotency-Key scope.** PR #218 adds the header to the *transfer* endpoint. It is unclear (and not stated in the ticket) whether other transfer-like endpoints (bulk transfer, standing-order execution, API retries from a load balancer) carry the same gap. **Inference:** if the debit/credit split is a pattern in `TransactionService`, other call sites may be equally exposed.
- **Timeline pressure.** Sprint 38 ends 2026-09-22; the 3.2.0 release is 2026-09-24. PR #218 is still in review as of 2026-09-12 (3 days before sprint end, 12 days before release). A review or test delay slips the fix out of 3.2.0.
- **No regression-test ticket or link.** The ticket does not reference an automated test (e.g., a toxiproxy-based integration test) that will guard against regression.
- **No linked issues at all.** The Finance Ops reversal, any desktop-web hardening, and any related design issue are not cross-referenced, making it harder to track completion.
