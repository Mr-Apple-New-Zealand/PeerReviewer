## Grouped issues and root-cause read

**Group 1 — 401-triggered crashes (likely one shared root cause): BANKUI-4A1, 4A2, 4A9, 4B3**
- All are `TypeError: Cannot read properties of undefined (...)` inside `auto.function.angular.error_handler`, all `handled: false`, and each has a breadcrumb note of a 401 response immediately before the crash (from `/api/settlements/CustomerOrder/Search`, `/api/hq/SettlementAllocation/InvokeAction`, `/api/payments/PaymentBatch/Actions`, and 22 XHR 401s in 40s for 4A1).
- 4A1 and 3C8 fire at the **same second** (`2026-09-05T02:14:08–09Z`), and 4A2 matches exactly too — inference: these started from a single triggering event around that timestamp, not from either listed frontend release (4.6.0 on 08-27, 4.7.0 on 09-10). That points to a backend/API-side change (e.g. auth/session behaviour) that isn't captured in this export.
- Combined this is the largest distinct-user impact (roughly 30–44 users each, can't be summed per the export's own note, but clearly overlapping and widespread) and the only true unhandled-crash cluster.
- Working hypothesis (inference): the UI doesn't handle 401/auth failures before trying to process the response body, so an expired/invalid session surfaces as a JS crash instead of a clean re-auth or error state.

**Group 1b — underlying 401 flood: BANKUI-3C8**
- `HttpErrorResponse 401`, `handled: true`, 5140 events / 44 users — this is the console-logged symptom of the same session/auth problem feeding Group 1. It's not itself a crash, but likely the actual thing to fix; fixing the cause here may resolve or shrink 4A1/4A2/4A9/4B3 as a side effect.

**Group 2 — deployment-related: BANKUI-5D6 (ChunkLoadError, chunk 6728)**
- First seen 2026-09-10T21:11:36Z, six minutes after the 4.7.0 deploy (21:05:00Z) — classic stale-asset pattern (client has an old app shell referencing a chunk hash removed by the new deploy).
- Users (58) exceed events (63) almost 1:1, meaning nearly every affected user hit it once — consistent with a cache/versioning issue rather than a code defect in a specific screen.
- Worth flagging: the failing chunk filename (`6728.b4f17ce620a8d539.js`) is the exact same file named as the crash location (`lastFrame`) in BANKUI-4A1 and 4A2. This may be coincidental (shared bundle used by both routes) or may indicate the chunk itself is implicated in both problems — **not confirmed**, and can't be confirmed without source maps.

**Not our defect: BANKUI-2F0**
- `SecurityError` culprit is `chrome-extension://.../inject.js`, 1 user only, all breadcrumbs from a single browser session with no app code involved. This is a third-party browser extension conflict, not an application bug. Despite having the second-highest event count (4812), it should not be triaged as a defect — recommend marking resolved/ignored in Sentry.

**Already resolved, low priority: BANKUI-1A7**
- `RangeError: Maximum call stack size exceeded`, marked resolved in 4.6.0, but `lastSeen` is 2026-09-11 — after that release. Low volume (18 events/12 users). Possibly stale clients on cached old bundles, or an incomplete fix. Not sprint-worthy at this volume, but worth a quick check rather than silent dismissal.

## Recommendation for the two sprint slots

1. **Investigate and fix the 401/session-handling root cause (3C8 + the 4A1/4A2/4A9/4B3 crash cluster as one piece of work).** This is the highest-value pick: it's the only unhandled-crash pattern, hits the most distinct users, started from a single identifiable event, and a single fix (proper handling of 401 responses before touching the payload, and/or fixing whatever is causing the 401s) plausibly resolves five Sentry issues at once rather than one.
2. **Fix the stale-chunk issue behind BANKUI-5D6.** It correlates tightly with the 4.7.0 deploy, affects a comparable number of distinct users to the crash cluster, and is typically a contained fix (cache-busting / reload-on-chunk-failure logic), making it a good second item within capacity.

Do **not** spend a slot on BANKUI-2F0 (not an app defect) or BANKUI-1A7 (already resolved, low volume) — this avoids repeating the earlier mistake of chasing raw event counts, since 2F0 and 3C8 have the two highest event totals but are respectively a non-issue and a symptom rather than the best standalone fix.
