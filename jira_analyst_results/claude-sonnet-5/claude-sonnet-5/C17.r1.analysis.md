# BANK-495 Analysis

## Summary
A batch actions screen (`/payments/batch/actions`) in bank-ui 4.7.0 throws an uncaught `TypeError: Cannot read properties of undefined (reading 'sort')` and the screen goes blank, requiring a reload. Support has attached one Sentry event as evidence; there is no confirmed reproduction, only a hunch that it correlates with long-idle tabs.

## Current state
- **Status:** Open, Unresolved, unassigned, High priority.
- **Blocking progress:** No one has been assigned, no root-cause investigation has started beyond Tom Becker's initial read of the stack trace, and the environment the event actually came from hasn't been confirmed (see below) — Tom explicitly asked for this before treating it as a production incident.

## What the Sentry event actually shows
Reconstructing the breadcrumb timeline:

1. **~07:10–07:13 UTC:** Normal session activity — the user queries settlement allocations, edits numeric grid cells, invokes actions. All XHRs return `200`. A token refresh (`/api/security/token/refresh`) succeeds at one point.
2. **Gap of ~4.16 hours** (timestamp jumps from `1789182813` to `1789197792`) with no breadcrumbs — consistent with the ticket's suspicion that this relates to tabs left open/idle for a while.
3. **On resuming interaction** (deselecting a filter value, opening a dropdown, clicking a menu item), essentially **every subsequent API call returns `401` with an empty body**: `GetAllRunBookingsForCustomerOrder`, `Branch/Query`, `ClearanceType/GetAll`, `GetAllDistinctCustomerGroup`, `Period/Query`, `CustomerOrder/Search`, and later `SettlementAllocation/InvokeAction`, `PaymentBatch/Get`, `PaymentBatch/Actions`.
4. **Correlated with these 401s**, four uncaught TypeErrors fire in quick succession:
   - `Cannot read properties of undefined (reading 'rows')` ×2
   - `Cannot read properties of undefined (reading 'returnProperties')`
   - `Cannot read properties of undefined (reading 'length')`
   - `Cannot read properties of undefined (reading 'sort')` — this is the one actually captured as the full event/title.
5. The final captured exception's mechanism is `auto.function.angular.error_handler`, `handled: false` — i.e. it escaped to Angular's global error handler, which is consistent with the screen going blank (the component tree is torn down).

## Underlying defect (inference)
- **Inference, based on the tight correlation between 401 responses and the TypeErrors:** the frontend code assumes API responses always succeed and immediately reads properties (`.rows`, `.returnProperties`, `.length`, `.sort`) off the response body without checking for an error/failure state. When the backend returns `401` with an empty body (likely because the auth/session token had expired during the long idle gap), the response data is `undefined`, and the unguarded property access throws.
- Tom Becker's comment ("something is calling `.sort` on an array that isn't there... I'd rather understand why it's undefined") aligns with this: the "why" is very likely the 401/empty-body pattern, not a data/timing race in normal operation.
- This does **not** appear to require the "batch actions" screen specifically — the same class of unguarded-response bug shows up on at least four different call sites (`rows`, `returnProperties`, `length`, `sort`) across allocation, run-bookings, and payment-batch endpoints, suggesting a systemic gap in error handling (e.g., a shared HTTP interceptor or service layer not distinguishing 401 from success) rather than one isolated bug.

## Key details present / missing
**Present:**
- One full Sentry event with breadcrumbs, tags, environment/browser/OS context, and a stack trace for the final `.sort` exception.
- Affected version (bank-ui 4.7.0), components (Web UI, Auth).

**Missing / not determinable from this event:**
- **Environment conflict:** the event's `environment` tag and `_dsc.environment` both say **"Production"**, but every URL in the event (page URL, all API calls) is `bank-uat.example.com` — a UAT host. This is a real conflict in the data, not just Tom's suspicion; it needs confirming before this is logged/escalated as a production incident.
- **No confirmed repro steps** — only a hypothesis ("tab open a while") with no controlled test.
- **Root cause of the 401s themselves is not shown.** The event doesn't reveal whether the token-refresh mechanism failed to fire after the idle period, whether the refresh token itself had expired, or whether the backend session was invalidated some other way. We only see one successful refresh *before* the gap, and no refresh attempt visible after it.
- **Stack trace is unsymbolicated** — function names are minified (`Y`, `V`, `H`, `ie.project`, etc.) and Sentry's own symbolication attempts failed (`scraping_attempts` show DNS resolution failures for `bank-uat.example.com...google.internal`, i.e. Sentry couldn't fetch source maps from this host). So the exact source line/component responsible cannot be identified from this event alone.
- **Support trimmed the stack trace** ("28 further frames in the same rxjs error-propagation chain trimmed... raw_stacktrace removed... duplicated stacktrace.frames"), so the full call chain between the RxJS error propagation and the actual `.sort()` call site is not visible in what's attached.
- The other three TypeErrors (`rows`, `returnProperties`, `length`) are only breadcrumb messages, not full events with stack traces — we can't confirm from this file whether they share the exact same code path as the `.sort` one, only that they're strongly correlated in time and both follow 401 responses.
- No volume/frequency data — only one event was pulled; how many users/sessions are affected is unknown from this ticket.

## Risks and gaps
- **Environment ambiguity risk:** if this is actually a UAT-only issue mislabeled as Production, prioritising it as a High/production incident could be premature — needs verification (per Tom Becker's comment) before further triage.
- **No owner assigned** despite High priority.
- **No linked tickets** — worth checking whether there's an existing auth/session-timeout ticket, since the likely defect (unhandled 401 crashing the UI) is an Auth-related issue as much as a Web UI one, matching the ticket's own component tags (Web UI, Auth).
- Fix suggested by Tom Becker (defensive guard on `.sort`) would only mask this one call site; if the root cause is systemic unguarded-response handling on 401, similar crashes will keep recurring at other call sites (as already seen with `rows`/`returnProperties`/`length` in the same session).

## Suggested next actions
1. **Confirm the true environment** the event came from (Production vs UAT) before treating this as a production incident — flagged by Tom Becker, still open.
2. **Investigate session/token expiry behaviour after long idle periods**: check why no token refresh is visible in the ~4-hour gap before the 401 cascade, and whether refresh silently failed or was never attempted.
3. **Fix the response-handling gap** at the HTTP client/interceptor or shared data-service level so that failed (401 or otherwise non-2xx) responses don't leave callers dereferencing `undefined` — rather than only guarding the single `.sort()` call, given at least three other call sites showed the same symptom in this one session.
4. **Get source maps resolvable for `bank-uat.example.com`** in Sentry (the scraping attempts failed due to DNS/internal-host issues) so future events symbolicate properly and pinpoint exact source locations.
5. **Assign an owner** given the High priority and try to build a deliberate repro (leave a tab open past token/session expiry, then interact) rather than relying on incidental Sentry captures.
