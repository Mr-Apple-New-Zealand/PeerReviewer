# BANK-482: Log Comparison Analysis

## 1. Summary
Statement retrieval (`GetStatementLineQuery`) has regressed from ~300ms to 30–73 seconds after the 4.7.0 release, making the Statements page unusable. The after-log shows a migration reindexing statement lines was applied just before the regression window, plus thread pool starvation — both of which directly contradict the two theories offered in comments.

## 2. Current state
- Status: Open, Unresolved, High priority, assigned to Tom Becker.
- Blocking progress: the two comments propose different (and, per the logs, unsupported) root causes rather than confirming one. No fix version or sprint set; no investigation of the migration has been logged yet.

## 3. Quantified regression
| Operation | Before (4.6.3) | After (4.7.0) | Change |
|---|---|---|---|
| GetStatementLineQuery | ~281–319ms (10 samples, tight range) | 33,757–72,974ms (14 samples) | ~100x–240x slower |
| GetAccountSummaryQuery | 2,987–3,341ms | 3,011–3,402ms | Unchanged |
| ExportStatementCommand | 1,840ms | 1,902ms | Unchanged |
| DB health check | 6ms | 9ms | Unchanged (DB reachable, fast) |

Additional detail: within the after-window itself, `GetStatementLineQuery` times escalate — from ~33–36s at 00:20–00:23 up to 67–73s by 00:24:21–00:24:34 — indicating the problem worsens over the course of the window, not a flat regression. A `ThreadPool starvation detected: 31 work items queued, 0 threads available for 4200ms` warning appears at 00:24:11, coinciding with the sharpest jump.

## 4. What changed vs. what did not
- **Changed**: `GetStatementLineQuery` latency (the core regression); a migration `20260914_2100_ReindexStatementLines` was applied at app startup (21:05:36) before the affected window; thread pool starvation appears only in the after-log.
- **Unchanged**: `GetAccountSummaryQuery` and `ExportStatementCommand` timings are essentially identical before and after; DB health check remains fast in both logs.

This directly contradicts both comments:
- Tom Becker (09:20) states "Nothing in 4.7.0 touched statements" — but the after-log shows the app itself started as `App=4.7.0` and applied a migration named `ReindexStatementLines`, which is squarely in the Statements component.
- Ravi Kumar (09:40) attributes the slowness to `GetAccountSummaryQuery` — but that query's timing is unchanged between the two logs, while `GetStatementLineQuery` is the one that regressed. The log evidence does not support this theory.

## 5. What these logs cannot establish
- **Causation**: The logs show a migration was applied and a regression followed, but do not show query plans, index usage, lock waits, or DB-side timing — so the link between the reindex migration and the slowdown is correlation only, not proven cause (label: inference).
- **Escalation mechanism**: Whether the worsening pattern (33s → 73s) is caused by thread pool starvation itself, by lock contention building up, or by some other cascading effect is not shown — only that starvation and worsening latency co-occur.
- **Scope**: Both logs are single 5-minute windows from single pods (different pod names/IDs each side), so we cannot confirm this reproduces consistently across all pods, times of day, or account types, nor rule out that traffic/concurrency levels differed between the two windows.
- **Affected population**: No evidence on whether this affects all customers or a subset (e.g., accounts with large statement history).

## 6. Risks and gaps
- Direct conflict between assignee's comment ("not us") and the log he/the ticket has attached (app version 4.7.0, statements-specific migration) — needs resolving before work is deprioritized.
- No reproduction steps, no acceptance criteria, no fix version set.
- No linked tickets for the 4.7.0 release itself or for the migration `20260914_2100_ReindexStatementLines` — traceability to what that migration actually does is missing.
- Business impact stated qualitatively ("branch staff telling customers to call back") but no ticket/incident volume attached.
