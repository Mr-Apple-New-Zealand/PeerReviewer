## Summary
On mobile web, if a transfer between own accounts times out (`ERR_TXN_504`) and the user taps Retry, the source account is debited twice while the destination is credited only once. Root cause identified as two compounding issues: the debit/credit aren't wrapped in a single DB transaction, and the Retry action resubmits with no idempotency key, so the server treats it as a brand-new transfer.

## Key details
- **Steps to reproduce** (given, staging): log in on mobile web, start a transfer between own accounts, inject >30s latency between API and DB (toxiproxy used), tap Retry when `ERR_TXN_504` appears.
- **Expected vs actual:** expected one debit/one credit; actual two debits, one credit — confirmed via log excerpt showing txn=8841 debit committed, credit failed on timeout, then txn=8842 both debit and credit committed.
- **Affected component/version:** Transactions, 3.1.4; fix targeted for 3.2.0.
- **Platform scope:** Reproduces on mobile web. Tom Becker confirmed it does **not** reproduce on desktop web, because desktop disables the submit button and has no Retry button after a timeout — indicating the bug is specific to the mobile web Retry flow.
- **Customer impact:** three customers affected (support calls 5, 6, 8 September); this matches the "customer-impact" label.
- **Acceptance criteria:** not explicitly stated in the ticket. Implied fix criteria from Priya's comment: single atomic debit/credit transaction, and idempotency key support so retries don't create duplicate transfers. No formal QA/acceptance checklist is documented.
- **Missing:** no explicit rollback/compensation criteria, no confirmation that Finance Ops has processed the manual reversals, no linked tickets (Links: None) despite this affecting both backend and customer remediation workflows.
