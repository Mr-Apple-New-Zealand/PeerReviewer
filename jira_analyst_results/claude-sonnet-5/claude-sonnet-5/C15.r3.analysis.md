# BANK-471 Analysis

## 1. Summary
Payment receipt (and other) customer emails stopped sending around 14:00 today. The assignee attributes this to ASP.NET Data Protection key storage/encryption warnings, but the attached log shows the actual failures are SMTP authentication errors — the mail server is rejecting basic authentication. The log does not support the stated root cause.

## 2. Current state
- **Status/owner:** In Progress, assigned to Marcus Reid (who is also the reporter).
- **Blocking progress:** The ticket asks "Platform" to fix data-protection key storage, but nothing in the log ties key storage to the email failures — so acting on that request as written would not fix the reported problem. A pod restart at 18:02 already occurred and did not resolve it (confirmed by Priya Nair's comment and by continued SMTP failures after the restart timestamp in the log).
- No fix version, due date, or sprint set despite Highest priority and active customer impact (support call volume "climbing").

## 3. What the log actually shows
- At startup (18:02:41–42) there are two generic ASP.NET Core warnings about Data Protection keys not being persisted and no XML encryptor configured. These are **standard startup warnings** in this framework and are not linked in the log to any email-sending code path.
- The actual send failures, starting at **18:02:48**, are:
  `System.Net.Mail.SmtpException: The SMTP server requires a secure connection or the client was not authenticated. The server response was: 5.7.139 Authentication unsuccessful, basic authentication is disabled.` — **SMTP status code 535**, from `EmailSender.SendAsync`.
- The same 535 error recurs at 18:03:08–23, 18:28:33 (customer 55617), and 18:38:02 (customer 63340) — i.e. it is a **persistent, recurring authentication failure against the SMTP server**, not a one-off.
- At 18:05:00 the log records the SMTP config in use: `smtp.example.com:587, user svc-notify@example.com, StartTls=True`. The error text "basic authentication is disabled" indicates the mail provider is rejecting the authentication method/credentials being used, consistent with a provider-side change (e.g. basic auth deprecation) or expired/invalid credentials — not a data-protection key problem.
- Separately, the outbox dispatcher shows a growing backlog (1412 → 2089 pending messages over the log window) and a warning that failed item 991204 "stays at the head of the queue" with **fixed 5s retry, no backoff, no dead-letter path** — a real but secondary reliability issue.
- The health check at 18:21:09 reports `Healthy` but explicitly skips SMTP ("smtp skipped"), so the health probe would not have caught this.

**Does the log support the reporter's explanation?** No. The Data Protection warnings are present but not connected to any send failure in the log; the actual, repeated, explicit failure is SMTP 535 authentication rejection. This is a factual mismatch between the assignee's stated diagnosis and the evidence in the attached log — worth flagging as a conflict rather than accepting the "clear cut" conclusion in the comment.

## 4. Key details — present vs missing
- **Present:** exact error/stack trace, SMTP status code, host/user in use, timestamps, outbox growth rate, confirmation restart didn't help.
- **Missing:**
  - Logs from before the 18:02 restart (the log itself notes the previous container's log "was not captured before it was replaced"), so there's no direct evidence of what was happening at 14:00 when the outage reportedly started. We only know the same SMTP 535 error was present immediately after the restart.
  - Whether SMTP credentials/auth method were recently changed, or whether the mail provider changed its auth policy (the phrase "basic authentication is disabled" suggests a provider-side policy change).
  - Acceptance criteria for resolution (e.g. "all queued messages delivered," "no new 535 errors for X minutes").
  - No linked tickets — no incident ticket, no linked change/config ticket for the mail provider, no separate ticket for the outbox retry/dead-letter gap.

## 5. Risks and gaps
- **Misdirected fix:** As written, the ticket routes this to "Platform" to fix data-protection key storage — this will not resolve the SMTP authentication failure and risks delaying the actual fix while call volumes climb.
- **Growing backlog:** ~1900+ messages pending and increasing; without backoff/dead-letter, once auth is fixed there could be a large burst of delayed/duplicate-risk sends that needs a deliberate drain plan.
- **Single-person ticket:** Reporter and assignee are the same person, and the comment expresses reluctance to investigate further ("I would rather not spend more time on this, it is fairly clear cut") — worth noting as a bias that should be checked against the log evidence rather than accepted, especially since the log contradicts it.
- **Priya Nair's suggestion** to restart the pod again should not be treated as a fix — the log shows the error persisted through the existing restart, consistent with an external (SMTP-side) cause rather than an in-process/key state issue.
- **Gap in timeline:** No log coverage of the 14:00–18:02 window, so we can't confirm the SMTP issue is the sole cause of the full outage duration, only that it's present and ongoing after the restart.

## 6. Suggested next actions
- Correct the diagnosis on the ticket: reassign/route to whoever owns the SMTP relay / mail provider account (`svc-notify@example.com` on `smtp.example.com:587`) to check whether basic auth has been disabled or credentials rotated/expired — this is the actual failure per the log, not Data Protection key storage.
- Do not restart the pod again as a fix attempt; it already failed to resolve this once, and the error is external (SMTP auth), not process state.
- Once SMTP auth is restored, monitor the outbox backlog (currently ~2089 and rising) to confirm it drains, and check for duplicate-send risk given "no backoff, no dead-letter" retry behaviour.
- Separately log the outbox dispatcher's lack of backoff/dead-letter handling as a follow-up reliability item (distinct from this incident).
- Add a due date / SLA tracking given Highest priority and active customer/call-centre impact, and update the description with the corrected root cause once confirmed.
- If key storage is genuinely believed to be an issue, provide log evidence connecting it to email delivery before assigning that work to Platform — currently none exists in the attached log.
