## Summary
Customers stopped receiving payment receipt emails from ~14:00 today. The attached log (captured after an 18:02 pod restart) shows the notification service's outbox dispatcher repeatedly failing to send emails via SMTP with **535 5.7.139 "Authentication unsuccessful, basic authentication is disabled."** The queue of pending notifications is growing continuously (1412 → 2089 messages over ~37 minutes in the log).

## Does the log support the reporter's explanation?
**No — the two are not connected.** Marcus Reid's comment attributes the failure to Data Protection key storage ("keys are effectively junk... that is why notifications are failing"), but:
- The log lines he's likely referring to (`Storing keys in a directory... may not be persisted`, `No XML encryptor configured`) are **standard ASP.NET Core startup warnings** that appear on every boot of this kind of app. They relate to protecting things like tokens/cookies, not to SMTP delivery, and the log shows no decryption error or key-related failure anywhere.
- The actual, repeated, specific error in the log is an **SMTP authentication rejection from the mail server**, with an explicit reason: basic authentication is disabled server-side (535 5.7.139 — this response code is characteristic of Exchange Online/Microsoft 365 rejecting basic auth). This is an external/credential-configuration problem, not a Data Protection key problem.
- This is a conflict between the ticket's stated diagnosis and its own attached evidence — worth flagging before routing to Platform for a key-storage fix, since that would not address the actual failure shown in the log.
