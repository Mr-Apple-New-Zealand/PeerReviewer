# BANK-482: Log Comparison — Before vs After 4.7.0

## Quantified regression
- **GetStatementLineQuery**: baseline ~281–319ms (consistent across 7 samples). After release: 33,757ms–72,974ms across 11 samples. That is roughly **100x to 250x slower**, and the durations *escalate* within the 5-minute window (33.7s → 35.9s → 36.5s → 44.3s → up to 69–73s in the final six samples).
- **GetAccountSummaryQuery**: baseline ~2,987–3,341ms; after release ~3,011–3,402ms. **Effectively unchanged.**
- **ExportStatementCommand**: 1,840ms baseline vs 1,902ms after. **Effectively unchanged.**
- **DB health check**: 6ms baseline vs 9ms after. **Effectively unchanged**, and still fast — the database connection itself is not visibly overloaded.

## What changed
- The regression is isolated to `GetStatementLineQuery`, not the account summary query.
- A new log line appears only in the after-log: `[WRN] ThreadPool starvation detected: 31 work items queued, 0 threads available for 4200ms` — a symptom absent from the baseline.
- The app startup log for the after-window shows: `Applied 1 pending migration: 20260914_2100_ReindexStatementLines` at 2026-09-14 21:05:36, on the 4.7.0 pod. This is a statements-related schema/index change deployed with 4.7.0.

## What did not change
- Account summary query latency, export command latency, and DB health-check latency are all essentially identical before and after. This is evidence the database connection and at least some query paths are unaffected — the problem does not appear to be a blanket DB or infrastructure outage.

## Conflicts with comments (logs vs stated claims)
- **Tom Becker** states "Nothing in 4.7.0 touched statements... I don't think this is us." The after-log directly contradicts this: it shows a migration named `ReindexStatementLines` applied at 4.7.0 startup, which by name concerns statement line data. This is a factual conflict between the ticket comment and the attached log — worth flagging back to Tom.
- **Ravi Kumar** suggests the culprit is "the account summary query… always slow." The logs do not support this: `GetAccountSummaryQuery` timing is essentially flat (~3s) in both logs. The actual regression is entirely in `GetStatementLineQuery`. This looks like an assumption based on reputation ("everyone knows it's slow") rather than the evidence in this ticket.

## Inference (labeled)
- The co-occurrence of the `ReindexStatementLines` migration and the subsequent `GetStatementLineQuery` slowdown is suggestive but **only a correlation** from timestamps and naming — not a proven causal link.
- The escalating durations plus the ThreadPool starvation warning suggest a compounding effect (e.g., requests queuing behind a slow or blocking call, consistent with a missing/rebuilding index or a blocking synchronous DB call), but the logs don't show query plans, index state, or CPU/GC metrics needed to confirm this.

## What these logs cannot establish
- **Root cause**: no query execution plan, index statistics, or DB-side slow query log is included — cannot confirm whether the migration caused a missing/degraded index, a lock, a table rebuild in progress, or something else.
- **Scope**: only one pod is sampled in each log (different pod names entirely: `...w4lnp` before, `...xr6vh` after) and only a single 5-minute window each. Cannot confirm whether all pods/instances are affected, whether this is sustained over hours, or specific to certain accounts/statement types.
- **Causality direction**: cannot confirm whether ThreadPool starvation is causing the slow queries or is a downstream effect of them backing up.
- **Customer/account scope**: no indication of which accounts or statement volumes were being queried; cannot rule out that this only affects certain accounts (e.g., large statement histories).
- **Infrastructure state**: no CPU, memory, GC, or connection-pool metrics for the pod are included.
