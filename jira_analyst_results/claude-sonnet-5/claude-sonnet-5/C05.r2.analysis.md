**Duplicate check**

- **BANK-440 is very likely a duplicate of BANK-425.** Both describe the same symptom — web dashboard/home screen balance stale after a transfer, unaffected by refresh — same component area (Web/Transactions), same affects version (3.1.4). BANK-425 already has a root-cause diagnosis from Hana Sato: the front end caches the balance in local storage (`BalanceCache`) for 15 minutes and nothing invalidates it on transfer.
- **MOB-88 is not a duplicate.** It's a separate platform (mobile push notifications) with a distinct root cause (notification built from the `TransferRequested` event instead of `TransferCompleted`). Coincidentally similar symptom ("stale balance shown after transfer") but unrelated mechanism.
- **BANK-419 is not a duplicate** — it's the task that introduced the 15-minute local-storage cache in 3.1.4, which is the probable root cause of both BANK-440 and BANK-425 (inference, based on timing: BANK-419 shipped the cache in 3.1.4, and both bug reports affect 3.1.4 and describe cache-like staleness).

**1. Summary**
Users see an outdated balance on the web dashboard after completing a transfer, even though the balance API itself returns the correct value immediately. The issue only clears after logging out and back in (BANK-440), matching an earlier report of the same behavior with a root cause already identified (BANK-425).

**2. Current state**
- BANK-440: Open, unassigned, no fix version, not linked to BANK-425.
- BANK-425: Open, unassigned, but has a root-cause comment from Hana Sato and a proposed fix (clear `BalanceCache` on successful transfer). Not yet implemented.
- Neither ticket references BANK-419, which shipped the caching behavior in 3.1.4.

**3. Key details**
- Steps to reproduce: present in both BANK-440 and BANK-425 (make a transfer, view web dashboard/home screen, balance doesn't update; refresh doesn't help per BANK-425).
- Affected component/version: Web, 3.1.4, in both.
- Root cause: identified only in BANK-425 (`BalanceCache`, 15-min local storage TTL, no invalidation on transfer) — this matches the "clears after logout" behavior reported in BANK-440, since logout would clear local storage.
- Acceptance criteria: missing from both tickets; no explicit statement of expected behavior (e.g. "balance must update within X seconds of a successful transfer").
- Fix version/owner: neither ticket has an assignee or fix version set.

**4. Risks and gaps**
- No links exist between BANK-440, BANK-425, and BANK-419 despite being clearly related — risk of duplicated investigation/fix effort.
- BANK-419 (Done, 3.1.4) appears to be the change that introduced this regression; this is an inference based on the caching mechanism description matching exactly, and the affected version aligning, but it isn't confirmed by comments on BANK-440/BANK-425.
- No acceptance criteria defined for the fix (e.g. should the cache be invalidated only on transfer, or should transfer responses just be excluded from caching).
- MOB-88 is unrelated but worth flagging to the team as a second instance of stale-balance-after-transfer, in case there's a broader pattern worth reviewing (different code path though).
