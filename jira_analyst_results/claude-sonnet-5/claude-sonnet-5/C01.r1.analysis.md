**1. Summary**
A mobile-web transfer that times out after ~30 seconds can be retried by the user, but the retry is sent as a brand-new request with no idempotency protection, and the debit/credit are not atomic. This has caused at least one confirmed double-debit ($250 debited twice, credited once), with three customers reporting the issue via support calls (5, 6, 8 September).

**2. Current state**
- Status: In Progress, assigned to Priya Nair.
- Root cause fully diagnosed and reproduced in staging (Priya Nair, 2026-09-09; confirmed by Tom Becker, 2026-09-10).
- Fix in progress: PR #218 wraps debit+credit in a single DB transaction and adds `Idempotency-Key` header support to the transfer endpoint.
- Blocker: PR #218 is **waiting on code review** as of the last update (2026-09-12). No further updates since then; today is 2026-09-15, and the informally stated target release (3.2.0, 2026-09-24) is 9 days away — review, merge, testing and release all still need to happen in that window.

**3. Key details**
- Steps to reproduce: documented and confirmed (log in on mobile web, inject >30s latency between API and DB via toxiproxy, trigger ERR_TXN_504, tap Retry).
- Affected component/version: Transactions, mobile-web, v3.1.4. Confirmed **not** reproducible on desktop web (no Retry button, submit is disabled after timeout) — Tom Becker, 2026-09-10.
