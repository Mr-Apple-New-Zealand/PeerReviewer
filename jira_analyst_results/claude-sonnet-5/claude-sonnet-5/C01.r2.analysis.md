## Summary
On mobile web, a transfer that times out with `ERR_TXN_504` and is then retried results in the source account being debited twice while the destination is credited only once. Root cause identified as two combined issues: the debit/credit are not wrapped in a single DB transaction, and the Retry action resubmits the transfer with no idempotency key so the server treats it as a brand-new transfer.

## Current state
- **Status:** In Progress, assignee Priya Nair.
- **Fix in progress:** PR #218 wraps debit+credit in a single transaction and adds `Idempotency-Key` header support to the transfer endpoint. It is currently **blocked on code review**.
- **Target:** fix version 3.2.0, with Aroha Walker noting a target release date of 2026-09-24.
- No blocking dependency is recorded other than the pending review.

## Key details
- **Steps to reproduce (staging):** log in on mobile web, start a transfer between own accounts, inject >30s latency between API and DB (toxiproxy used), tap Retry when `ERR_TXN_504` appears. Confirmed reproducible by both Priya Nair and Tom Becker.
- **Affected version:** 3.1.4; fix targeted for 3.2.0.
- **Affected component:** Transactions; explicitly scoped to **mobile web** (labels confirm) — Tom Becker confirmed it does **not** reproduce on desktop web, since desktop disables the submit button and has no Retry option after timeout.
- **Log evidence:** shows txn=8841 debit committed, then credit timeout, then txn=8842 debit+credit both committed — consistent with the reported double-debit.
- **Customer impact:** 3 customers reported via support calls (5, 6, 8 September), each presumably needing a manual reversal.
- **Acceptance criteria:** not explicitly stated in the ticket. Implied from "Expected" section: a retried transfer should result in exactly one debit and one credit (no duplication), likely via idempotency key handling. This should be confirmed explicitly before closing.
