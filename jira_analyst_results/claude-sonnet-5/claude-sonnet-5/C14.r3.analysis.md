## Summary
- Users reported that saving a secondary branch on a payment routing rule "spins and fails" with no error code. The attached log confirms a matching backend failure: `AddPaymentRoutingRuleSecondaryCommand` and `BulkUpdateSecondaryBranchesCommand` both fail with **403 Forbidden** when payments-api calls the `masterfile-api` service (via Dapr) to resolve branch data.
- The log also contains three other, unrelated error patterns (SQL conversion errors, SQL timeouts, and severely slow queries), plus a serious secrets-exposure finding (plaintext DB password in the logs). These should not be conflated with the reported issue but do need attention.

## Key details

**Issue directly matching the reported symptom (fix first):**
- `AddPaymentRoutingRuleSecondaryCommand` (RuleSetId 41001, SecondaryBranchID 71; also RuleSetId 41002) fails with:
  `Dapr.Client.InvocationException: ... invoking method: 'branchlocation/get?ID=71&includeDetails=False' on app-id: 'masterfile-api' ---> HttpRequestException: Response status code does not indicate success: 403 (Forbidden)`
- `BulkUpdateSecondaryBranchesCommand` fails the same way calling `branchlocation/GetAll` on `masterfile-api`.
- These occur at least twice each in the trimmed log (support removed repeated identical stack traces, so the true count is unknown).
- **This is the action described by users** — adding/updating a secondary branch on a routing rule — and it fails outright (403), which is consistent with "spins then fails" with no user-facing error code (the API returns an exception, not a friendly error).
- This is **not a database-team issue**: it's an authorization failure on a service-to-service call to `masterfile-api`. Root cause (expired/misconfigured Dapr access policy, revoked service credential, or a permission change on masterfile-api's side) can't be determined from this log alone — it needs masterfile-api's own logs or the Dapr sidecar/policy config.

**Other distinct problems in the log (separate from the reported issue):**
- `UpdatePaymentRoutingRuleCommand` (RuleSetId 41003) fails with a generic `ApplicationValidationException: Application validation errors have occured.` — no detail on which field/rule failed. Could be user error or a real validation bug; can't tell from this log.
- Repeated SQL error on `SearchPaymentRoutingRuleQuery`: `Conversion failed when converting the ****** value '******' to data type ******` (SQL Error 245). The actual value/column is masked in the log, so the specific bad data can't be identified. Recurs several times — looks like a data-quality issue in the database, but attribution needs the database team to check underlying data/column types.
- `GetMonitorJobsQueryHandler` (pending payments monitor) repeatedly throws `Execution Timeout Expired` (SQL Error -2), roughly 22:26–22:29, then recovers. Looks like a database performance/locking issue, separate feature area.
- `GetStatementLineQuery` shows escalating long-running requests (35s → 72s against a 10s threshold) at the very end of the log window — a worsening performance problem, unrelated to routing rules, that should be watched.

**Security finding (flagged, not an instruction in the ticket, just a fact in the data):**
- At startup the log records at DBG level: `Using connection string: Server=sql-prd.internal,1433;Database=Payments;User ID=svc_payments;Password=Pr0d-Payments-2026!;TrustServerCertificate=True` — a **production database password in plaintext** in application logs. This is a credential exposure and should be treated as urgent regardless of the routing-rule bug.

**Routine noise (can be ignored for triage):**
- Startup/shutdown banners, DataProtection key warnings, "Service Permissions found and sent on the event bus", ObjectMapper license messages.
- Normal completed requests (`GetPaymentBatchActionListQuery`, `ReversalItemsCommand`, `RunRoutingRuleGeneratorCommand`, etc.) with unremarkable durations.
- `GetPendingPaymentQuery returned 404: pending payment 88213 not found` — looks like an expected "not found" response, not an error.
- `TaskCanceledException: The connection was aborted by the client` at 21:11:02 — likely a client navigating away/timeout, not evidence of a server bug on its own.
- Two `RunRoutingRuleGeneratorCommand` transactions starting at the identical timestamp (21:06:09) both completed successfully — worth a passing note as a possible double-trigger, but not an active problem based on this log.
