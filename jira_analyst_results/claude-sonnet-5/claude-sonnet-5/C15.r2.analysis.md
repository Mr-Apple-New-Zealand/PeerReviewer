## 3. What the log actually shows
- Pod `notifications-api-59d7c8b4f6-tq8wz` restarted at **18:02:41**.
- Two **generic ASP.NET Core startup warnings** at 18:02:41–42:
  - `Storing keys in a directory ... that may not be persisted outside of the container.`
  - `No XML encryptor configured. Key {...} may be persisted to storage in unencrypted form.`
  These are standard boilerplate warnings that appear on any container start when Data Protection isn't configured with persistent/encrypted key storage — they are not, by themselves, evidence of a failure in progress.
- The **actual send failures**, starting at 18:02:48 and recurring through 18:38, are all:
  ```
  System.Net.Mail.SmtpException: The SMTP server requires a secure connection or the client
  was not authenticated. The server response was: 5.7.139 Authentication unsuccessful,
  basic authentication is disabled.
  SMTP status code: 535
  ```
  This is a classic mail-provider rejection of **basic authentication** on the SMTP credential used by `svc-notify@example.com` at `smtp.example.com:587` — nothing to do with data-protection keys.
- Outbox queue grows continuously across the log window: 1412 → 1508 → 1604 → 1702 → 1799 → 1896 → 1993 → 2089 pending messages. Combined with the note that item **991204 has reached 5 delivery attempts and stays at the head of the queue** with "no backoff and no dead-letter path," this confirms a genuine, escalating backlog — consistent with the contact centre's reports.
- Health check at 18:21:09 reports `Healthy (db 8ms, nats 3ms, smtp skipped)` — SMTP connectivity is explicitly **not** checked, so monitoring would not have caught this.
- A brief unrelated NATS reconnect blip occurs at 18:07:12–13 and self-resolves; doesn't appear connected to the email failures.

## 4. Does the log support the reporter's explanation?
**No.** Marcus's comment states the cause is "obvious": unpersisted data-protection keys with no XML encryptor. The log does contain those warnings, but they are startup noise, not the error causing failed sends. Every actual send failure in the log is an **SMTP 535 authentication error** — the mail server rejecting basic auth. This is a distinct, well-known failure mode (many mail providers, e.g. Microsoft 365/Exchange Online, have disabled basic auth in favour of OAuth2/modern auth), and points to a **credential or auth-method problem** with the SMTP configuration, not to key storage.
This is flagged as a factual conflict, not an instruction I'm following blindly: the ticket's own attached evidence disagrees with its author's stated conclusion, and the comment explicitly asks to close the investigation ("I would rather not spend more time on this") despite the log not actually supporting that conclusion.

## 5. Risks and gaps
- **Wrong fix risk**: if a Platform engineer proceeds on Marcus's stated cause (fix data-protection key persistence) without checking the log's actual errors, the SMTP auth failure — the thing actually blocking mail delivery — will not be fixed, and the backlog will keep growing.
- **Backlog/dead-letter risk**: with "no backoff and no dead-letter path," the queue is growing (~100 msgs per 6 minutes in this excerpt) and the head-of-line item is stuck; a fix needs to also address processing the backlog, otherwise even after SMTP is fixed there may be a large re-send storm or ordering issues.
- **Monitoring gap**: health check explicitly skips SMTP, so this class of failure has no automated detection today.
- **Timeline gap**: can't confirm whether the 14:00 reports and the 18:02+ SMTP 535 errors are the same root cause, given missing pre-restart logs.
- **No component/owner clarity**: ticket asks for "Platform" to fix key storage, but the actual problem (SMTP auth) may belong to whoever manages the mail relay/credentials — likely a different team or an external mail provider account.
- **Restart already tried and failed** (Priya, 18:44) — repeating it is unlikely to help since the error is a credential/auth-method rejection, not a transient connection issue.
