## Grouped issues (by likely shared cause)

**Group A — Cascading TypeErrors from unhandled 401 responses**
- BANKUI-3C8 (5140 events, 44 users) — `HttpErrorResponse 401` on `/api/settlements/Run/GetAllRunBookingsForCustomerOrder`, logged via a generic `console.error` handler for every failed request.
- BANKUI-4A1 (312 events, 41 users) — preceded by 22 XHR breadcrumbs returning 401.
- BANKUI-4A2 (289 events, 39 users) — preceded by 401 from `/api/settlements/CustomerOrder/Search`.
- BANKUI-4A9 (104 events, 33 users) — preceded by 401 from `/api/hq/SettlementAllocation/InvokeAction`.
- BANKUI-4B3 (97 events, 31 users) — preceded by 401 from `/api/payments/PaymentBatch/Actions`.
- **Inference**: these five issues are one root cause, not five separate defects. The near-identical `firstSeen` timestamps (all ~2026-09-05T02:14:0x) and the pattern of "401 response → code assumes a populated body → TypeError on `.sort`/`.rows`/`.returnProperties`/`.length`" strongly suggest the UI does not handle failed/unauthorized API responses defensively across several screens (settlements run, batch actions, allocation reports/entry). This is based on the breadcrumb summaries and shared timing, not confirmed backend logs.
- The underlying trigger (why calls started returning 401 on 2026-09-05) is **not in this data** — the export's releases list only shows 4.6.0 (2026-08-27) and 4.7.0 (2026-09-10), neither of which lines up with the 2026-09-05 onset. That needs separate investigation (auth/session expiry change, backend permission change, token config, etc.).

**Group B — Post-deploy chunk load failure**
- BANKUI-5D6, `ChunkLoadError: Loading chunk 6728 failed... 404`, culprit `/payments/batch/actions`. Only 63 events but **58 distinct users** — the highest user count of any issue in the export.
- **Inference**: `firstSeen` (2026-09-10T21:11:36Z) is ~6 minutes after the 4.7.0 deploy (2026-09-10T21:05:00Z). Classic pattern of clients holding an old index.html/bundle reference after a deploy invalidates chunk hashes. Likely a caching/deployment config issue rather than an application logic bug, but high blast radius.

**Not grouped / standalone**
- BANKUI-1A7: status `resolved`, already shipped in release 4.6.0. No action needed; included only because the export query pulls both resolved and unresolved issues.

## Not our defect / noise
- **BANKUI-2F0** — `SecurityError` from `chrome-extension://hdnmoggkpjoiaeldlphnmgejfcbkadkc/inject.js`. 4812 events but only **1 user**, all from a single browser session, no app breadcrumbs. This is a third-party browser extension interfering with the page, not a bank-ui defect. This is exactly the kind of high-event/low-user issue the team was burned by last sprint — recommend adding a Sentry inbound filter to suppress `chrome-extension://` culprits rather than triaging it as app work.

## Recommended priority for the two sprint slots
1. **Group A (the 401 cascade, treated as one root-cause fix)** — highest combined user impact (up to ~44 distinct users on the root 401 issue, plus overlapping affected users across four dependent screens), touches multiple pages, and matches the actual symptom pattern (crashes following failed API calls) rather than raw event count.
2. **BANKUI-5D6 (chunk load failure)** — lower event count but the **single largest distinct-user count** (58) of any real defect, and correlates cleanly with the 4.7.0 deploy, making it likely to recur on every future deploy until fixed (e.g., forced reload on chunk failure, cache-control/versioning fix).

This avoids repeating last sprint's mistake: sorting purely by event count would put BANKUI-3C8 (5140) and BANKUI-2F0 (4812) at the top — but 2F0 is not our bug, and 3C8 in isolation understates the real (multi-page) impact of Group A.
