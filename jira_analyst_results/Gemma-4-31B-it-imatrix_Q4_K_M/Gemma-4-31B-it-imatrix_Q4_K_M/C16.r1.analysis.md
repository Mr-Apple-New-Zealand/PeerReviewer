**Analysis of Log Regression: BANK-482**

The `GetStatementLineQuery` has suffered a severe performance regression following the 4.7.0 release, with response times increasing from ~300ms to between 33 and 73 seconds. This has led to ThreadPool starvation.

**Quantified Regression: GetStatementLineQuery**
*   **Baseline (4.6.3):** 281ms to 319ms.
*   **Post-Release (4.7.0):** 33,757ms to 72,974ms.
*   **Impact:** An increase in latency of approximately 110x to 240x.

**What Changed**
*   **Version:** The application version moved from 4.6.3 to 4.7.0.
*   **Database Schema:** A migration was executed upon startup: `20260914_2100_ReindexStatementLines`.
*   **System Stability:** The 4.7.0 logs show a `ThreadPool starvation detected` event (31 work items queued, 0 threads available for 4200ms), which was not present in the baseline.

**What Remained Constant**
*   **GetAccountSummaryQuery:** Performance remained stable (~2.9s to 3.3s in 4.6.3 vs ~3.0s to 3.4s in 4.7.0). This contradicts the suggestion in the ticket comments that this query is the cause of the current issue.
*   **ExportStatementCommand:** Performance remained stable (~1.8s in 4.6.3 vs ~1.9s in 4.7.0).
*   **Database Health:** The `/healthz` check remained fast (6ms vs 9ms).

**Log Limitations**
These logs cannot establish:
*   The specific technical cause of the slowdown (e.g., why the reindexing migration caused a regression).
*   Whether the ThreadPool starvation is a direct result of the slow queries or a separate configuration issue in 4.7.0.
*   The exact code changes introduced in 4.7.0, other than the mentioned migration.

**Inferences**
*   **Root Cause:** The regression is likely caused by the migration `20260914_2100_ReindexStatementLines`, as it is the only recorded change temporally linked to the collapse of `GetStatementLineQuery` performance.
*   **Conflict:** Ravi Kumar's comment suggesting `GetAccountSummaryQuery` is the problem is contradicted by the logs, which show that specific query's performance is unchanged.
