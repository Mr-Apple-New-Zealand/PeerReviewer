**Summary:**  
A transfer retry after a timeout (ERR_TXN_504) causes the source account to be debited twice while the destination is credited only once. This occurs because the retry triggers a new transfer without an idempotency key, and the debit/credit operations are not atomic — the first debit commits before the credit times out, leaving the second debit uncancelled.

**Current state:**  
- **Status:** In Progress  
- **Assignee:** Priya Nair  
- **Resolution:** Unresolved  
- **PR #218** is open and awaiting code review to fix the issue.  
- **Target release:** 3.2.0 (due 2026-09-24)  
- **Customer impact:** 3 confirmed cases; Finance must manually reverse duplicate debits.

**Key details:**  
- **Steps to reproduce:**  
  1. Initiate transfer on mobile web.  
  2. Introduce >30s latency (via toxiproxy).  
  3. Tap Retry on timeout.  
- **Expected:** One debit, one credit.  
- **Actual:** Two debits, one credit.  
- **Root causes (from Priya’s comment):**  
  - Retry POSTs a new transfer without idempotency key → server treats as new request.  
  - Debit/credit not in same transaction → first debit commits before credit fails.  
- **Affected version:** 3.1.4  
- **Fix in PR #218:**  
  - Wrap debit + credit in a single database transaction.  
  - Add Idempotency-Key header to prevent duplicate transfers.  
- **Mobile web only:** Desktop web disables retry and prevents this bug.
