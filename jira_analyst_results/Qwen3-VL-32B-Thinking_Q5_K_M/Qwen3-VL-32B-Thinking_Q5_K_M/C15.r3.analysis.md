# Analysis of BANK-471: Customers are not receiving payment receipt emails

**Summary**  
Customers are not receiving payment receipt emails, with contact center reporting the issue started around 14:00. The log shows repeated SMTP authentication failures (535) for payment receipt emails, with the server response "5.7.139 Authentication unsuccessful, basic authentication is disabled." The reporter's claim that data protection keys are the cause is not supported by the evidence.

**Current state**  
- Status: In Progress  
- Owner: Marcus Reid  
- Blocker: Misdiagnosis of the root cause (reporter incorrectly attributes the issue to data protection keys while log shows SMTP authentication failure)

**Key details**  
- Steps to reproduce: Missing (no sequence provided to reproduce the issue)  
- Affected components: Notifications (specifically the notifications service)  
- Affected versions: notifications 2.3.4 (as per ticket)  
- Acceptance criteria: Missing (no definition of when the issue is resolved)  
- Critical log evidence: SMTP errors show "535 5.7.139 Authentication unsuccessful, basic authentication is disabled" and "The SMTP server requires a secure connection or the client was not authenticated"

**Risks and gaps**  
- **Critical conflict**: Reporter's claim about data protection keys being the cause contradicts log evidence showing SMTP authentication failures. The log explicitly shows: "5.7.139 Authentication unsuccessful, basic authentication is disabled" and "SMTP status code: 535"
- **Missing information**: No details about SMTP server configuration, credentials, or recent changes
- **Ambiguity**: No indication of whether the issue started with the 2.3.4 release (the affected version) or was previously working
- **Gaps**: No information about the SMTP service itself (e.g., who manages it, whether credentials have expired)
- **Inference**: The data protection key warnings (log entries at 18:02:41-42) are likely unrelated to the email delivery issue as they are warnings (not errors) and the log shows the service is functioning otherwise

**Suggested next actions**  
- Platform team should investigate SMTP server configuration to determine why authentication is failing (given the specific error 535/5.7.139)
- The ticket should be updated to correctly identify the root cause as SMTP authentication failure, not data protection keys
- The team should verify the authentication method used by the notifications service (log shows "StartTls=True" but server may require a different mechanism)
- Verify if the SMTP server configuration has changed recently (14:00 is the reported time of issue start)
- The "No XML encryptor configured" warning (18:02:42) should be addressed separately as it appears unrelated to current failure

**Note**: The log explicitly shows the service is attempting to send to "smtp.example.com:587" with user "svc-notify@example.com" (18:05:00), but the server is rejecting this with the 535 authentication error. This is the actual issue causing the email failures, not the data protection key warnings.
