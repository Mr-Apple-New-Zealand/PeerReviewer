### Summary  
A mobile web transfer timeout (ERR_TXN_504) causes duplicate debits when users retry the transaction. The source account is debited twice while the destination is credited once, due to the retry triggering a new transfer without an idempotency key and the debit/credit not being in the same database transaction. Three customers reported this issue via support calls (Sept 5–8, 2026).  

### Current state  
- **Status**: In Progress (updated 2026-09-12 16:40)  
- **Owner**: Priya Nair  
- **Blocking progress**: Waiting on code review for PR #218 (wraps debit/credit in a single transaction and adds idempotency key support). No other blockers noted.  

### Key details  
- **Steps to reproduce**:  
  1. Log in to mobile web, start a transfer between own accounts.  
  2. Add >30s latency (via toxiproxy) to cause timeout (ERR_TXN_504).  
  3. Tap Retry after timeout.  
- **Affected components**: Mobile web transfer flow (Transactions component).  
- **Affected versions**: 3.1.4 (production).  
- **Fix versions**: 3.2.0 (target release: 2026-09-24).  
- **Acceptance criteria**:  
  - Retry after timeout should not create duplicate debits.  
  - Debit and credit must be atomic (single database transaction).  
  - Idempotency key must prevent duplicate processing.  
- **Missing**:  
  - Exact retry button behavior (desktop web disables the button; mobile web does not).  
  - How idempotency keys are generated/validated.
