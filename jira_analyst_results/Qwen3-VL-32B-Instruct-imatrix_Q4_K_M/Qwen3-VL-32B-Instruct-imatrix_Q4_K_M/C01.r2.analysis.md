**Summary**  
A bug in the mobile web transfer flow causes the source account to be debited twice when a transfer times out and the user retries. The debit and credit operations are not atomic, and the retry lacks an idempotency key, leading to duplicate debits. This has affected three customers and requires manual reversal by Finance Ops.

**Current State**  
- **Status**: In Progress  
- **Assignee**: Priya Nair  
- **Blocking Factor**: Awaiting code review for PR #218, which implements a fix by wrapping debit/credit in a single transaction and adding idempotency key support.  
- **Target Fix Version**: 3.2.0 (scheduled for 2026-09-24)  
- **Sprint**: Sprint 38 (ends 2026-09-22) — fix is likely to be delivered in the next sprint if code review is completed soon.

**Key Details**  
- **Steps to Reproduce**:  
  1. Log in on mobile web, initiate transfer between two own accounts.  
  2. Introduce >30s latency (e.g., via toxiproxy).  
  3. When "ERR_TXN_504" appears, tap Retry.  
- **Affected Components**: Transactions  
- **Affected Version**: 3.1.4  
- **Fix Version**: 3.2.0  
- **Acceptance Criteria**:  
  - Retry should not cause duplicate debits.  
  - Debit and credit must be atomic (in one DB transaction).  
  - Retry must use idempotency key to prevent duplicate processing.  
  - Mobile web UI should not allow retry without idempotency.
