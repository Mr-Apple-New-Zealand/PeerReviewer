**Summary**  
The Statements API performance degraded significantly after release 4.7.0, with `GetStatementLineQuery` requests taking 35–72 seconds (vs. ~300ms before), causing timeouts and browser failures. The `GetAccountSummaryQuery` remains similarly slow (~3–3.5s), but the regression is concentrated in `GetStatementLineQuery`. A database migration (`20260914_2100_ReindexStatementLines`) was applied at release time, and the logs show thread pool starvation, indicating a systemic performance issue.

---

**Quantified Regression**

| Metric | Before 4.7.0 (log) | After 4.7.0 (log) | Change | Notes |
|--------|--------------------|-------------------|--------|-------|
| `GetStatementLineQuery` avg | ~300ms | ~50,000ms (median ~35,000ms) | **~167x slower** | Multiple requests exceed 35s, some over 70s |
| `GetAccountSummaryQuery` avg | ~3,200ms | ~3,200ms | **No change** | Consistent performance, not the cause |
| `ExportStatementCommand` | 1,840ms | 1,902ms | **Slight increase** | Not significant |
| Thread pool status | Not reported | Starvation detected (31 queued, 0 available threads) | **New issue** | Indicates system-level overload |

---

**What Changed Between Logs**

1. **Application Version**:  
   - Before: `App=4.6.3`  
   - After: `App=4.7.0`  
   → Confirmed version change.

2. **Database Migration Applied**:  
   - After log: `Applied 1 pending migration: 20260914_2100_ReindexStatementLines`  
   → This migration likely altered the `StatementLines` table index structure.  
   → **Strong inference**: This migration caused the performance regression in `GetStatementLineQuery`.

3. **Performance of `GetStatementLineQuery`**:  
   - Before: ~300ms  
   - After: 35,000–72,000ms  
   → **Massive regression**. This is the primary cause of the "unusable" statements page.

4. **Thread Pool Starvation**:  
   - Only appears in after log: `ThreadPool starvation detected: 31 work items queued, 0 threads available for 4200ms`  
   → Indicates the API is overwhelmed by long-running requests, which are likely the slow `GetStatementLineQuery` calls.

5. **Health Check**:  
   - DB latency: 6ms → 9ms  
   → Minor increase, not significant.

---

**What Did Not Change**

- `GetAccountSummaryQuery` performance: ~3.2s before and after → **No regression**.
- `ExportStatementCommand`: ~1.8s → ~1.9s → **Negligible change**.
- Health check status: Both show “Healthy” → **No service-level failure**.
- Log format and structure: Identical → **No instrumentation change**.

---

**What These Logs Cannot Establish**

1. **Root Cause of Migration Impact**:  
   - The logs show the migration was applied, but **not** what the migration did (e.g., dropped index, added non-covering index, etc.).  
   - No SQL execution plans or query metrics are included.

2. **Exact Trigger for Performance Drop**:  
   - The logs start after the migration is applied. We cannot confirm whether the migration *caused* the regression or if another change (e.g., config, DB load, or external dependency) coincided.

3. **User Experience Details**:  
   - Logs show backend delays, but **not** browser timeouts, UI behavior, or error messages shown to users.  
   - No client-side logs or network traces.

4. **Scope of Impact**:  
   - Logs show only one pod (`statements-api-7d4a2f9c61-xr6vh`).  
   → Cannot confirm if the issue is isolated to one instance or systemic.

5. **Whether the Migration Was Intended to Improve Performance**:  
   - The migration name (`ReindexStatementLines`) suggests it was meant to improve performance.  
   → If so, it had the **opposite effect** — but logs don’t explain why.

---

**Conclusion**

The logs **clearly show** a massive performance regression in `GetStatementLineQuery` after 4.7.0, coinciding with a database migration. The migration is the **most likely root cause**, and the thread pool starvation confirms the system is overwhelmed. `GetAccountSummaryQuery` performance is unchanged, so Ravi Kumar’s comment is misleading — the issue is not with that query.
