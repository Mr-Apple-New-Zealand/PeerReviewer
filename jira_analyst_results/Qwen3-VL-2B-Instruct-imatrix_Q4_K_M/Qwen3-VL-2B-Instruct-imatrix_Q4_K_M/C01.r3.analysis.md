**Summary:**  
A bug in the mobile web transfer functionality where a customer's $250 transfer is being debited twice and credited only once due to a timeout and retry mechanism. The issue occurs when the spinner hangs for over 30 seconds, triggering a retry, which causes the same transaction to be processed twice.

**Key Details:**  
- **Reproduction Steps:**  
  1. Log in on mobile web.  
  2. Start a transfer between two own accounts.  
  3. Introduce latency (e.g., via toxiproxy) to simulate a 30-second delay.  
  4. When the error "Request timed out (ERR_TXN_504)" appears, tap Retry.  

- **Expected Behavior:**  
  - One debit and one credit.  

- **Actual Behavior:**  
  - Two debits (the same amount) and one credit.  

- **Root Cause (from ticket):**  
  1. The retry action sends a new POST request to `/api/transaction/transfer` without an **Idempotency Key**, causing the server to treat it as a new transfer.  
  2. The debit and credit are **not in a single database transaction**, so the first debit (which is committed) remains active when the credit fails due to timeout.  

- **Log Evidence:**  
  - `debit committed txn=8841` → `credit failed txn=8841: timeout after 30000ms` → `debit committed txn=8842` → `credit committed txn=8842`  
  - This shows two debits and one credit, confirming the issue.

- **Impact:**  
  - 3 customers reported this (support calls on 5, 6, and 8 September).  
  - The issue is **only visible on mobile web**; it does **not reproduce on desktop web** (as confirmed by Tom Becker).

- **Dependencies:**  
  - PR #218 is open: It wraps the debit and credit in a single transaction and adds Idempotency-Key support.  
  - Waiting for code review on PR #218.  
  - Target release: 3.2.0 (2026-09-24).

**Conclusion:**  
This is a critical bug in the mobile web transfer flow. The root cause is a lack of idempotency in the retry logic and improper transaction isolation. The fix requires changes to the transfer endpoint to wrap the debit and credit in a single transaction and use an Idempotency-Key header. The fix is expected to be ready for review and deployment by 2026-09-24.
