**Regression Quantification & Analysis**

**Summary:**
The statements page performance degraded significantly after release 4.7.0, with `GetStatementLineQuery` requests taking 35k–73kms (vs 280–320ms pre-release), and thread pool starvation detected. The `GetAccountSummaryQuery` remained relatively stable (~3kms vs ~3kms). The regression is not due to a new feature but a performance degradation in an existing, known slow query.

- **Status:** Open (Unresolved)
- **Owner:** Tom Becker (initially assigned; no action taken yet)
- **Blocking:** No known fix version or sprint assigned; no resolution or workaround provided.

**Key Details:**

- **Pre-release (4.6.3):**
  - `GetStatementLineQuery`: 280–320ms (avg ~300ms)
  - `GetAccountSummaryQuery`: 3k–3.3kms (avg ~3200ms)
  - No long-running requests; no thread pool starvation.

- **Post-release (4.7.0):**
  - `GetStatementLineQuery`: 35k–73kms (avg ~50kms)
  - `GetAccountSummaryQuery`: 3k–3.4kms (avg ~3300ms)
  - Thread pool starvation detected: 31 queued work items, 0 threads available for 4.2s.
  - Multiple `GetStatementLineQuery` requests exceeded 10s threshold (long-running warning).

- **Change since 4.7.0:**
  - **New migration applied:** `20260914_2100_ReindexStatementLines` — likely the root cause.
  - **Query performance degraded:** `GetStatementLineQuery` is now 100x slower on average.
  - **Thread pool exhaustion:** Indicates backend resource contention, not just query slowness.

- **What did NOT change:**
  - `GetAccountSummaryQuery` performance is unchanged (still ~3kms).
  - No new code touched statements (per Tom Becker’s comment).
  - No new database schema or index changes mentioned.
