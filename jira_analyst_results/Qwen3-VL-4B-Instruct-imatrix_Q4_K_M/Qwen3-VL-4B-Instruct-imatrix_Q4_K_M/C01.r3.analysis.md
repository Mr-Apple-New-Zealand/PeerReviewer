**Summary:**  
A transfer retry after a timeout on mobile web causes the source account to be debited twice while the destination is credited once, due to lack of idempotency and missing transactional integrity. This has affected three customers and is blocking the 3.2.0 release.

**Current state:**  
- **Status:** In Progress  
- **Assignee:** Priya Nair  
- **Resolution:** Unresolved  
- **Priority:** High  
- **Due Date:** None (but target is 3.2.0 release on 2026-09-24)  
- **PR:** #218 is open and awaiting code review.

**Key details:**  
- **Steps to reproduce:**  
  1. Log in on mobile web, start a transfer between own accounts.  
  2. Introduce >30s latency (via toxiproxy).  
  3. Tap “Retry” after “Request timed out (ERR_TXN_504)”.  
- **Affected components:** Transactions (mobile web)  
- **Affected version:** 3.1.4  
- **Fix target:** 3.2.0  
- **Acceptance criteria:**  
  - One debit, one credit per transfer.  
  - No duplicate debits after retry.  
  - Retry should be idempotent and atomic.

**Risks and gaps:**  
- **Ambiguity:** No clear acceptance criteria for “retry behavior” or “idempotency key” implementation.  
- **Dependency:** PR #218 is pending code review — no confirmation if it fixes both issues (idempotency + atomicity).  
- **Customer impact:** Finance must manually reverse duplicate debits for 3 customers — no automated fix yet.  
- **Platform difference:** Desktop web does not have retry button — this is a known difference, but not a blocker.  
- **No test coverage mentioned** — risk of regression.
