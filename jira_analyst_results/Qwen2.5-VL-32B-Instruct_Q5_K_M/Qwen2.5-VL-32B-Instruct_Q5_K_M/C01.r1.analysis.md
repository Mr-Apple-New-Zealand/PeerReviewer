### Analysis of Ticket BANK-412

#### **Summary**
The issue occurs when a customer retries a timed-out transfer on mobile web, resulting in the source account being debited twice while the destination account is credited only once. This bug impacts customers using version 3.1.4 and has been reproduced in staging with specific latency conditions.

---

#### **Current State**
- **Status:** In Progress
- **Assignee:** Priya Nair
- **Blocking Factors:**
  - Code review for PR #218 is pending.
  - No due date is set, but the fix is targeted for version 3.2.0, scheduled for release on 2026-09-24.

---

#### **Key Details**
- **Steps to Reproduce:**
  1. Log in on mobile web and initiate a transfer between two accounts.
  2. Introduce more than 30 seconds of latency between the API and database (e.g., using toxiproxy).
  3. When the timeout error "ERR_TXN_504" appears, tap Retry.

- **Affected Components:** Transactions
- **Affects Versions:** 3.1.4
- **Fix Versions:** 3.2.0
- **Acceptance Criteria:**
  - The retry mechanism should ensure idempotency (i.e., no duplicate debits).
  - Debit and credit operations should be atomic (in a single database transaction).

**Missing Details:**
- No explicit acceptance criteria are listed in the ticket.
- No test cases or verification steps are provided for the fix.

---

#### **Risks and Gaps**
1. **Idempotency Risk:**
   - The current implementation lacks an idempotency key mechanism, allowing retries to be treated as new transfers.
   - This could lead to further duplicate debits if the issue is not resolved before the release.

2. **Atomicity Issue:**
   - Debit and credit operations are not atomic, leading to inconsistent states when one part of the transaction fails (e.g., credit timeout).

3. **Customer Impact:**
   - Three customers have already been affected, requiring manual reversal by Finance Ops.
   - The issue is marked as "High" priority due to its financial impact.

4. **Platform-Specific Behavior:**
   - The bug only reproduces on mobile web; desktop web behaves differently (submit button is disabled after a timeout).

5. **Dependency on Code Review:**
   - PR #218, which addresses the issue, is awaiting code review. Delays in review could push the fix beyond the 3.2.0 release.

6. **No Test Cases:**
   - There are no documented test cases or automated checks to verify the fix.
