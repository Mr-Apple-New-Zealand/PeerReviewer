### Incident Timeline, Detection Time, Recovery Time, and Root Cause Analysis

#### **Summary**
An incident occurred where all users were unable to complete transfers due to a high transfer error rate. The issue was caused by a mismatch in JWT signing keys between the Auth service and the Transactions API after a configuration deploy.

---

### **Incident Timeline**

1. **Incident Start (Detection):**  
   - **Time:** 2026-09-11 09:31 NZST  
     - Monitoring alerts indicated an increase in transfer errors, with the error rate exceeding 20%.
     - The first visible symptoms were observed around 09:31 NZST when errors started appearing.

2. **Incident Declaration:**  
   - **Time:** 2026-09-11 09:47 NZST  
     - Sam Okafor declared the incident, noting a transfer error rate of 64%.

3. **Support Queue Spike:**  
   - **Time:** 2026-09-11 10:05 NZST  
     - Marcus Reid reported a spike in support calls, with over 40 calls in the last 15 minutes.

4. **Database Investigation:**  
   - **Time:** 2026-09-11 10:10 NZST  
     - Priya Nair suggested the database might be the issue due to slow queries on the transactions table.

5. **Root Cause Identified:**  
   - **Time:** 2026-09-11 10:24 NZST  
     - Sam Okafor identified the root cause as a mismatch in JWT signing keys between the Auth service and the Transactions API. The Auth service started issuing tokens signed with a new key, but the Transactions API was still validating against the old key.

6. **Rollback Initiated:**  
   - **Time:** 2026-09-11 10:31 NZST  
     - Sam Okafor began rolling back the configuration deploy (OPS-81).

7. **Recovery Complete:**  
   - **Time:** 2026-09-11 10:42 NZST  
     - The rollback was completed, and the transfer error rate dropped below 1%.

8. **Incident Resolved:**  
   - **Time:** 2026-09-11 10:50 NZST  
     - Sam Okafor resolved the ticket, noting the root cause and scheduling a post-incident review for 2026-09-16.

---

### **Time to Detect (TTD)**
- **Detection Time:** From the start of errors (09:31 NZST) to incident declaration (09:47 NZST).  
  - **TTD:** 16 minutes

### **Time to Recover (TTR)**
- **Recovery Time:** From incident declaration (09:47 NZST) to the error rate dropping below 1% (10:42 NZST).  
  - **TTR:** 55 minutes

---

### **Root Cause**
The root cause of the incident was identified as a mismatch in JWT signing keys:
- The Auth service started issuing tokens signed with a new key after the configuration deploy (OPS-81).
- However, the Transactions API continued to validate tokens against the old key, resulting in 401 errors ("IDX10503: Signature validation failed").

---

### **Analysis**
- **Detection:** The incident was detected within 16 minutes of the first symptoms appearing, which is relatively quick.
- **Recovery:** The recovery took 55 minutes, primarily due to identifying the root cause and rolling back the configuration deploy.
- **Root Cause Clarity:** The root cause was clearly identified and resolved by rolling back the configuration change.

### **Suggested Next Actions**
1. **Post-Incident Review:**  
   - Conduct a post-incident review on 2026-09-16 to analyze the incident, identify improvement opportunities, and update processes or tools to prevent similar issues in the future.
   - Participants should include Sam Okafor, Marcus Reid, and Priya Nair, as they were key contributors during the incident.

2. **Process Improvement:**  
   - Implement a mechanism to ensure that all dependent services are updated simultaneously when changing JWT signing keys.
   - Consider adding automated tests or validation steps in the deployment pipeline to catch such mismatches before they affect production.

3. **Monitoring Enhancements:**  
   - Improve monitoring to detect discrepancies between Auth service token signatures and Transactions API validation keys in real-time.

4. **Documentation Update:**  
   - Update documentation for configuration deploys involving JWT signing keys to include explicit steps for updating all dependent services.

---

### **Conclusion**
The incident was resolved successfully by rolling back the problematic configuration deploy. The root cause was a mismatch in JWT signing keys, which highlights the need for better coordination between services during configuration changes. A post-incident review is scheduled to address these gaps and prevent future occurrences.
