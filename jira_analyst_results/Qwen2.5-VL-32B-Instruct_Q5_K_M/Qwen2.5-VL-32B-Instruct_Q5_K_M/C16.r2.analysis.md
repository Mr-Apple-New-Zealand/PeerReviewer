### Analysis of BANK-482: Statements page unusable since release 4.7.0

#### Summary:
The statements API has become significantly slower after the release of version 4.7.0, with `GetStatementLineQuery` requests now taking over a minute to complete, compared to sub-second responses before the release. This regression is impacting customer-facing functionality and causing operational issues for branch staff.

---

### Current State:
- **Status:** Open
- **Assignee:** Tom Becker
- **Blocking:** The root cause of the performance regression has not been identified yet.
- **Priority:** High, as this issue is affecting customer experience and operational processes.

---

### Key Details:
#### Steps to Reproduce:
1. Access the statements API endpoint (`GetStatementLineQuery`) after version 4.7.0.
2. Observe significantly longer response times compared to before the release.

#### Affected Components:
- **Statements API** (component)
- **Version:** 4.7.0

#### Acceptance Criteria:
- The performance of `GetStatementLineQuery` should match or exceed the baseline performance observed in version 4.6.3.
- Response times for `GetStatementLineQuery` should not exceed 10 seconds.

### Quantification of Regression:
#### Before Release (Version 4.6.3):
- **GetStatementLineQuery:** Average response time ~300ms.
- **GetAccountSummaryQuery:** Average response time ~3200ms.
- **ThreadPool:** No starvation detected.

#### After Release (Version 4.7.0):
- **GetStatementLineQuery:** Average response time >35 seconds, with some requests taking over a minute.
- **GetAccountSummaryQuery:** Average response time remains around ~3200ms.
- **ThreadPool:** Starvation detected, with 31 work items queued and no available threads for 4200ms.

#### Key Changes:
- The `GetStatementLineQuery` performance has regressed significantly, increasing by over **100x**.
- ThreadPool starvation is a new issue introduced in version 4.7.0.
- The migration applied (`20260914_2100_ReindexStatementLines`) may be related to the regression.

#### No Changes:
- The `GetAccountSummaryQuery` performance remains stable, indicating that this query is not the primary cause of the issue.
- The health check (`/healthz`) continues to report as "Healthy" with similar database response times (6ms before vs. 9ms after).
