### Summary
The issue is that retrying a timed-out transfer on mobile web results in the source account being debited twice while the destination account is credited only once. This has affected three customers and is due to the lack of idempotency in the retry mechanism and separate database transactions for debit and credit.

### Current state
- **Status:** In Progress
- **Owner:** Priya Nair
- **Blocking progress:** Waiting on code review for PR #218, which aims to fix the issue by wrapping debit and credit operations in a single transaction and adding idempotency support.

### Key details
- **Steps to reproduce:**
  - Log in on mobile web.
  - Start a transfer between two own accounts.
  - Introduce more than 30 seconds of latency between the API and the database.
  - When ERR_TXN_504 appears, tap Retry.
  
- **Affected components or versions:** Transactions component, version 3.1.4.
- **Acceptance criteria:**
  - The debit and credit operations should be part of a single transaction to ensure atomicity.
  - The retry mechanism should use an idempotency key to prevent duplicate transactions.
  - The issue should not reproduce on mobile web after the fix.

### Risks and gaps
- **Ambiguities:** It is unclear if the fix in PR #218 will fully address the issue of separate database transactions for debit and credit.
- **Missing information:** No details are provided on how Finance Ops will handle the manual reversal of duplicate debits for affected customers.
- **Dependencies:** The ticket depends on the successful code review and merge of PR #218.
