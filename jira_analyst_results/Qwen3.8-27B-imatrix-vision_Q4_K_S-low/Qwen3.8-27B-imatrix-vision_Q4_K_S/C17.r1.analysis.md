The breadcrumbs tell a clear story in two phases separated by a **~83-minute idle gap**:

**Gap (timestamps 1789182813 → 1789197792, ~83 minutes):**
- No breadcrumbs. Tab was open but idle.

**Phase 2 – Resumption and cascade failure (timestamps 1789197792 → 1789197830, ~38 sec):**

  - `GET /api/payments/PaymentBatch/Actions`
- Angular's `HttpErrorResponse` objects were logged to console (status 401, statusText "OK" — a known Angular quirk where `statusText` is unreliable on error responses).
- **Four TypeError events** were fired in rapid succession (visible as `sentry.event` breadcrumbs and the main exception):
  1. `Cannot read properties of undefined (reading 'rows')`
  2. `Cannot read properties of undefined (reading 'rows')`

- User navigated back from allocation-entry → allocation-reports → batch actions, triggering further 401s and the final `.length` TypeError.
- The screen went blank (Angular error handler killed the component tree).

## 2. The Underlying Defect

This is a **two-layer problem**:

**Trigger: Auth token expiry without graceful recovery.**
The token that was refreshed during Phase 1 became invalid during the 83-minute idle period. When the user resumed, all API calls returned 401. The app did **not** attempt a second token refresh, did not redirect to login, and did not surface a "session expired" message. The 401s propagated straight into component code.

**Defect: Missing null/guard checks on API response handling.**
The component code (in chunk `6728`) uses RxJS operators (the `project` function in the stack trace is RxJS's internal `MapOperator.project`) to transform HTTP responses. It assumes the response body has the expected shape (`.rows`, `.sort`, `.returnProperties`, `.length`) and accesses those properties directly. When the HTTP client returns a 401 error, the response body is `undefined` (or the observable emits an error that bypasses the normal data path), and the code calls a method on `undefined`.

Specifically, the main exception:
```
TypeError: Cannot read properties of undefined (reading 'sort')
```
originates in `ie.project` at `6728.b4f17ce620a8d539.js:1:60295`, propagated through the RxJS error chain (`ie.next` → `ie._next` → `ie.project`), and was caught by Angular's `ErrorHandler`. The mechanism is `auto.function.angular.error_handler` with `handled: false` — meaning it was an **unhandled** error that took down the view.

**Inference (not directly provable from the event):** The most likely design flaw is that the service layer's HTTP calls use something like `http.get(...).pipe(map(res => res.body.rows.sort(...)))` without an ` catchError ` or a guard like `res?.body?.rows?.sort(...)`. The 401 causes Angular's HttpClient to throw an `HttpErrorResponse` (not a `HttpEvent` with a body), so `res` is the error object, and `res.rows` (or whatever intermediate property) is `undefined`.

## 3. Environment Discrepancy (Important)

| Field | Value | Implication |
|-------|-------|-------------|
| Sentry `environment` tag | `"Production"` | SDK is configured to report as Production |
| Actual URL | `https://bank-uat.example.com/...` | This is a **UAT** environment |

Tom Becker's comment flags this correctly. The Sentry SDK is misconfigured for this deployment — it's tagging UAT traffic as Production. This means:
- Production alerting/noise may be contaminated by UAT events.
- The "production incident" framing in the ticket is based on a mislabelled environment.

This needs to be resolved before triage priority can be correctly assessed.
