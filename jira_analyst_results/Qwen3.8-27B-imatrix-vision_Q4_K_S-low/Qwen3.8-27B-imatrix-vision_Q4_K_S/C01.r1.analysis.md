# Analysis: BANK-412

## 1. Summary

A mobile-web transfer that times out mid-execution leaves the source account debited but the destination not yet credited. When the customer taps **Retry**, the server creates a second transfer with no idempotency check, producing a second debit while the first credit (which never fired) is missing. Net effect: **two debits, one credit**. Three customers are affected to date.

## 3. Key Details

### Root cause (confirmed by Priya, reproduced in staging)

Two independent defects combine to produce the bug:

1. **No idempotency key on the transfer endpoint.** The Retry button issues a fresh `POST /api/transaction/transfer`. The server has no way to recognise it as a duplicate of a previous attempt, so it creates a new transaction.
2. **Debit and credit are not in a single database transaction.** When the credit leg times out (30 s), the debit leg has already been committed and is not rolled back.

Together: the first attempt commits a debit and loses the credit; the retry commits a second debit and a second credit. Result is two debits, one credit.

### Log evidence

```
09:41:02  debit committed  txn=8841  account=***1180  250.00
09:41:32  credit FAILED    txn=8841  timeout after 30000ms
09:41:40  debit committed  txn=8842  account=***1180  250.00   ← retry
09:41:41  credit committed txn=8842  account=***2271  250.00
```

The 8-second gap between the failed credit (09:41:32) and the retry debit (09:41:40) is consistent with the user tapping Retry after seeing the error.

### Reproduction

- **Environment:** Staging, version 3.1.4, mobile web
- **Method:** Inject >30 s latency between API and database via toxiproxy
- **Steps:** Initiate transfer → wait for `ERR_TXN_504` → tap Retry
- **Desktop web:** Confirmed **not** affected (Tom Becker, 2026-09-10). Desktop disables the submit button after a timeout and has no Retry button.

### What the fix (PR #218) addresses

- Wraps debit and credit in a single database transaction (addresses root cause #2).
- Adds `Idempotency-Key` header support to the transfer endpoint (addresses root cause #1).

- **Idempotency edge case (inference).** The ticket does not specify what happens when the client sends an `Idempotency-Key` that was already used for a *successfully completed* transfer (i.e., the first attempt actually succeeded server-side but the client saw a timeout). If the server returns the original result, the customer is fine; if it rejects the request, the customer is stuck. This needs to be covered in the PR review.
- **Scope confirmation.** The bug is confirmed on mobile web only. It is worth explicitly stating in the ticket that desktop web is out of scope so it is not re-tested unnecessarily.
- **No regression test mentioned.** PR #218 description does not mention whether a regression test (e.g., an integration test with simulated timeout + idempotency replay) is included.
