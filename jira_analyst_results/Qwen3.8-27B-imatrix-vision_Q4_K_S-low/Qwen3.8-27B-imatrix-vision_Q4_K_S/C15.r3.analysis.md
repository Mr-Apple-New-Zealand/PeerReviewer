## Analysis: BANK-471

### 1. Summary

Customers stopped receiving payment receipt emails at approximately 14:00 on 2026-09-15. The attached log shows the **actual cause is an SMTP authentication failure** (error 535 — "basic authentication is disabled" on the server), not the data protection key issue the reporter has identified. The outbox is accumulating undelivered messages with no backoff or dead-letter path, and a single stuck item is blocking the queue head.

---

### 2. Does the log support the reporter's explanation?

**No.** This is the most important finding.

**What Marcus claims:**
> "The service is storing its data protection keys in a directory that is not persisted and there is no XML encryptor configured, so the keys are effectively junk. That is why the notifications are failing."

**What the log actually shows:**

The data protection warnings are *present* in the log:
```
[18:02:41 WRN] Storing keys in a directory '/app/.aspnet/DataProtection-Keys' that may not be persisted outside of the container.
[18:02:42 WRN] No XML encryptor configured. Key {3c8e5a19-7b62-44d0-a8f1-9e2d47c6b085} may be persisted to storage in unencrypted form.
```

However, these are **warnings about key persistence at rest** — they would matter if the service needed to decrypt data (e.g. cookies, tokens) written by a previous container. They do **not** cause SMTP authentication to fail.

The actual repeated error is:
```
System.Net.Mail.SmtpException: The SMTP server requires a secure connection or the client was not authenticated.
The server response was: 5.7.139 Authentication unsuccessful, basic authentication is disabled.
SMTP status code: 535
```

This is an **SMTP server-side policy rejection**. The server at `smtp.example.com:587` is refusing the service account `svc-notify@example.com` because basic authentication has been disabled on the server side. This is a credential/auth-mechanism mismatch, not a key-storage problem.

**Inference (high confidence):** Something changed on or around 14:00 on the SMTP server or the email provider — most likely a policy update that disabled basic auth in favour of OAuth2 or another mechanism. The service was not updated to match.

### 5. Risks and gaps

- **Wrong diagnosis is actively wasting time.** The ticket is at Highest priority with a clear customer-impact label, but the assigned engineer has concluded the cause is key storage and is asking Platform to fix that. That fix will not restore email delivery.
- **Backlog will continue to grow** until the SMTP auth issue is resolved. If the outage extends, customers will receive stale receipts in a burst, which may create its own support burden.
- **Outbox design gap:** No exponential backoff, no dead-letter queue, no maximum retry limit that removes the item. A single poison message can block all subsequent sends. This is a latent reliability issue independent of the current incident.
- **Health check blind spot:** Monitoring will not alert on this failure mode because the health endpoint skips SMTP.
- **Data protection key issue is real but separate.** It should be tracked as its own ticket (e.g. keys lost on pod restart could break any feature that relies on encrypted payloads persisted in the database or session). It is not the cause of this outage.
