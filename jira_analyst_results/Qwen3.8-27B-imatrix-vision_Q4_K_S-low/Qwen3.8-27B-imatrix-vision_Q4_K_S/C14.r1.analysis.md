# Triage: payments-api-prod.log

## 1. What is actually broken

### A. 403 Forbidden from `masterfile-api` — **direct cause of the user report**

- **Commands affected:** `AddPaymentRoutingRuleSecondaryCommand` and `BulkUpdateSecondaryBranchesCommand`
- **What happens:** The payments-api calls `masterfile-api` via Dapr to validate a branch ID before saving a secondary branch. `masterfile-api` returns **403 (Forbidden)** every time.
- **Occurrences in log:** 4 distinct error events (19:09:00, 19:09:10, 19:13:31, 04:01:20), all identical in nature.
- **User-facing impact:** This is exactly the operation the two users reported — saving a secondary branch on a routing rule. The request enters a transaction, the Dapr call fails, the transaction is rolled back, and the user sees a generic failure. The "spinning" is the Dapr call waiting for a response before the 403 comes back.
- **Root cause (inference):** An authentication or authorisation failure between the two services. The Dapr sidecar is presenting an identity that `masterfile-api` does not accept. Likely causes include an expired/rotated OAuth token, a missing or misconfigured Dapr identity annotation, or a change on the `masterfile-api` side (e.g. a new auth policy, a service account change, or a deployment that changed its auth configuration). The log does not show which.

**This is the item to fix first.**

### B. SQL Error 245: Conversion failure in `SearchPaymentRoutingRuleQuery`

- **Occurrences:** 5 error events (03:37:32, 03:38:24, 03:38:50, 03:40:12, 20:26:31)
- **Message:** `Conversion failed when converting the ****** value '******' to data type ******.` (actual values are masked)
- **Impact:** Intermittent failures when searching/filtering routing rules. Some searches in the same time window succeed (e.g. 03:38:46 completes in 465 ms, 03:46:26 in 222 ms), so the failure is data-dependent — certain row values trigger the conversion error while others do not.
- **Likely cause (inference):** A data-quality problem in the `PaymentRoutingRule` table (or a joined table). A value stored in a column is not compatible with the type the query expects (e.g. a non-numeric string in a column the query casts to `INT`, or a malformed date). The masking prevents identification of which column or value.
- **Priority:** Second. It degrades search functionality but does not block saves.

### C. Execution timeout on `GetMonitorJobsQuery`

- **Occurrences:** A burst of 7+ timeouts between 22:26:37 and 22:29:08, then the same query succeeds normally from 22:36:47 onward.
- **Impact:** Users viewing the pending-payment monitor screen would have seen failures or long waits during that ~3-minute window.
- **Likely cause (inference):** Transient database contention — a lock, a long-running query, or connection-pool pressure that resolved on its own. The subsequent slow `GetStatementLineQuery` warnings (33–73 s, starting 00:20) suggest the database was under sustained pressure around the same period, though the timing is uncertain because the log has no dates.
- **Priority:** Third. It self-resolved but the pattern (burst of timeouts, then slow queries) warrants a database-team check on what was running at that time.

---

### D. Validation exception on `UpdatePaymentRoutingRuleCommand` (RuleSetId 41003)

- **Occurrences:** 2 rapid retries (22:35:24 and 22:35:32)
- **Message:** `ApplicationValidationException: Application validation errors have occured.`
- **Assessment:** This is the application correctly rejecting a request that violates business rules. It is not a bug in the API itself, but the error message is unhelpful — it does not say *which* validation failed, making it impossible for the user (or support) to act on it. The 8-second gap between the two attempts suggests a user clicking "retry" without changing anything.
- **Priority:** Low. Cosmetic / UX issue. Not related to the reported problem.
