## Summary

Eight open/resolved Sentry issues for bank-ui over the week of 5–12 Sept. Five of them share a single root cause (401 API responses followed by unguarded property access in the UI), one is a post-deploy stale-chunk problem, one is a third-party browser extension, and one is already resolved. The effective defect count is **two**, which fits the sprint capacity.

---

## Grouping by cause

### Group A — 401 cascade: unhandled API error responses in the UI

| Issue | Property accessed | Events | Users | Trigger API |
|-------|-------------------|--------|-------|-------------|
| BANKUI-4A1 | `.sort` | 312 | 41 | (22 × 401 in 40 s, endpoint not specified) |
| BANKUI-4A2 | `.rows` | 289 | 39 | `/api/settlements/CustomerOrder/Search` |
| BANKUI-4A9 | `.returnProperties` | 104 | 33 | `/api/hq/SettlementAllocation/InvokeAction` |
| BANKUI-4B3 | `.length` | 97 | 31 | `/api/payments/PaymentBatch/Actions` |
| BANKUI-3C8 | (raw 401 logged) | 5 140 | 44 | `/api/settlements/Run/GetAllRunBookingsForCustomerOrder` |

**What's happening (inference, based on breadcrumb patterns and error shapes):**
The backend returns a 401. The response body is not the shape the UI code expects (likely an error envelope or empty body). The component then calls `.sort()`, `.rows`, `.length`, or `.returnProperties` on `undefined` and crashes. BANKUI-3C8 is the same 401 events being captured separately by the app's own `console.error` handler — it is `handled: true`, so it doesn't crash the app, but it inflates the event count and is a duplicate signal of the same underlying problem.

**Why this is the defect:** The UI does not check the HTTP status (or the response shape) before accessing properties on the payload. A 401 should either redirect to login or show a user-facing error, not throw a TypeError.

**Combined impact:** up to 44 distinct users, ~5 942 events over 8 days, ongoing (last seen 9 Sept 12).

### Group B — Stale chunk after 4.7.0 deploy

| Issue | Events | Users |
|-------|--------|-------|
| BANKUI-5D6 | 63 | 58 |

**What's happening:** Release 4.7.0 was deployed at `2026-09-10T21:05Z`. The first event for BANKUI-5D6 is at `21:11:36Z` — six minutes later. The requested file `6728.b4f17ce620a8d539.js` returns **404**. The breadcrumb notes "a navigation immediately before." This is the classic stale-cache-after-deploy problem: a user's cached `main` bundle references a chunk hash that no longer exists on the CDN.

**Why it's distinct from Group A:** Different mechanism (network 404 on a JS file, not an API 401), different user population (58 users, wider than Group A), and it started at a precise time (deploy).

**Note:** The same chunk file (`6728.b4f17ce620a8d539.js`) appears as the `lastFrame` for BANKUI-4A1 and BANKUI-4A2. This means those users *did* successfully load chunk 6728 — they are on the new version. The 58 users hitting the 404 are on the old cached version.

### Group C — Not our defect

| Issue | Events | Users |
|-------|--------|-------|
| BANKUI-2F0 | 4 812 | **1** |

- Source: `chrome-extension://hdnmoggkpjoiaeldlphnmgejfcbkadkc/inject.js`
- Error: `SecurityError: Blocked a frame with origin "https://bank-uat.example.com" from accessing a cross-origin frame`
- Breadcrumb: "no app breadcrumbs; every event is from the same browser session"
- This is a browser extension (likely an ad-blocker or tab-manager) injecting a script that tries to access a cross-origin iframe. It is not our code.
- **Action:** Add a Sentry filter to ignore events whose `lastFrame` URL starts with `chrome-extension://`, or mark the issue as "Ignored" with a note.

> This is almost certainly the issue that caused last sprint's misallocation: 4 812 events is the highest event count in the list, but it affects exactly one user.

## Recommended priority for the sprint

| # | What to fix | Why first/second |
|---|-------------|-----------------|
| 1 | **Group A – Add defensive handling for non-2xx API responses** (interceptor or per-component guards) | Affects up to 44 users across 4+ code paths; it is a genuine app defect that will recur for *any* future API error, not just 401. Fixing it in one place (e.g. an Angular `HttpInterceptor` that redirects on 401 and a shared `safeGet` pattern for response access) eliminates all five issues at once. |
| 2 | **Group B – Add a chunk-load-failure retry / "please refresh" fallback** | Affects 58 users (widest reach) and is actively breaking navigation post-deploy. The fix is well-known and small: catch `ChunkLoadError`, attempt a full page reload once, and if it fails again show a user-facing "please refresh" message. It will also protect against future deploys. |

**Separate investigation (not sprint work, but flag to the team):** *Why* are users receiving 401s? The UI fix prevents the crash, but if it's a token-expiry bug or an auth-service outage, users are still being logged out or blocked. This needs a look at the backend/auth side — possibly a separate ticket.

## Risks and gaps

- **No source maps.** Ravi's comment confirms source maps are not uploaded. All `lastFrame` values are minified identifiers (`ie.project`, `q.render`, `L.buildAction`, `N.setRows`). This makes it harder to confirm *exactly* which component or line is at fault without reading the bundle. The Group A fix is still straightforward (add guards), but precise line-level debugging will be painful until source maps are in the pipeline.
- **401 root cause unknown.** The Sentry data tells us the UI crashes on 401s, but not *why* the 401s are happening. Session expiry? Token rotation race? Auth-service misconfiguration? This is outside the scope of the UI fix but should be tracked.
- **User overlap is unquantified.** The JSON notes that the same user can appear in more than one issue. The true number of affected users across Group A is somewhere between 41 and 146 (41+39+33+31+44), likely closer to 41–50 given the same time windows and endpoints.
- **BANKUI-3C8 is a duplicate signal.** It is the same 401 events as the breadcrumbs in 4A1/4A2/4A9/4B3, just captured by a different mechanism (`console` vs `angular.error_handler`). It should not be treated as an independent problem; it will resolve (or at least drop in volume) when the 401s stop or when the console handler is suppressed for expected auth errors.
- **No acceptance criteria or reproduction steps** in the ticket. The analysis above is inferred from the Sentry data; a quick manual repro (force a 401 on `/api/settlements/Run/GetAllRunBookingsForCustomerOrder` and navigate to `/settlements/run/8214`) would confirm.
