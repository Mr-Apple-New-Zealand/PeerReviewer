# Analysis: BANK-471 — Customers not receiving payment receipt emails

## 1. Summary

Email delivery for the notifications service has been failing since approximately 14:00 today. The root cause visible in the attached log is an **SMTP authentication failure (535)** — the server rejects the service's credentials because "basic authentication is disabled." This is not caused by the data protection key warnings that the reporter identifies. The outbox queue is growing (1,412 → 2,089 messages in ~37 minutes) with no successful deliveries and no dead-letter path.

## 3. Does the log support the reporter's explanation?

**No.** Marcus's comment attributes the failure to the data protection key warnings:

> "The service is storing its data protection keys in a directory that is not persisted and there is no XML encryptor configured, so the keys are effectively junk. That is why the notifications are failing."

The log does confirm those two warnings are present, but they do not explain the observed failure. .NET Data Protection keys protect things like anti-forgery tokens and cookie encryption — they are not used for SMTP transport-layer authentication. The actual error in every failed send is an **SMTP server rejecting the client's credentials** because basic auth has been disabled on the server side. These are unrelated systems.

**Inference (labelled):** The error code `5.7.139` is specific to Microsoft Exchange Online / Microsoft 365 and indicates the tenant has disabled basic authentication for SMTP. The most likely scenario is that the M365 tenant (or the service account `svc-notify@example.com`) was migrated or had basic auth disabled as part of a security policy change, and the notifications service was not updated to use OAuth 2.0 (Modern Auth) before that change took effect.

## 6. Risks and gaps

| Risk / Gap | Detail |
|------------|--------|
| **Queue head-of-line blocking** | Outbox item 991204 stays at the head after 5 failed attempts with no backoff and no dead-letter. This means **one permanently failing item blocks all other notifications indefinitely**. Even if the SMTP issue is fixed, if a single recipient is malformed or permanently rejectable, the queue will stall again. |
| **No dead-letter path** | Failed messages are retried forever. No operational visibility into which messages are permanently stuck. |
| **Health check skips SMTP** | `/healthz` reports "Healthy" while email delivery is completely broken. Monitoring is blind to this failure mode. |
| **Lost prior log** | The 14:00–18:02 window is unaccounted for. We cannot confirm whether the failure mode was the same throughout or whether something else was happening earlier. |
| **Data protection key warnings are real but separate** | Keys will be lost on every container restart. This is a genuine reliability and security issue (unencrypted keys on a non-persistent volume) but is **not** the cause of the current outage. It should be tracked separately. |
| **Reporter's misdiagnosis may delay fix** | Marcus has stated the cause is "clear cut" and asked Platform to fix key storage. If the team follows this lead, time will be spent on the wrong problem while the queue continues to grow. |
| **Priya's suggestion to restart again** | This will not help. The cause is a configuration/auth-method mismatch, not a transient state. |
