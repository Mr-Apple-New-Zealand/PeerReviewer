## Summary

The user's authentication token expired during a ~4-hour idle period. When they returned and triggered a UI action, a cascade of API calls returned **401** with empty response bodies. The frontend code then attempted to read properties (`.sort`, `.rows`, `.length`, `.returnProperties`) from the response data object — which was `undefined` because there was no body — and threw an unhandled `TypeError` that crashed the Angular error handler and blanked the screen.

The underlying defect is **not** a missing array in the data model (as Tom Becker initially suspected). It is that the application does not handle 401/auth-failure responses defensively before accessing response data.

## The Underlying Defect

**Primary: No 401 handling before data access.**

The code in the batch actions component (and related components) assumes that a successful HTTP call will always yield a parsed data object. When the response is a 401 with an empty body, the `response.body` or the observable's emitted value is `undefined`, and any subsequent property access throws. The error is unhandled (`"handled": false`) and propagates to Angular's `ErrorHandler`, which blanks the view.

This is a **defensive-coding / error-handling gap**, not a data-model bug. The four different property names (`sort`, `rows`, `length`, `returnProperties`) confirm the pattern is repeated across multiple components or code paths that all make the same assumption.

**Secondary: No client-side token-expiry detection or auto-refresh-on-401.**

The app does perform token refreshes (one is visible in the breadcrumbs), but there is no evidence of an HTTP interceptor that catches 401 responses, attempts a refresh, and retries the request. Instead, the 401 propagates to the component code, which then crashes.

## Risks and Gaps

### Environment contradiction (critical for triage)

The tag says `environment: Production` but every URL in the event is on `bank-uat.example.com`. This means either:

- The UAT instance is reporting to the production Sentry project with a mislabelled environment tag, **or**
- The tag is set by a configuration that does not match the actual deployment.

Tom Becker's question ("confirm which environment this is actually coming from") is answered by the data: **the URLs are UAT**. Whether this constitutes a production incident depends on whether the same code runs in production with the same defect — which is almost certainly the case since the ticket says it affects `bank-ui 4.7.0` and the code is identical. But the *evidence* is from UAT, and that should be stated in any incident write-up.

### Missing source maps / symbolication

All three JS chunks are marked `js_no_source` with DNS resolution failures. This means:

- The function name `ie.project` is minified; we cannot see the actual source line.
- We cannot confirm *which* array the `.sort` call is operating on.
- We cannot confirm whether the 401 cascade is the **only** trigger or whether a network timeout, a malformed 200 response, or a race condition could also produce an undefined data object.

### What this event does **not** let you determine

1. **The exact source code location** of the `.sort` call (no source maps).
2. **Whether the 401 cascade is the sole trigger.** The evidence strongly supports it for this event, but without a repro or additional events with different failure modes (e.g., 500, timeout), we cannot rule out other causes.
3. **The token lifetime.** We know a refresh succeeded ~1 min into the session and the token was dead ~4 h later, so the lifetime is between those bounds, but the exact configured value is not in this data.
4. **Whether an HTTP interceptor for 401 handling exists but is broken, or is simply absent.** The event shows no retry-after-refresh pattern, but we'd need to see the code.
5. **Blast radius.** One event is attached. We don't know how many users hit this, how frequently, or whether it's limited to long-idle sessions.
6. **Whether the `transaction: /settlements/run/8214` is stale.** The user was on `/payments/batch/actions` but the transaction name refers to a different route. This may indicate a navigation-tracking bug or a stale span name, but we can't confirm from this data alone.

### The trimmed stack trace

The attachment note says support "removed the duplicated raw stack trace and trimmed the repeated frames." The frames we do see are all minified polyfills/rxjs error-propagation infrastructure. The **most relevant frame** is the last one: `ie.project` in chunk `6728`. Without symbolication, this is as far as we can get.
