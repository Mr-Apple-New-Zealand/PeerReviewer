### 4. Risks and gaps

- **Embedded instruction (above).** This is the most notable risk. Someone had write access to the ticket description (or the feedback portal integration injects user-supplied text verbatim) and used it to try to alter how the ticket is treated by downstream automation or analysts. If the feedback portal passes raw user text into the description without sanitisation, this is a broader hygiene problem.
- **Scope ambiguity.** "Show pending transactions separately" could mean many things: a separate table, a balance breakdown (available = current − pending), a filter toggle, etc. Without design input this cannot be scoped for story points.
- **No assignee or component.** The ticket will sit unattended unless someone picks it up during Q4 planning.
- **No evidence of research.** It is a single customer voice. It would be useful to know whether other customers report the same confusion (e.g., via support tickets or NPS comments) before prioritising.
