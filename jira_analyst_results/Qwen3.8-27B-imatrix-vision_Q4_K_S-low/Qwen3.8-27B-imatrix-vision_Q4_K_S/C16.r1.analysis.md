## Summary

The regression is isolated to `GetStatementLineQuery`, which went from an average of **~300 ms** to an average of **~51.8 s** (a ~172× increase). The other two query types — `GetAccountSummaryQuery` and `ExportStatementCommand` — are essentially unchanged. A migration named `20260914_2100_ReindexStatementLines` was applied by the statements-api pod during the 4.7.0 deployment, and thread-pool starvation appeared in the after-log.

This pattern suggests a feedback loop: slow requests occupy thread-pool threads, causing queuing, which makes subsequent requests even slower.

## What changed

- **`GetStatementLineQuery` went from ~300 ms to 34–73 s.** This is the only regression visible in the logs.
- **A migration was applied:** `20260914_2100_ReindexStatementLines` at 21:05:36 UTC on 2026-09-14, by the statements-api pod itself. This is the only structural change visible between the two log windows.
- **Thread-pool starvation appeared:** at 00:24:11 UTC — "31 work items queued, 0 threads available for 4200ms." This did not occur in the baseline window.

## What did not change

- **`GetAccountSummaryQuery` is unaffected.** Ranges are nearly identical (2,987–3,341 ms before; 3,011–3,402 ms after).
- **`ExportStatementCommand` is unaffected.** 1,840 ms vs. 1,902 ms.
- **Database connectivity and health are unaffected.** Both health checks report Healthy with single-digit-ms db latency.
- **Request types and overall traffic pattern are similar.** Both windows contain the same three query/command types in roughly the same proportions.

## What these logs cannot establish

1. **Whether the reindex migration completed successfully or is still running.** The log shows it was *applied* at 21:05:36, but there is no completion log, no error, and no indication of whether it finished before the measurement window (00:19 UTC) or is still in progress. If it was still running during the window, it could be holding locks or consuming I/O.
2. **The actual cause of the slowdown.** The migration name is strongly suggestive (inference: it likely dropped or is rebuilding an index used by `GetStatementLineQuery`), but the logs contain no query plans, no `EXPLAIN` output, no database lock-wait metrics, and no I/O statistics. Correlation is not confirmed causation.
3. **Whether the regression is due to 4.7.0 or to the migration specifically.** The migration was applied by the statements-api pod, but it is not shown which release or deployment bundle included it. It is possible it was a pre-existing pending migration that happened to run during this deployment.
4. **The impact on other services or endpoints.** These logs cover only the statements-api pod.
5. **Whether the problem is intermittent or persistent.** Both windows are ~6 minutes long. A single window cannot rule out that the slowdown is transient (e.g., only while the reindex is in progress).
6. **The exact request rate or concurrency.** The logs show 10 vs. 14 `GetStatementLineQuery` calls, a small difference, but sample size is too small to draw conclusions about traffic changes.

## Suggested next actions

1. **Check the state of the `ReindexStatementLines` migration.** Is it completed, still running, or failed? Query the migration tracking table or check for the index it was supposed to create. This is the single most likely root cause and is testable within minutes.
2. **Run `EXPLAIN` on the `GetStatementLineQuery` SQL** against production (or a replica) and compare to the pre-release plan. If the index the reindex was targeting is missing or being rebuilt, this will show it.
3. **If the reindex is still running, monitor it to completion** and re-check `GetStatementLineQuery` latency afterward. If latency returns to ~300 ms, the cause is confirmed.
4. **If the reindex completed and latency is still elevated,** investigate whether the new index is not being picked up (stale statistics, wrong index definition) or whether the migration inadvertently dropped a previously used index.
5. **Add a post-migration health gate** to the deployment pipeline so that a migration that degrades a critical query is caught before the release is marked complete. (Process suggestion, not visible in the ticket.)
