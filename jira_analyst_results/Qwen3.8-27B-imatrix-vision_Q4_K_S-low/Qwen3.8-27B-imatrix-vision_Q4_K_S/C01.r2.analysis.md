## 1. Summary

A timeout during a mobile-web transfer causes the Retry button to fire a second request with no idempotency key, and because the debit and credit are not wrapped in a single database transaction, the result is two debits and one credit. Three customers have been affected so far. A fix (PR #218) is in code review targeting the 3.2.0 release.

## 3. Key Details

**Root cause (two compounding defects, per Priya's comment 2026-09-09):**
1. No idempotency key on the transfer endpoint — Retry creates a new transaction rather than resuming the original.
2. Debit and credit are separate database commits — when the credit times out, the first debit is already durable.

**Reproduction (staging, confirmed by both Priya and Tom Becker):**
- Mobile web, own-account transfer, >30 s latency injected via toxiproxy, tap Retry after ERR_TXN_504.

**Scope:**
- Affected version: 3.1.4
- Affected surface: mobile web only. Tom Becker (2026-09-10) confirmed desktop web is **not** affected (submit button is disabled, no Retry button).

**Log evidence (from ticket description):**
```
09:41:02  debit committed txn=8841 account=***1180 amount=250.00
09:41:32  credit failed   txn=8841: timeout after 30000ms
09:41:40  debit committed txn=8842 account=***1180 amount=250.00
09:41:41  credit committed txn=8842 account=***2271 amount=250.00
```
txn=8841 is the first attempt (debit only). txn=8842 is the retry (both debit and credit succeed).

**Missing from ticket:**
- No acceptance criteria beyond "one debit, one credit" — no mention of what the UI should display if the timeout occurs (e.g., should Retry be disabled, should the user be told the first attempt may have partially succeeded?).
- No linked issues or duplicate tickets referenced.
- No attached screenshots.
