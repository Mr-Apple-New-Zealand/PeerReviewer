## BANK-482: Log Comparison — Quantified Regression

### Summary

`GetStatementLineQuery` went from ~300 ms to 34–73 s (a **~110× to 240× regression**) after the 4.7.0 deployment. No other endpoint in the log shows meaningful change. The deployment applied a migration explicitly named `ReindexStatementLines`, which is the most likely cause.

---

### Quantified comparison

| Endpoint | Before (4.6.3) | After (4.7.0) | Change |
|---|---|---|---|
| `GetStatementLineQuery` | 281–319 ms (10 samples, mean ≈ 300 ms) | 33 757–72 974 ms (14 samples, mean ≈ 49 970 ms) | **~110×–240× slower** |
| `GetAccountSummaryQuery` | 2 987–3 341 ms (4 samples, mean ≈ 3 171 ms) | 3 011–3 402 ms (4 samples, mean ≈ 3 225 ms) | No meaningful change |
| `ExportStatementCommand` | 1 840 ms (1 sample) | 1 902 ms (1 sample) | No meaningful change |
| Health check (db latency) | 6 ms | 9 ms | No meaningful change |

**Escalation within the "after" window:** query times start at ~34–36 s, climb to ~41–44 s, then jump to ~67–73 s in the final cluster. This is not a flat regression; it is worsening within a single six-minute window.

**New event not present in the baseline:**
> `2026-09-15 00:24:11 [WRN] ThreadPool starvation detected: 31 work items queued, 0 threads available for 4200ms.`

This likely explains the escalation: as `GetStatementLineQuery` calls tie up all worker threads, subsequent requests queue and their measured latency inflates further, creating a feedback loop.

---

### What changed in the deployment

The after-log shows one new event at pod startup that is absent from the baseline:

> `2026-09-14 21:05:36 [INF] Applied 1 pending migration: 20260914_2100_ReindexStatementLines.`

This is the only deployment-level difference visible in the logs. The migration name directly references statement lines — the same entity that `GetStatementLineQuery` reads.

---

### What did not change

- `GetAccountSummaryQuery` performance is stable (~3 s in both windows). This is relevant because Ravi Kumar's comment suggests this query is the problem, but the data does not support that.
- `ExportStatementCommand` is stable.
- Database connectivity is healthy in both windows.
- No other warnings, errors, or new log lines appear in the after-log apart from the `GetStatementLineQuery` warnings and the thread-pool starvation event.

### What these logs cannot establish

1. **Root cause of the slowdown.** The logs confirm *that* the query is slow but not *why*. Possibilities include: the reindex dropped an existing index before the new one was built (leaving a window of unindexed queries), the new index is on the wrong columns, the query planner switched to a full table scan, or the migration failed partway. None of these are distinguishable from the data provided.

2. **Whether the migration completed successfully.** The log says "Applied 1 pending migration" but does not record duration, row counts, or a success/failure status. A partially applied index rebuild is consistent with the observed behaviour but is not confirmed.

3. **Whether the escalation is purely a thread-pool cascade or a separate worsening.** The jump from ~44 s to ~72 s coincides with the starvation warning, but it is possible the queries are also genuinely degrading (e.g., lock contention on the index). The logs do not separate these.

4. **Blast radius.** We have one pod, one environment, one six-minute window. We cannot tell whether other pods, other regions, or the staging environment are similarly affected, or whether the issue is intermittent at other times of day.

5. **The browser timeout the reporter describes.** The logs are server-side. The actual browser timeout threshold, the total page load time (which may aggregate multiple queries), and the user-facing error message are not captured here.

6. **Whether 4.7.0 changed any application code for the statements path.** The logs only evidence the migration. A code change to the query itself, the ORM mapping, or the connection pool configuration in 4.7.0 cannot be confirmed or excluded from these logs alone.
