# Analysis of BANK-495

## What Actually Happened in the User's Session

The breadcrumbs tell a clear story:

1. **~07:24–07:33 UTC** — The user is actively working on the batch actions screen, performing settlement allocation actions. All API calls return 200. A token refresh at ~07:32:46 (`POST /api/security/token/refresh`) succeeds.

2. **~07:33:33 → 07:49:52 UTC** — A **~16-minute gap** with no activity. The tab was left open.

3. **~07:49:52 UTC** — The user clicks a dropdown toggle, then a dropdown item. This triggers a batch of API calls that **all return 401** (response body size: 0 bytes):
   - `GET /api/settlements/Run/GetAllRunBookingsForCustomerOrder`
   - `POST /api/masterfile/Branch/Query`
   - `GET /api/masterfile/ClearanceType/GetAll`
   - `GET /api/hq/SettlementBatch/GetAllDistinctCustomerGroup`
   - `POST /api/masterfile/Period/Query`

4. **Immediately after the 401 burst**, multiple TypeErrors fire (captured as breadcrumb `sentry.event` entries):
   - `Cannot read properties of undefined (reading 'rows')` — ×2
   - `Cannot read properties of undefined (reading 'returnProperties')` — ×1
   - `Cannot read properties of undefined (reading 'length')` — ×1

5. **The main exception for this event** — `Cannot read properties of undefined (reading 'sort')` — fires when the user navigates back to `/payments/batch/actions`, triggering `GET /api/hq/PaymentBatch/Get` and `GET /api/payments/PaymentBatch/Actions`, both of which also return 401.

6. The user then navigates through several sub-pages and back, with continued 401s. The screen is effectively unusable.

**In short:** the user's session token expired during inactivity. When they resumed, every API call returned 401 with an empty body. The code attempted to read properties (`.rows`, `.sort`, `.length`, `.returnProperties`) from the empty response and crashed.

---

## The Underlying Defect

**Primary defect: No 401 handling in the data-fetching pipeline.**

When an HTTP 401 is returned, the code path in `ie.project` (chunk `6728.b4f17ce620a8d539.js`, an RxJS operator) treats the response as if it were a successful payload and calls `.sort` (or `.rows`, `.length`, etc.) on the response body — which is `undefined` or `null` because the 401 response has a zero-byte body. This unhandled TypeError propagates through Angular's error handler and crashes the component tree, producing the blank screen.

**Contributing factor: Token refresh failure.**

A token refresh mechanism exists (proven by the successful `POST /api/security/token/refresh` at 07:32:46), but it clearly did not prevent or recover from the 401s at 07:49:52. Possible explanations (inference, not confirmed by the event):
- The refresh token itself had expired by that point.
- The interceptor only refreshes for a subset of requests.
- Multiple simultaneous 401s triggered a race condition in the refresh logic.

The event does not contain a second refresh attempt in the 401 window, which is notable.

## Critical Discrepancy: Environment

| Field | Value |

| `url` | `https://bank-uat.example.com/payments/batch/actions` |
| Transaction | `/settlements/run/8214` |

The Sentry environment is tagged **Production** but the hostname is explicitly **bank-uat**. This is either:
- A misconfigured environment tag in the UAT deployment (the Sentry SDK is set to report as "Production"), or
- A naming convention where "uat" is the actual production domain (unlikely given the "example.com" TLD and the "uat" segment).

**Tom Becker's comment flags this correctly.** Until this is resolved, the ticket's High priority and production-incident framing are unconfirmed.

## Suggested Next Actions

1. **Resolve the environment question** (Tom Becker or DevOps). Confirm whether `bank-uat.example.com` is UAT or Production, and fix the Sentry environment tag if it's misconfigured. This determines whether this is a production incident.

2. **Fix the source-map / symbolication pipeline.** Sentry's scraping failed because it tried to resolve `bank-uat.example.com` via `google.internal` DNS. Either:
   - Upload source maps to Sentry at build/deploy time, or
   - Fix the public URL and DNS so Sentry's crawler can fetch the bundles.
   Without this, no future events from this app will be symbolicated.

3. **Add a 401 interceptor guard** (assign to a developer once environment is confirmed). The HTTP interceptor should:
   - Detect 401 responses.
   - Attempt token refresh (single-flight, deduplicated across concurrent requests).
   - Either retry the original request or redirect to login.
   - **Never** pass a 401 response body into the data-mapping layer.

4. **Add defensive null-checks** in the RxJS `map`/`mergeMap` operators in chunk 6728 (or wherever the batch actions component fetches data). Even with a proper interceptor, a guard on `.sort`, `.rows`, `.length` prevents a blank screen if an unexpected empty response ever slips through.

5. **Build a reproduction:** Open the batch actions screen, wait until the token TTL expires (or manually expire the token in dev tools), then trigger a data-fetching action. Confirm the crash. This should be straightforward once the environment question is settled.
