# Triage of payments-api-prod.log (OPS-92)

## 1. Summary

The user-reported "spins then says it failed" when saving a secondary branch is caused by the payments-api receiving **HTTP 403 (Forbidden)** from `masterfile-api` via Dapr service invocation. Two distinct commands are affected: `AddPaymentRoutingRuleSecondaryCommand` (single-branch save) and `BulkUpdateSecondaryBranchesCommand` (bulk save). A separate, unrelated data-level SQL conversion error is also present and intermittently breaking the routing rule search view.

## 3. Key Findings (broken vs. noise)

### A. CRITICAL – Dapr 403 from masterfile-api (the reported issue)

**What the log shows (verbatim):**

```
Dapr.Client.InvocationException: An exception occurred while invoking method:
'branchlocation/get?ID=71&includeDetails=False' on app-id: 'masterfile-api'
 ---> System.Net.Http.HttpRequestException: Response status code does not
indicate success: 403 (Forbidden).
```

And for the bulk variant:

```
Dapr.Client.InvocationException: An exception occurred while invoking method:
'branchlocation/GetAll' on app-id: 'masterfile-api'
 ---> System.Net.Http.HttpRequestException: Response status code does not
indicate success: 403 (Forbidden).
```

**Occurrences (time-of-day only, no date in log):**

| Timestamp | Command | Endpoint |
|-----------|---------|----------|
| 19:09:00 | AddPaymentRoutingRuleSecondary (BranchID 71) | `branchlocation/get?ID=71` |
| 19:09:10 | BulkUpdateSecondaryBranches | `branchlocation/GetAll` |
| 19:13:31 | AddPaymentRoutingRuleSecondary (BranchID 71) | `branchlocation/get?ID=71` |
| 04:01:20 | BulkUpdateSecondaryBranches (BranchID 72) | `branchlocation/GetAll` |

**Impact:** Directly blocks users from saving secondary branches on routing rules. This is the exact symptom reported. The "spinning" is consistent with the Dapr gRPC call hanging or the UI polling before the 403 propagates back.

**Ownership:** This is a **service-to-service authentication/authorization failure**. The payments-api is calling masterfile-api through Dapr and being denied. This is **not** a database issue. It needs either:
- The Platform/Infra team to check Dapr/mesh auth policy changes, or
- The masterfile-api team to check why they are returning 403.

> **Priya Nair's question answered:** This is a Platform or masterfile-api issue, not a database-team issue.

## 5. What the Log Does NOT Let You Determine

- **Root cause of the 403.** Is it a Dapr mTLS certificate expiry? A new authorization policy? A missing service account binding? The log only shows the symptom.
- **Whether the 403 is new or chronic.** Without dates, we cannot tell if this started hours ago or has been present for days (possibly silently failing for other commands that aren't user-visible).
- **The exact data causing SQL Error 245.** The values are masked.
- **Whether the two user reports are the same incident or two separate ones.**
- **Whether the GetMonitorJobsQuery timeouts and the GetStatementLineQuery slowdowns are related** (possible shared DB resource contention, but timestamps don't overlap cleanly).
