**Summary**  
A bug in the mobile web transfer flow causes the source account to be debited twice when a transfer times out and the user taps "Retry". This occurs because the retry initiates a new transfer without an idempotency key, and the debit and credit operations are not wrapped in a single database transaction. Three customers have been affected. The fix is in progress and targeted for release 3.2.0.

**Key Details**  
- **Steps to Reproduce**:  
  1. Log in on mobile web and start a transfer between two own accounts.  
  2. Introduce >30s latency (e.g., via toxiproxy).  
  3. When "ERR_TXN_504" appears, tap Retry.  
- **Affected Component**: Transactions  
- **Affected Version**: 3.1.4  
- **Fix Target**: 3.2.0  
- **Expected Result**: One debit, one credit.  
- **Actual Result**: Two debits, one credit.  
- **Log Evidence**:  
  - First debit committed (txn=8841).  
  - Credit failed (timeout).  
  - Second debit committed (txn=8842).  
  - Second credit committed (txn=8842).  
- **Customer Impact**: 3 customers affected; manual reversal required.  
- **Acceptance Criteria**: Not explicitly stated. Inferred:  
  - Retry should not cause duplicate debits.  
  - Debit and credit must be atomic (single DB transaction).  
  - Idempotency key must be respected on retry.
