**BANK-482 — Log comparison for Statements API**

**Summary**
Opening a customer statement is slow / timing out after release 4.7.0. The attached 5-minute windows show a severe regression for `GetStatementLineQuery` on 4.7.0 with a migration applied at start-up, while `GetAccountSummaryQuery`, `ExportStatementCommand` and DB health check latencies are essentially unchanged.

### Quantified regression

**GetStatementLineQuery**
* Before, App=4.6.3, 2026-09-13 00:19-00:25 UTC: 10 samples, 281 ms to 319 ms. Range ~288-319 ms.
* After, App=4.7.0, 2026-09-15 00:20-00:24 UTC: 14 samples all logged as long-running >10 s, 33,757 ms to 72,974 ms. Range ~35 s to ~73 s.
* Regression: ~100-250x increase, from ~0.3 s to tens of seconds.

**GetAccountSummaryQuery**
* Before: 3,102 ms; 3,341 ms; 2,987 ms; 3,255 ms
* After: 3,188 ms; 3,402 ms; 3,011 ms; 3,297 ms
* No material change. ~3.0-3.4 s both windows.

**ExportStatementCommand**
* Before: 1,840 ms
* After: 1,902 ms
* Essentially unchanged.

**Health check /healthz**
* Before: db 6 ms healthy
* After: db 9 ms healthy
* Essentially unchanged.

**What changed in the logs**
* App version: 4.6.3 → 4.7.0
* Start-up event on 4.7.0: `2026-09-14 21:05:36 [INF] Applied 1 pending migration: 20260914_2100_ReindexStatementLines.`
* New warnings on 4.7.0: `Long-running request GetStatementLineQuery took 35171ms … 72974ms (threshold 10000ms)` and `ThreadPool starvation detected: 31 work items queued, 0 threads available for 4200ms`
* `GetStatementLineQuery` no longer completes in ~300 ms; all observed requests are long-running.

**What did not change**
* `GetAccountSummaryQuery` latency remains ~3 s.
* `ExportStatementCommand` latency remains ~1.9 s.
* DB health check latency remains low, 6 ms → 9 ms.

### What these logs cannot establish

* Cause: logs show correlation with 4.7.0 start-up and migration `20260914_2100_ReindexStatementLines`, but do not prove the migration or any code change caused the slowdown.
* Browser timeouts / “unusable” user experience: no client-side data, only API request durations.
* Scope and reproducibility: only one 5-minute window per side is shown; cannot confirm this is representative.
* Root cause of thread-pool starvation: logs report starvation, not why `GetStatementLineQuery` became slow, nor whether starvation is cause or symptom.
* Whether 4.7.0 touched Statements code: Tom Becker comments “Nothing in 4.7.0 touched statements. The release was notifications and the admin screens.” The logs show a statements-api migration applied on 4.7.0 start-up, a conflict that is not resolved by logs alone.
* Query plans, DB indexes, data volume, or configuration differences between the two windows.

Inference: The regression is isolated to `GetStatementLineQuery` and coincides with the 4.7.0 deployment and the `ReindexStatementLines` migration. This is an inference from timing correlation only; logs do not confirm causation.

**Risks / gaps**
* Conflicting statements about scope: Tom’s comment that statements were untouched vs migration applied to statements-api on 4.7.0.
* Ravi Kumar’s comment in BANK-482 suggests `GetAccountSummaryQuery` as the usual slow query. Logs show `GetAccountSummaryQuery` is unchanged; the degradation is in `GetStatementLineQuery`.
* No acceptance criteria, reproduction steps, affected customer count, or error rate metrics are present in the ticket.
* No Fix version is set; ticket is Open, High priority, assigned to Tom Becker, reported by Hana Sato.
