**BANK-482 – Statements page unusable since release 4.7.0**

### Summary
The statements API is regressing on `GetStatementLineQuery` after the 4.7.0 deployment. The before-release baseline shows the query completing in ~300 ms. After 4.7.0 the same query is logged as long-running at 35-73 s and triggers thread-pool starvation. `GetAccountSummaryQuery`, `ExportStatementCommand` and DB health check latency are unchanged.

### Regression quantification from the two logs

**What changed**

* App version: `4.6.3` in `statements-api-before.log` 2026-09-13 00:19:02 vs `4.7.0` in `statements-api-after.log` 2026-09-14 21:05:33
* Migration applied after start in after log: `2026-09-14 21:05:36 [INF] Applied 1 pending migration: 20260914_2100_ReindexStatementLines.`
* `GetStatementLineQuery`
  * Before: 10 completions logged 281-319 ms. Range 281-319 ms, ~300 ms typical.
  * After: 0 normal completions logged. 14 long-running warnings logged 35,171 ms to 72,974 ms. Range 35.2 s – 73.0 s. Approx average ~51.8 s for the logged warnings.
  * Regression ~125x at the low end, ~240x at the high end vs baseline.
* Thread pool: after log shows `2026-09-15 00:24:11 [WRN] ThreadPool starvation detected: 31 work items queued, 0 threads available for 4200ms.` No such warning before.

**What did not change**

* `GetAccountSummaryQuery` latency:
  * Before: 3,102 ms, 3,341 ms, 2,987 ms, 3,255 ms
  * After: 3,188 ms, 3,402 ms, 3,011 ms, 3,297 ms
  * ~3.0-3.4 s before and after.
* `ExportStatementCommand`:
  * Before: 1,840 ms
  * After: 1,902 ms
* Health check DB latency:
  * Before: `db 6ms`
  * After: `db 9ms`

### What these logs cannot establish
* Root cause. The logs show correlation with 4.7.0 and the `ReindexStatementLines` migration, but do not prove causation.
* Whether `GetStatementLineQuery` is the actual code path used by the “opening a customer’s statement” UI. The description assumes it is, but the logs do not show client request mapping.
* Why Tom Becker states nothing in 4.7.0 touched statements, while a migration was applied at API start-up.
* Completion rate / timeouts. After log only records warnings for long-running requests; it does not show final completion or failures.
* Load / concurrency context. No request counts per minute, no concurrent user numbers, no error counts.
* DB-level details. No query plans, index usage, lock waits or reindex status beyond the migration applied line.
* Release timing. API start time is 2026-09-14 21:05:33, but the release window is not documented in the logs.

Inference, based on logs: the degradation is specific to `GetStatementLineQuery` and coincides with app 4.7.0 start and the `20260914_2100_ReindexStatementLines` migration. The account summary query suggested by Ravi Kumar is unchanged, so the logs do not support that hypothesis.
